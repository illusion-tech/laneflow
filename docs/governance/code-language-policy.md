# 代码语言立项审查

**状态**：Active  
**生效日期**：2026-09-26  
**依据**：#765；维护者明确要求未来非 Rust 代码进入正式仓库前完成立项审查。

规范术语“代码语言立项审查”（Code Language Proposal Review）登记于
[术语表](../reference/glossary.md)，本文规定其适用范围与人流程。

## 1. 默认语言与覆盖范围

LaneFlow 新增实现默认使用 Rust。**今后一切拟进入正式仓库的非 Rust 代码，都必须
先立项审查并取得明确接受结论。** 这项要求独立于 G1：G1 不适用不代表语言审查豁免。

范围覆盖新增及修改后拟合入的非 Rust 代码，包括产品实现、工具、研究、测试、构建、
CI、维护脚本、生成代码、提交到仓库的第三方代码，以及配置或文档中承载执行逻辑的
嵌入代码。不得因“临时”“只是研究”“几行脚本”“自动生成”而跳过审查。

按内容判断，不按后缀判断。例如 workflow YAML 中的 shell `run`、HTML 中的 JavaScript、
文档中的可执行程序示例均属于非 Rust 代码。纯数据、声明式配置、自然语言说明以及
仅说明工具参数的命令调用不属于程序实现；若其中嵌入执行逻辑，嵌入部分仍适用本规则。

规则不追溯宣布历史提交违规，也不要求一次性迁移全部存量代码。今后修改存量非 Rust
代码时，拟合入部分仍须有覆盖该变更的审查。只删除非 Rust 实现不需要语言例外；
历史测量源码可保留在冻结 Git 提交中，不应为清理当前入口重写历史证据。

## 2. 立项审查记录

在编写或引入拟入库的非 Rust 代码之前，先在 GitHub Issue 中记录语言选型审查。
已有任务 Issue 可以承载，不要求机械新建一个 Issue。审查至少包含：

1. 用途、选用语言、拟涉及的路径、预计代码范围及维护责任。
2. Rust 方案与现有 Rust 工具的适用性，选择非 Rust 的具体必要性和替代方案。
3. 新增解释器、编译器、依赖、跨平台支持和维护成本；适用的依赖/许可证/安全要求。
4. 验证和 CI 方式、可复现入口、产物与证据保存方式。
5. 适用期限或持续保留理由，以及迁移、替换或删除的条件。
6. **维护者明确接受的审查结论及其链接**，并注明接受的语言、用途和路径范围。

官方 Issue 表单在建单时询问非 Rust 代码计划，并提供审查记录入口。建单时可注明
“尚未确定”或“待审查”；这只记录待决事项，不代表接受。实现前必须明确语言范围，
涉及非 Rust 方案时补齐以上记录与接受结论，才能进入该方案的 G2。

“已经开 Issue”、Project 为 Ready、CI 通过、历史上存在同语言、Agent 自行评估方便，
都不能替代接受结论。没有接受结论时不得将该非 Rust 方案作为已获授权实现，也不得合入。
Agent 可以继续推进 Rust 方案，或整理可审查的方案材料；不得自行豁免语言审查。

审查接受仅覆盖所记录的范围。新增语言、用途或路径，或实质扩大范围/工具链/维护成本，
必须先补充审查；不得用一个历史研究脚本的接受结论覆盖整个仓库。
对已接受范围内的后续变更，PR 必须说明原结论如何覆盖本次变更，无需重复开单。

## 3. 开工与合入

- G0 阶段识别是否新增或修改非 Rust 代码（纯删除除外）；有则完成上节立项审查，再进入该方案的 G2。
- PR 明确是否新增或修改非 Rust 代码（纯删除除外）；若有，链接对应 Issue、接受结论，并列出本次范围。
- 审阅者核对实际 diff 与接受范围，包含嵌入代码；缺失或超出范围时不应合入。
- 原有 G1、测试、安全扫描、未解决审阅对话及 Merge Queue 规则继续适用。

本规则属于 G0/G2 人流程及代码审阅要求，不增加机器合并门禁，也不由 CI 解析 Issue
正文、评论或接受结论链接。审阅中发现不符合时，通过普通 review conversation 提出并处理；
未解决对话仍由 GitHub 原生规则拦截，遵循 ADR 0026/0027。
未引入扩展名白名单或声称 CI 能判断所有代码语言；不得把自动检查未报错解释为语言选型已获接受。

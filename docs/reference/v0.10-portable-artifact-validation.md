## 1. 计划撰写时实现事实与禁止误读

- 上述参考快照中，`laneflow-compiler::CompilationOutput` 已原子拥有配对的
  `ValidatedCanonicalLir` 和 `ValidatedSourceMapInput`；
- 上述参考快照的 workspace 没有 `laneflow-format`，也没有 LFCA/LFSM/LFSD/LFCP 生产实现；
- 上述参考快照的 `CompilationMetrics::semantic_fingerprint` 只服务同版本重复编译和性能证据，
  不是 artifact digest 或 `NetworkRevisionId`；
- #292/#296 的成功 CI 证明前置编译器和 production source 已交付，不证明 #298 格式；
- 本计划中的“预期”“必须”不是已执行结果。G2 后只能把实际命令、提交、原始输出和
  digest 登记到 #298 Gate Ledger 或对应实现 PR 的证据区，不能把计划表改写成追认式通过。

publication 入口另把调用方当前选择的同一份 `FormatLimits` 重新应用到已经由较宽预算发射的

## 4. 已知向量与独立复核

G1 不建设向量平台。设计正文直接保存两个 revision 的完整构造配方、逐节长度/摘要、
payload 长度/摘要、单 byte 差异 offset，以及四类对象的公共目录 offset 锚点；非作者
必须能用任意通用十六进制查看器和 SHA-256 工具人工复算。该复核不要求 JSON、JSON
Schema、xtask、代码生成器或仓库内第二套 emitter。

G2 才把设计冻结的语义输入 materialize 为固定 `expected.lfca/.lfsm/.lfsd` bytes；LFCP 的
#298-owned 外部 binding 可先用明确标注的 opaque receipt stand-in 固定完整 hex，#299 receipt
格式冻结后再增加真实 receipt+LFCP 联合向量，不能把 stand-in 追认为 receipt wire。每组 fixture 使用普通 Markdown README 记录
语义输入、版本、length、digest、revision 和关键 offset，不增加机器可写的
`expected.json`。测试只读固定 expected bytes，禁止先调用 production emitter 覆写期望
再与自身比较。更新 expected bytes 必须在 PR 中展示语义差异、版本决策和旧向量处置。

## 5. 跨平台与确定性执行矩阵

本矩阵按风险职责分配证明，不把 OS、process、规模和安全边界解释为自动笛卡尔积。#298 的
[G1 窄纠正][g1-evidence-lanes-correction] 冻结三个互补通道：

| 证明通道                   | OS/process                                                                              | workload / boundary              | 比较或接受条件                                                                           |
| -------------------------- | --------------------------------------------------------------------------------------- | -------------------------------- | ---------------------------------------------------------------------------------------- |
| Cross-platform exact bytes | Windows `x86_64-pc-windows-msvc`、Ubuntu `x86_64-unknown-linux-gnu`；两个 fresh process | min headless；full spatial       | LFCA/LFSM/LFSD exact bytes、digest、length、revision；当前正式 worker 集合 `{1}`         |
| P100 resources             | `LF-P100-REF-01`；两次 fresh process                                                    | P100 正式最高级                  | emitter/rehash/端到端时延、输出大小和候选暂存；不作为共享 runner exact-byte workload     |
| Format safety              | Windows、Ubuntu                                                                         | hard limit、最大可达、下一可构造 | `SEC-012/015` 的 boundary/`limit+1` 接受或稳定失败点；不物化上传巨型 emitter exact bytes |

共享 exact-byte CI 必须上传或核对同一已知摘要，不接受“各平台测试都绿但没有交叉比较 actual
bytes”。若某平台尚非 LaneFlow 正式支持目标，只能作为附加观察，不能用它替代 Windows 本机和
当前 Ubuntu required CI 的双轴证据。P100 规模与格式 hard limit 不引入新的 emitter 语义分支，

### 6.2 测量边界

- 工作负载使用 1、2、3、4、5 份完整信号化走廊；输入解析、复制、编译单元构造都在
  停表外；当前 production compiler 正式支持的 worker 集合只有 `{1}`，因此本次
  single-worker 已覆盖全部正式 worker 数；
- 每个 fresh process、每一级先预热一次，再取得 7 个正式样本；分别计量 production
  emitter、对三份最终 exact bytes 的独立 SHA-256，以及
  `Compiler::compile + emitter` 端到端墙钟；独立 rehash 不是对 emitter 内部 hash 阶段的
  拆分归因，也不与 emitter 时间相加；
- `staging_peak_exact_bytes` 是返回候选时同时存续的 LFCA+LFSM+LFSD 三个
  `Box<[u8]>` 的精确长度之和。它是设计冻结的候选暂存记账，不等于进程 RSS、allocator
  capacity 或编译器拥有的中间结构；`compiler_controlled_peak_bytes` 继续作为另一项独立
  编译器指标报告，不把两者相加冒充实测联合 heap 峰值；
- 每一级都把候选暂存调用方上限设置为该级 exact total `- 1`，并断言在下一对象分配前
  返回 `CandidateStagingLimitExceeded`，因此失败不返回或保留部分候选；两个用于成功路径的
  compiler 实例在全部轮次后各自 retained bytes 均为 `0`。原始 wrapper 输出中的
  `failure_retained_bytes` 是第二个 compiler 实例 retained 值的显示标签，不是独立 allocator
  post-failure 测量；本证据不据此声称进程 allocator 已释放全部容量。

### 6.5 结论与禁止外推

- #298 已取得修复前基线和修复后当前提交在既有合法 P100 production workload 上的 emitter、
  independent rehash、端到端增量墙钟、三类输出大小、候选暂存、编译器控制峰值、compiler
  retained 与失败不产生部分候选的证据，并补充 Genesis/Artifact 两条生产路径的分配流量和
  返回时净存活增量；
- 两个 fresh process 的绝对墙钟存在正常实验噪声，部分相邻级别不严格单调；本证据只保存
  描述性结果，不从 14 个样本拟合趋势、SLA 或新预算；
- 当前没有已接受的 portable emitter 产品 SLA 可供 Pass/Fail 比较。#292 的生产 R0 只覆盖
  `Compiler::compile`，明确排除 portable artifact 发射；因此本节关闭 #298 的测量证据缺口，
  不声明新的 Product Pass；
- 格式硬上限继续由设计正文作为安全天花板冻结。G2 测量不修改同一 wire version 的常量，
  也不把 #292 内部 LIR 的 `output_logical_bytes` 当作 LFCA 文件大小。

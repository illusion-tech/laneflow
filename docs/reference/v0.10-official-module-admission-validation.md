## 1. 实现范围

本轮只实现全部官方前端共享、且已经由 #315 G1/G2 授权的编译器基础：

- `CompilationUnit` 只保留编译器私有的共同 `TypedAstModule` / `TypedAstDeclaration`；
- 各具体官方模块只能通过字段私有包装进入同一条私有、原子准入路径；生产公共面没有
  第三方 `SourceLanguage`、通用 `add_module` 或可伪造的中间能力值；
- 逻辑 `SourceModuleDescriptor` 与一个或多个 `SourceDocumentDescriptor` 分离，模块使用
  版本化 `sourceDocumentSetDigest`，文档各自绑定键、SHA-256、精确来源记录长度、所属
  命名空间和冷显示/审计来源；
- 文档集摘要 v1 对按文档键排序后的紧凑描述符做一次 SHA-256；来源记录在模块构建完成后
  不进入编译单元保留状态；
- `LF-COMP-P100-INITIAL-v1` 保持不可变且只接受每模块一份文档；
  `LF-COMP-P100-INITIAL-v2` 只新增 `max_source_document_count = 1566`，没有默认值、
  自动升级或配置档身份混淆；
- 共同准入在提交前统一检查命名空间、文档键、导入、所有资源维度和控制存续内存；构建器
  载荷、模块向量、模块索引与文档索引组成增量存续账本，任一失败都不改变 builder；
- 共同准入内部以 `AdmissionPlan` 表达“已校验、未提交”事务，以 `AdmissionTotals`
  一次替换全部累计资源状态；文档索引只能从 `PendingSourceDocumentIndex` 消费式冻结为
  `FrozenSourceDocumentIndex`，源映射只取得具名解析结果；
- 共同准入建立并持久保留文档键到“所属规范模块序号 + 紧凑文档序号”的索引；`build`
  原位冻结绑定，来源映射复用它而不再次分配哈希表；
- 每个位置以自身 `SourceSpan.source_document_key` 和真实所属 MIR 模块共同解析；未登记键与
  跨模块错绑均返回 `LF-COMP-SOURCE-DOCUMENT-OWNERSHIP-MISMATCH`，不 panic、不静默误归因；
- `build` 在任何图工作集分配前，以模块/导入计数计算拓扑排序、Tarjan 环检测、规范重排和
  转换阶段的最大 scratch，并分别检查 `StageScratchBytes` 与包含构建器/输出共存关系的
  `CompilerControlledLiveBytes`；成功 `CompilationUnit` 只保留实际结果拥有的载荷、文档
  索引和 `TypedAstModule` 包装账本；
- 文档索引、平坦源映射文档描述符输出以及源映射 scratch 均进入统一资源预算。

明确不在本轮范围内：

- #296 的几何文档线格式、领域解析、文档角色和专用降阶；
- #297 的当前 ScenarioManifest / Traffic / Spatial 原始输入签名、来源验证、严格导入策略、
  三文档角色和专用降阶；
- 第三方自定义前端扩展点、可移植规范制品、独立验证器或生产路径切换。

因此本轮不能声明 #296 或 #297 已实现，也不能在 #315 G4 前解除它们的 G2 阻塞。

## 2. 正确性、配置档版本边界与失败关闭证据

新增或扩展的测试证明：

- v1 精确字段保持不变；v2 除 `SourceDocumentCount` 外逐维等于 v1；
- v1 多文档模块返回结构化 `LF-COMP-PROFILE-INCOMPATIBLE`，随后可用合法模块重试；
- v2 在 1566 份文档边界成功，1567 份失败，失败后 builder 状态不变；
- 同一候选内部以及既有编译单元之间的重复文档键均失败关闭；
- 共同准入负责的 17 个增量累计资源维度逐项触发精确维度诊断，且每次失败后模块、命名空间
  索引、文档索引和累计计数均保持空状态；`build` 的 scratch 与控制峰值另有边界减一失败、
  精确边界成功测试，限额诊断上下文不受模块加入顺序影响；
- 文档输入重排不改变文档集摘要或冻结顺序；单文档已知向量为
  `e23b2cd10cc8f74c1f21280373cfff89163f63006f262f631506ee4fad2fcf7e`；
- 精确三文档样例中，模块与实体声明位置落到第二份文档、关系位置落到第三份文档，
  第一份文档没有实体声明；模块位置和语义记录位置均冻结独立文档序号，三份冷来源
  可区分且构造期来源字节释放后仍可查询；
- 未登记文档键和借用另一逻辑模块文档键的两个反例均产生结构化归属诊断；模块、声明
  和关系位置与未知 HIR 引用同时出错的组合反例还证明，来源归属在任何 HIR 语义诊断
  前失败关闭，不会把语义错误归因到另一模块的文档；
- 测试计数器证明三份原始文档各执行且只执行一次 SHA-256；
- 测试专用第二官方模块包装复用同一条共同准入路径；compile-fail doctest 证明外部调用方
  不能构造文档描述符字段，也不能调用通用模块接入；
- 准入账本测试精确覆盖构建器模块向量、模块索引、文档索引和结果 `TypedAstModule` 包装；
  522 模块配置档边界可冻结，峰值内存差分测试继续覆盖文档键、unit 文档描述符、持久文档
  索引和源映射平坦文档表；1566 文档边界执行完整 `Compiler::compile`，证明不触发隐含
  scratch 越界。

## 3. 不兼容迁移说明

本切片有意移除旧的一模块一文档公共查询，不提供 deprecated shim、首文档回退或兼容包装：

- `SourceModuleDescriptor::source_content_digest()` 改为模块级
  `source_document_set_digest()`；两者语义不同，不能机械保留旧名称；
- `SourceModuleDescriptor::source_record_byte_len()` 与 `source_document_key()` 移到
  `SourceDocumentDescriptor`；调用方从 `SyntheticModule::source_documents()` 或
  `ValidatedSourceMapInput::source_documents()` 取得逐文档值；
- 单文档摘要与文档集摘要不要求相等。需要逐文档身份的调用方必须显式遍历文档。

因此未来提交和 Delivery PR 必须以 Conventional Commits 的 `!` 与 `BREAKING CHANGE:`
明确发布该迁移；不得把兼容层重新带回实现。

### 5.3 HIR 来源归属前置校验配对结果

外部审阅发现来源文档所有权原先只在源映射冻结阶段检查；当同一声明先触发 HIR 语义错误
时，归属错误会被遮蔽。本修复在 `build_hir` 产生任何语义诊断前，按规范模块和声明结构顺序
复用冻结文档索引，穷尽核对模块、导入、声明及关系位置；遍历不分配，也不保留第二份位置表。

在 rebase 后修复前精确头 `82b41f5` 与本修复候选上，分别以三个独立进程运行第 5.1 节同一
完整 P100 release 基线；每个进程内部仍为 1 次预热和 7 个正式样本。最高级结果如下：

| 样本                   | 三轮中位时延                   | 三轮 MAD                    | 中位数的中位数 | 相对修复前 |
| ---------------------- | ------------------------------ | --------------------------- | -------------: | ---------: |
| `82b41f5` 修复前精确头 | 10.8571 / 12.7592 / 11.6259 ms | 0.0289 / 0.8544 / 0.3170 ms |     11.6259 ms |          — |
| 本修复候选             | 12.4030 / 11.3869 / 12.1501 ms | 0.1168 / 0.0338 / 0.7367 ms |     12.1501 ms |     +4.51% |

修复前后均保持 10 个模块、330 条 `LaneEdge`、20975 条 LIR 记录、600887 逻辑输出字节、
2731087 B 编译器控制峰值、0 B 保留容量和相同语义指纹。新增无分配遍历的配对时延变化低于
百分之五性能门槛，没有资源账本或输出变化；共同准入停表边界本身未改变。

### 5.4 LIR 有类型排列与 owner-local 来源重排

后续审阅确认，HIR 信号组集合的 StableId 顺序只是阶段局部确定顺序，不能替代 LIR 的
完整 Identity v1 顺序。本轮以 crate 私有 `LirEntityOrder<K, O>` 成对拥有 MIR 阶段键的
LIR 顺序和阶段键到 LIR ordinal 的反向映射，并以
`OwnerLocalPermutation<Row>` 保存信号控制器组、相位状态两类无稳定身份关系的 MIR 行地址。
LIR 语义目标与来源位置由同一排列逐项生成，不再把目标 ordinal 临时复用为来源
`localIndex` 后二次排序。反例测试显式证明夹具的 HIR StableId 顺序与 LIR 完整身份顺序
不同，并逐项核对最终 LIR 目标、owner-local 下标和多文档来源行。

该收敛不新增公共 API、crate、依赖、稳定标识或兼容层。每个 owner 的排序次数由 LIR 与
source-map 各一次减少为 LIR 一次；代价是把 8705 条控制器组/相位状态 MIR 行地址保留到
source-map 冻结完成。地址均为受 `StageScratchBytes` 与
`CompilerControlledLiveBytes` 预检的有类型 `u32`，最高级生产工作负载的受控峰值因此从
2731087 B 精确增加 34820 B 至 2765907 B（+1.28%），冻结完成后释放。10 个模块、330 条
`LaneEdge`、20975 条 LIR 记录、600887 逻辑输出字节、0 B 保留容量和语义指纹
`f8bf90d57c8b7eea9045c17dcb59296fe72ce6601619baddf927ea54812b865d` 均不变；相对 #315
初始 3211621 B 基线仍减少 445714 B（13.88%）。本轮单进程 release 运行只用于核对资源、
输出和确定性，不把其墙钟样本升级为新的配对性能结论。

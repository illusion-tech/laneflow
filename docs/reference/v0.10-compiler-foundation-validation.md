## 1. 实现范围

本轮建立三个边界明确的包：

- `laneflow-static-contract`：`no_std` 静态契约值类型、Identity v1 实体/字段登记表、
  `StableId128`、有类型稳定标识和致密逻辑序号；
- `laneflow-compiler`：`Synthetic DSL → typed AST → HIR → MIR → validated Canonical LIR`
  干净单工作线程编译，结构化诊断、来源伴随数据、资源上限和完整 G1 领域子集；
- `laneflow-compiler-test-support`：只接受 `&ValidatedCanonicalLir` 的集成专用当前态投影
  （integration-only current projection）；该包 `publish = false`，不是生产后端。

G1 首批语义覆盖 LaneGraph、横断面所有者树、路口/Movement/ManeuverPath、StopLine、
ManeuverGate、WaitingZone、固定时制 Signals、Parking、ParticipantClass、AccessRule、
VehicleProfile、StaticRoute、CanonicalFrame 和 LaneEdge 规范空间几何。

## 2. 架构与依赖核对

`cargo tree --depth 1` 的本地事实是：

- 生产编译器（production compiler）`laneflow-compiler` 的依赖只有
  `laneflow-static-contract`、`blake3` 和 `sha2`；没有
  `laneflow-core`、`laneflow-spatial` 或 `laneflow-data`；
- `laneflow-compiler-test-support` 单向依赖编译器 + 当前核心/空间层（current
  Core/Spatial）；`laneflow-data` 与 `serde_json` 只作为迁移测试的开发依赖
  （dev-dependency）；
- 当前外部标识（current external ID）、运行时句柄（runtime handle）和
  `SpatialRegistry` 不进入 Canonical LIR；
- 投影从 LIR 的稳定标识（stable ID）与逻辑序号（ordinal）建立 current 对象，不反向
  调用 current 构造器充当编译器语义验证（compiler semantic validation）。

该依赖方向满足 ADR 0020 与 `compiler-foundation.md` 的分层要求。

## 3. 正确性与确定性证据

生产编译器测试覆盖：

- Identity v1 的全部登记实体已知向量、规范字节、BLAKE3-128、重复与碰撞失败关闭；
- 模块闭包、规范依赖顺序、来源描述符与来源位置；
- 各领域的引用、所有者、拓扑、数值、资源上限、错误优先级和失败原子性；
- 声明重排、集合重排、来源变化和进程随机 `HashMap` 顺序不改变规范语义；
- HIR/MIR/LIR 采用私有有类型 `u32` 区块键，Canonical LIR 使用公开有类型 ordinal。

`LF-COMP-CURRENT-EQUIV-v1` 的两个固定样例另行证明：

- 当前加载器（current loader）与独立测试前端（frontend）产生相同的完整 current 静态
  契约快照；
- 完整走廊 66 条 `LaneEdge` 的起点、中点、终点空间采样完全相同；
- 一千个 20 ms 固定步进中的车辆状态与所有核心事件（Core Event）在外部标识
  （external ID）归一化后逐 tick 相同；
- 使用新 `Compiler` 重编译得到相同稳定标识映射与静态快照；
- 多机动门等待区保留 3 个机动门出现项（gate occurrence）和 2 个等待区出现项
  （waiting-zone occurrence）。

## 5. 性能门槛适用性结论

G2 映射发现 `LF-COMP-P100-R0-v1` 的 126 条研究建议不能按原自然身份直接判定生产
编译器：`LF-COMP-ID-v1` 的抽象实体组合无法构造合法生产机动路径，模块图的抽象
`crossModuleReferences` 也不能在不新增领域声明的情况下映射为 Synthetic DSL；研究
阶段记录与受控分配不是生产 HIR/MIR/LIR 的观测值。精确差额与禁止伪预算规则见
`compiler-foundation.md` 第 11.4 节。

因此当前事实是：

- `LF-COMP-P100-INITIAL-v1` 资源上限仍有效，并已由生产入口执行失败关闭；
- #308 仍是容量估算与实现选型输入，不因本发现失去研究价值；
- 两个固定样例证明迁移正确性和小输入固定成本，但不能替代规模扩展生产基线；
- 不能勾选 #292 的 compile latency、retained memory、规模扩展验收项，也不能记录整体
  G3 Pass。

整体 G3 前必须新增 append-only G1 修订判断，冻结新的生产性能证据边界。建议采用：

1. 保留 #308 作为非门禁容量估算输入；
2. 以可编译的真实产品场景和生产编译器建立首轮规模阶梯；
3. 只测回答 #292 验收所需的总时延、规模扩展和实际可观测内存，不复刻 #308 的研究
   替身、进程隔离或大体积原始记录/证据（raw/evidence）流程；
4. 取得生产基线后同步 `compiler-foundation.md`、glossary、roadmap 与 #292 闸口账本
   （Gate Ledger）；

   最后新增 G3 合并判断。

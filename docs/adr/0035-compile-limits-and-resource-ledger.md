# 0035 编译资源上限只声明容量与宿主预算，受控分配统一经资源账本

**状态**: Proposed（2026-11-16 修订；取代同日以 Accepted 合入的初版，初版见[固定提交][adr-0035-initial]）<br>
**日期**: 2026-11-16<br>
**适用范围**: `laneflow-compiler` 的 `CompileLimits` 维度集合与配置档、编译与发射阶段的
受控分配记账、外部可移植字节的准入与配置档自洽检查；不改变任何可移植制品字节、格式
版本或 `NetworkRevisionId`<br>
**设计入口**: [#1296][issue-1296]、[#1288][issue-1288]<br>
**关联决策**: [ADR 0024][adr-0024]、[ADR 0025][adr-0025]

本文决定：编译资源上限配置档只声明容量维度与宿主预算维度，二者是全部限额；编译、
发射与公开检查的受控分配一律经同一个编译器资源账本按计划授予，暂存与输出字节成为
账本报告量而非限额。账本模型见[编译器资源账本][resource-ledger]，维度与配置档见
[编译器基础 §5.3][compiler-limits]。

## 背景

### #1288 暴露的失配

`CompileLimits` 现有 `LF-COMP-P100-INITIAL-v1`、逐项继承 v1 的 `LF-COMP-P100-INITIAL-v2`
与 `LF-COMP-SINGLE-NETWORK-1M-v2` 三个具名配置档，每个维度都是手写常量。P100 v1 允许
11,265 个稳定实体，但发射期 `ArtifactIndex` 对每个身份行计入 76 B，与编译管线共用
304,896 B 的 `StageScratchBytes`：实测 4,011 个稳定实体可以发射，4,012 个失败。来源是
`a6d73e5d`（#563）把发射期索引改为计入共用暂存计量器，常量没有随之重新校准，也没有
任何检查发现这一点。

### 初版决定与实现前调研

初版（见页头固定提交）的方向是：配置档只声明容量与宿主预算，暂存、输出与可移植对象
字节作为**推导字节维度**，其上限由与记账共用的成本公式代入容量上限求出。实现前对全部
记账点的调研（2026-11-16，`051f515a`）发现，问题不止于常量与公式脱节：

1. **记账没有统一抽象。** 编译器内至少有七套各自独立的内存计量结构：HIR 的
   `DomainBudget`、源映射冻结的 `SourceMapSizing`、发射器的 `Scratch`、道路编辑的
   `PreflightScratch`、`GeometryScratchAllowance`、`GeometryScratchBudget` 与
   `GeometryCompilationBudget`；HIR 计划、MIR、LIR 与源映射冻结各自复制了一份同名的
   字节折算函数，各阶段又分别手工累加上游阶段的存续字节。三种时机并存：开工前计划
   （HIR、MIR、LIR、源映射）、边分配边记账（发射器）、逐次分配前预检（道路编辑）。
   #1288 正是一处分配换了计量器、却沿用另一阶段上限的结果。
2. **计划与分配只靠约定对应。** HIR、MIR、LIR 与源映射冻结的计划层约有 316 处按
   “元素类型 × 计数”申请字节，实际分配写在另外的文件里，按同一计数预留容量；二者的
   类型与计数是否一致只靠人工保持，个别位置用 `debug_assert_eq!` 核对长度。
3. **发射阶段不在宿主预算内。** 发射器只计暂存与最终对象字节数：LFCA/LFSM/LFSD 的
   内存对象树、编码缓冲、内存发射路径返回的对象字节都不计入
   `CompilerControlledLiveBytes`；差异路径另有按 `(EntityKind, StableId128)` 建立的有序
   映射与几何字节副本，没有计入任何维度。
4. **推导上限作为限额不成立。** 计划公式的输入是数十个内部计数（路口、流向、机动路径、
   车道组成员等），它们不是容量维度，而是共同受声明数、稳定实体数、关系出现记录数等
   约束；公式含条件分支、`min` 与跨领域耦合。逐项代入容量上限得到的值远高于任何可达
   输入，作为限额永远不会触发；求共同约束下的精确上确界需要逐阶段求解最大化问题，
   既难审计，又随每次记账变化重做。一个永不触发、却需要整套推导维护的限额只是断言。
5. **部分宿主预算维度没有执行对象。** 编译器不跨编译保留容量，
   `Compiler::retained_capacity_bytes()` 恒为零；P100 档未定义可移植对象与 bundle 维度，
   而百万档的 bundle 上限等于单对象上限的两倍，不是独立校准的宿主资源边界。

根因是：限额（宿主允许多少）与记账（编译器实际申请多少）没有分开建模，记账又分散在
各阶段各写一套。本次修订把二者分开，并把记账收敛到一处。

## 决策

### 1. 配置档只声明容量维度与宿主预算维度，二者是全部限额

每个具名配置档只声明：

- **容量维度**：编译单元允许的输入与中间记录规模，即模块数、来源文档数、导入边数、
  单模块与总来源字节、声明数、稳定实体数、Typed AST/HIR/MIR/LIR 记录数、有类型引用、
  关系出现记录、标识字段出现记录、机动门、等待区、几何点、符号、字符串项、单字符串
  字节、总字符串字节与诊断数。
- **宿主预算维度**：宿主为一次编译、一次发射或一次公开检查提供的资源，即编译器控制
  总存续字节（`CompilerControlledLiveBytes`）与一次编译后允许保留的容量字节
  （`RetainedCapacityBytes`）。

`StageScratchBytes`、`OutputBytes`、`PortableObjectBytes` 与 `PortableBundleBytes` 从
`CompileLimits` 删除，不拆分、不推导。每个配置档都包含上述全部维度，不存在“该配置档
未定义此维度”的状态。

正常输入的拒绝只来自三处：容量维度、制品容量（第 4 节）与宿主预算维度。暂存峰值、
输出逻辑字节与各阶段存续峰值由账本报告，供证据与回归比较使用，不参与拒绝。

### 2. 可移植字节边界交给格式预算与宿主预算

- 单个可移植对象的字节由调用方传入的 `FormatLimits::max_object_bytes`（调用方接收预算）
  与线格式原语硬上限约束，超出时按格式边界报告。
- 内存发射路径返回的对象字节计入发射账本的宿主存续预算。
- 暂存目录发射路径写入调用方选择的目录，磁盘字节是调用方的暂存资源，编译器不另设
  bundle 限额。
- 配置档自洽检查以单调上界核对：容量上限下可能产生的单对象字节不超出线格式可表示
  范围与原语硬上限（第 6 节）。

### 3. 受控分配统一经编译器资源账本

一次编译、一次发射或一次公开检查各持有一个**编译器资源账本**（compiler resource
ledger），对照所选配置档的宿主预算记账：

1. **计划准入**：每个编译遍在任何与计数成正比的分配前，按实际计数求出本遍计划（新增
   存续、查找与暂存字节）。账本把计划与当前存续相加，超出宿主预算即按
   `CompilerControlledLiveBytes` 拒绝，此时尚未分配。
2. **按计划授予**：编译遍的受控分配只能从已准入计划中按“元素类型 × 数量”取得授予，并
   按授予精确预留容量。授予累计超出计划属编译器记账缺陷，报告为内部错误，不作为资源
   限额诊断。计划与分配的对应由授予接口在结构上保证，不再依赖约定。
3. **释放与报告**：授予随容器释放归还账本。账本记录总存续峰值、各阶段暂存峰值与编译
   结束时保留的容量，作为报告量返回。
4. **覆盖范围**：编译管线全部编译遍、单制品发射、差异发射、发射期自校验与公开检查入口
   使用同一账本模型。发射的内存对象树、编码缓冲、实体索引、比较投影、变化行与内存
   发射对象字节全部经账本授予。

账本取代背景第 1 条列出的各内存计量结构与重复的字节折算函数，阶段内部的计划公式迁入
账本计划。按容量维度累计遍历工作量的预算（如 MIR 策略校验的 `WorkBudget`）约束的是
计算量而非内存，不属于账本。调用方在进入公开接口前持有的输入（编译单元、`CompilationOutput`、调用方
字节）不计入该次账本；复制或驻留进编译器的字节计入。

### 4. 外部可移植字节先按制品容量准入

不来自本次编译的可移植字节（差异 base，以及公开检查入口接收的 LFCA、LFSM、LFSD）另按
**制品容量**准入：只统计可从受检制品直接取得的各种类稳定实体行、关系出现记录行、
几何点与几何字节、策略成员行、字符串与向量字节，以及 LFSD 各变化表行数，在格式预检
之后、计划准入与建立索引之前完成，错误标明输入一侧与容量维度。差异 base 须满足本次
发射所选配置档的制品容量；需要更大的 base 时，调用方选择容量覆盖它的配置档。

制品容量准入保证“配置档内的输入”有确定含义；账本的计划准入保证即使输入在容量内，
多侧组合超出宿主预算时也在分配前拒绝。

### 5. 发射端目标索引只建立一次

LIR 实体规范顺序按 Identity v1 原像排序，不是 StableId 字节序，本设计不改变它。目标
LFCA 的 StableId 排列由发射上下文建立一次，经账本授予，供目标关系投影自校验与 LFSD
构建共用；差异 base 仍按原规则建立索引并检测重复。`check_portable_policy_diff` 继续从
最终字节独立建立检查视图，ADR 0024 的后发射 bundle 检查合同不变。

### 6. 配置档自洽检查

每个具名配置档必须通过：

1. **格式可表示性**：按容量上限求出的单对象字节单调上界不超出线格式可表示范围与原语
   硬上限；容量值转换为 `usize` 时在目标平台可表示。
2. **可成功规模维度**：对除诊断数外的每个容量维度构造一份在该维度取可达上限、其余
   维度取构造所需最小值的输入，正向完成编译、单制品发射与 genesis、以自身为 base、
   两侧 StableId 不相交、身份保持而内容大量修改、关系重连等正向差异场景，账本峰值
   不超出宿主预算。无法单独逼近上限的维度须说明由哪个维度连带约束。
3. **诊断保留维度**：诊断数只在失败路径验收：恰好 16 条、至少 17 条并设置截断、较小
   规范键替换已保留项，且不返回成功输出或部分发射候选。
4. **账本一致性**：常规测试中每个编译遍的授予累计不超出计划，受控容器的实际容量不超出
   授予。

负向场景单独验收：base 超出制品容量时须在建立索引前按 base 一侧与容量维度拒绝；超过
宿主预算的组合须在分配前按 `CompilerControlledLiveBytes` 拒绝。P100 配置档的上述检查在
常规 CI 中运行，不得只放在 `#[ignore]` 测试中；百万档在常规 CI 中执行格式可表示性
检查，可成功规模维度由其端到端证据入口承担。

### 7. 新配置档取代既有三档，1.0 前不并存

| 新配置档标识符              | 构造器                               | 容量与宿主预算来源                             |
| --------------------------- | ------------------------------------ | ---------------------------------------------- |
| `LF-COMP-P100`              | `CompileLimits::p100()`              | 继承 `LF-COMP-P100-INITIAL-v2` 的对应维度      |
| `LF-COMP-SINGLE-NETWORK-1M` | `CompileLimits::single_network_1m()` | 继承 `LF-COMP-SINGLE-NETWORK-1M-v2` 的对应维度 |

按 [1.0 前开发原则][pre-1-0]，标识符与构造器不带世代后缀；被取代的三个配置档及其构造器
随实现删除，不保留别名，现有调用方一并迁移。配置档标识符只出现在编译诊断与生成器、
测量入口的工作负载清单文本中，不进入 LFCA、LFSM、LFSD 或 `NetworkRevisionId`；退役旧
配置档不改变任何制品字节。

## 后果

- #1288 类失配从结构上消除：分配必须持有授予，授予来自经宿主预算准入的计划，不存在
  “换了计量器却沿用另一阶段上限”的路径。
- P100 档声明的 11,265 个稳定实体在宿主预算内可以发射与差异发射；#1288 的 G2 Routing
  证据入口改用 `LF-COMP-P100` 后恢复可运行，§7.1 是否重新取证由维护者裁定。
- 发射阶段首次纳入宿主预算。若某个既有官方 fixture（固定测试环境）的发射峰值超出宿主
  预算，自洽检查在 CI 中失败，须显式调整宿主预算并说明依据。
- 编译诊断不再出现 `max_stage_scratch_bytes`、`max_output_bytes`、
  `max_portable_object_bytes` 与 `max_portable_bundle_bytes`；对应量出现在账本报告中。
- 授予超出计划由资源限额诊断改为编译器内部缺陷，调用方不能通过调整配置档绕过。
- 以更大的既有制品为差异 base 时，调用方须选择容量覆盖该 base 的配置档；公开检查入口
  对调用方字节先做制品容量准入，再建立索引。

## 被拒绝的替代方案

### 推导字节维度作为限额（初版）

见背景第 4 条：逐项代入容量上限的值永不触发，精确上确界需逐阶段求解共同约束下的
最大化问题；两者都让限额退化为需要整套维护的断言。初版要解决的“常量与记账脱节”由
账本的计划准入与按计划授予解决。

### 保留各阶段暂存常量作为第二道限额

暂存常量与宿主预算重复约束同一份内存，且任何记账口径补全都会再次要求校准，正是
#1288 的成因。

### 有界计数类型追踪每个内部计数受哪个容量约束

只有推导上限需要它。去掉推导限额后，内部计数受容量约束由准入保证，宿主预算由账本
按实际计数核对，类型层追踪不再有消费者。

### 以全局分配器计数代替账本

全局分配器只能观测进程级总量，不能区分编译器受控分配与宿主分配，也不能在分配前
拒绝；计数分配器与计时测量不能同进程运行的规则也使其不适合作为生产路径。分配器
层证据继续由 `stats_alloc`、`dhat` 在测量入口承担。

### 把 bundle 字节保留为宿主预算维度

磁盘暂存字节属于调用方选择的暂存目录，编译器既不拥有也无法观测其余量；现有数值没有
独立校准来源。内存发射路径的对象字节已由账本计入宿主存续预算。

### 原地调大 v1 的暂存常量，或新档只把暂存常量调大

`limits.rs` 规定配置档语义不可原地改变；新档的手写常量仍与记账无关，同类失配会再出现。

### 把发射期 StableId 排列持久化进 LFCA

运行时借用违反 ADR 0025 构建完成后不借用 LFCA 的决定；运行时复制需要提升 LFCA 版本，
只省去运行时身份索引排序与差异 base 的索引构建，仅在[共享静态路网身份索引][shared-identity]
改造实测后仍证明排序成本构成阻断时另行立项。

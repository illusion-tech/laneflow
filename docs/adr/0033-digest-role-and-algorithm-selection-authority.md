# 0033 摘要角色与摘要算法选型权威

本文规定新增或复核摘要时“先确定角色，再选算法”的规则，并给出每类角色的默认算法。
本文拥有角色与选型规则，具体字节合同由各自设计拥有。确定性派生摘要
（deterministic derivation digest）不承担身份或完整性证明；其持久结果仍须可重建、
可区分版本。LuST 的对应字节合同见[真实路网工作负载 §4 与 §6.2](../design/real-road-workloads.md)。
其他既有摘要不因新增角色自动迁移，改变字节合同须各自进入 G1。

## 背景

SHA-256 的优势是互操作：任何语言、任何通用工具都能独立重算并比对。LaneFlow 主树
约有十二个 crate 直接依赖 `sha2`，新增摘要时通常直接沿用 SHA-256，选型理由没有记录。
其中相当一部分摘要只由 LaneFlow 自己产生、自己验证，没有外部重算方，例如确定性
状态摘要和编译器来源追溯摘要。对这类摘要，SHA-256 的互操作价值用不上，代价却一直
存在。算法差异取决于输入长度、硬件指令与实现，长缓冲区吞吐不能代替短前像测量；
[LuST 实测](../../research/issue-1029-lust-digest/xxh3-review.md)中，带 SHA 指令的
SHA-256 比 BLAKE3 更快，XXH3 又比二者更快。

仓库已有按角色选算法的先例。[网络编译器 §7.6](../design/network-compiler.md) 规定
BLAKE3-128 只用于持久实体标识，XXH3 只用于编译器进程内缓存，SHA-256 负责制品、镜像
与发布完整性，三者不得混用；ADR 0020 规定稳态 tick 不进入任何哈希计算。但这套分层
只约束编译器，运行时、取证工具与测试证据并不受其约束。

1.0 发布前，摘要算法仍可按 `laneflow-pre-1-0` 原则直接改写；1.0 后任何更换都是破坏性
格式变更。因此需要在发布前确立全局选型权威。

## 决策

### 1. 摘要按角色划分，一个摘要只承担一个角色

| 角色           | 英文辅助                        | 定义                                                                         | 验证方             |
| -------------- | ------------------------------- | ---------------------------------------------------------------------------- | ------------------ |
| 瞬态指纹       | transient fingerprint           | 进程内哈希表、缓存与候选匹配使用的短值；命中后必须比较完整权威值             | 同一进程           |
| 确定性派生摘要 | deterministic derivation digest | 将规范前像映射为可重建的排序键、采样值或派生参数；不作唯一身份或内容相等证明 | 派生结果的重建方   |
| 持久标识摘要   | persistent identity digest      | 从规范前像派生、作为实体或对象稳定标识持久保存的值                           | LaneFlow 实现      |
| 内部完整性摘要 | internal integrity digest       | 认证字节或规范值未被改变，只由 LaneFlow 实现产生和重算                       | LaneFlow 实现      |
| 互操作摘要     | interoperable digest            | 认证字节或规范值，且须允许 LaneFlow 之外的实现、通用工具或人工流程独立重算   | 任意实现或通用工具 |

角色由**用途承担的证明责任**、**验证或重建方**和**持久化范围**共同决定，不由
数据大小或调用频率决定。先判断是否将摘要作为身份或内容相等证明；仅将值用于排序、
采样或参数映射的，按确定性派生摘要处理。摘要本身不持久、但决定持久产物内容时，
仍须冻结算法和字节规则，并对结果变化提升版本；不能仅因持久结果存在，就将派生
用途归为内部完整性摘要。

同一个摘要值不得跨角色复用，不得因为“已经算过”就拿来兼作其他角色；唯一例外是设计
文档说明两个用途的证明责任、前像与验证方完全一致。瞬态指纹不得写入制品、存档、公开 API 或
证据文件，也不得影响任何确定性输出，包括通过哈希表迭代顺序间接影响。

### 2. 每类角色的默认算法

| 角色           | 默认算法                                             | 说明                                                                                    |
| -------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 瞬态指纹       | XXH3-64／XXH3-128，或标准库默认哈希                  | 非密码学；不得持久化。引入 XXH3 依赖须另走依赖安全审查                                  |
| 确定性派生摘要 | XXH3-64                                              | 须满足下述输入信任、碰撞与分布条件；固定 seed、secret、编码及版本，不使用标准库随机哈希 |
| 持久标识摘要   | BLAKE3，按需截断（现行 `StableId128` 为 BLAKE3-128） | 现行实体标识算法不因本文改变                                                            |
| 内部完整性摘要 | BLAKE3-256                                           | 密码学；用于失真检测、审计比对、确定性状态摘要等                                        |
| 互操作摘要     | SHA-256                                              | 只在确有外部重算方时使用                                                                |

**SHA-256 不再是默认选项。** 在互操作摘要以外的角色中使用 SHA-256，必须在 Issue 或
设计文档中写明理由，例如与某个互操作摘要属于同一格式家族、或外部重算方尚在规划中。
选择互操作摘要角色时，必须写明外部重算方是谁；“将来可能有人需要验证”不构成理由。

**非密码学哈希仅允许用于瞬态指纹和符合条件的确定性派生摘要。** 不得将其用作
持久标识、内部完整性或互操作摘要；也不得在不可信方能借碰撞换取错误结论时使用。
确定性派生必须逐项满足：

1. 写明输入信任边界；来源完整性由独立机制验证，不能由派生值倒推来源可信。
2. 写明碰撞后果并确定处理方式。排序须以完整权威值形成总顺序，主键相同不等于
   对象相同；比例映射可以重复，但不得因此宣称唯一身份。
3. 明确所需分布与允许的偏差，不把确定性、粗分箱结果或固定样本无碰撞当作均匀性、
   独立性、不可预测性或对抗安全证明。
4. 若输入可由参与者挑选，须明确是否容许其影响派生结果。涉及抗操纵抽样、公平
   抽签或保密时另做安全设计；公开固定 SHA 同样不能自动阻止反复尝试输入操纵排名。
5. 满足 §4 的精确重建要求，且不放宽 §6 的稳态 tick 禁令。

### 3. 新增摘要的立项要求

新增摘要时，Issue 或设计文档必须写明：

1. 角色；
2. 验证或重建方（同一进程、LaneFlow 实现，或具体的外部重算方）；
3. 持久化范围（不持久、存档、制品、公开 API、证据文件）；
4. 偏离默认算法时的理由。

确定性派生摘要还须写明输入信任边界、碰撞处理、分布要求与允许的操纵范围；
“只需要确定性”不足以代替这些条件。

没有写明角色的摘要不得进入主树。

### 4. 持久结果的域分隔、版本与更换

- 确定性派生摘要、持久标识摘要、内部完整性摘要与互操作摘要都必须带域分隔前缀和派生版本，使不同
  用途、不同版本的前像不会产生相同输入。
- 确定性派生须冻结算法变体、seed 与 secret 选择、字段编码/边界、比较顺序、端序、
  位提取及数值映射；不得使用 Rust `Hash` trait 的非规范序列化、进程随机 seed 或
  机器原生内存布局形成持久合同。至少提供可由独立实现核对的固定测试向量。
- 更换算法即更换派生版本。1.0 前更换时直接改写当前合同，只保留一套算法，不保留
  旧算法的读取或并行计算路径（`laneflow-pre-1-0`）。
- 新增的公开类型与字段按角色命名，不在名称中写入算法。现有以算法命名的类型与字段
  （例如 `Sha256Digest`、字段类型代码 `Sha256`）在对应摘要复核时一并处理，不单独
  发起改名。

### 5. 以性能为由更换算法须先测量

以性能为理由更换现有摘要的算法时，必须测量单项与所在调用的成本，再比较候选算法；
测量须在同一工具链、同一机器上对比，并按现有基线口径保存证据。无法准确归因时
如实报告波动，不把两个独立计时的比值当作精确阶段占比。

迁移判断须分别说明角色匹配、每次调用的持续收益、调用频率、依赖维护与一次性基线
重建成本。非瓶颈上的收益可能很小，不得把局部加速宣称为整体加速；占比小或需要
一次性重建都不是自动否决理由。本条不允许为性能削弱所选角色的安全要求。

### 6. 热路径禁止哈希保持不变

ADR 0020 规定稳态 tick 不进入 `StableId128`、BLAKE3、XXH3、哈希查找与字符串处理；
本文不放宽该规则。瞬态指纹同样不得进入稳态 tick。

### 7. 摘要算法依赖由 `cargo-deny` 约束

`sha2`、`blake3` 以及今后引入的摘要算法 crate，只允许登记的 crate 直接依赖。登记名单
以 `deny.toml` 的 `[bans]`（`wrappers`）为唯一事实源，由现有 `Dependency policy` 检查
执行，不新增合并门禁，也不解析 Issue 或 PR 正文。新增直接依赖方时，须在同一变更中
更新 `deny.toml`，并按 §3 写明新增摘要的角色。本文不重复列出名单。

### 8. 单一事实源

本文是摘要角色与算法选型的唯一权威。[网络编译器 §7.6](../design/network-compiler.md)
的算法角色条款改为引用本文；具体摘要的前像、字节布局与派生版本仍由各自设计文档
定义。角色术语的中英映射由 `docs/reference/glossary.md` 管理。

### 9. 已确定的归类

以下归类在本文接受时即为结论，用于说明规则的适用方式；其余现有摘要按设计入口
Issue 的盘点逐项复核。

- **实体稳定标识**：`StableId128` 属于持久标识摘要，算法 BLAKE3-128 保持不变。
- **可移植规范制品家族**：LFCA、LFSM、LFSD、LFCP 的对象精确字节摘要属于互操作摘要，
  外部重算方是宿主资产管线与通用工具对制品文件的校验，算法 SHA-256 保持不变。
  同一格式家族中的 `NetworkRevisionId`、修订—制品绑定与分块摘要，严格说只能由懂得
  LaneFlow 格式的实现重算，但与对象摘要同属一个格式家族，同样保持 SHA-256（理由见
  “取舍”）。
- **编译器进程内缓存**：编译器内部哈希表与候选匹配属于瞬态指纹。
- **LuST 人口排序与位置比例**：属于确定性派生摘要，采用 XXH3-64；原 ID 字节处理
  排序平局，比例值不承担唯一身份。固定来源及制品字节的 SHA-256 校验保持独立。

## 取舍

- **内部完整性摘要为什么选 BLAKE3-256 而不选 XXH3-128**：

| 维度                       | BLAKE3-256                             | XXH3-128                       |
| -------------------------- | -------------------------------------- | ------------------------------ |
| 对刻意构造的碰撞           | 抵抗，约 128 位安全强度                | 不抵抗，碰撞可被刻意构造       |
| 对随机失真的漏检概率       | 约 2⁻²⁵⁶                               | 约 2⁻¹²⁸，实际同样可以忽略     |
| 大块数据单线程吞吐（量级） | 每秒数 GB                              | 每秒数十 GB                    |
| 依赖                       | 已在依赖树中                           | 需新增依赖并通过依赖安全审查   |
| 对 ADR 0032 完整性声明     | 现有按密码学摘要假设的定性声明基本不变 | 须改为只针对随机错误的概率声明 |

  只防随机失真时，XXH3-128 的检测能力足够，速度更快。但内部完整性摘要大多会被持久
  保存或交换（检查点、存档、提交给他人复现的证据），保存后的使用场景超出产生时的
  威胁模型；一旦输入可能被他人控制，非密码学哈希给出的“相等”不再有证明力。
  因此保持 BLAKE3-256 的角色默认值。确定性派生不作这种相等证明，不能反过来用
  本条要求所有持久结果都必须密码学化；性能差异仍须按具体前像测量。
- **可移植规范制品家族为什么整体保持 SHA-256**：对象精确字节摘要有真实的外部重算方，
  应当保持 SHA-256。`NetworkRevisionId` 等语义摘要虽然实际只由 LaneFlow 格式实现重算，
  但制品体量为 MB 级，SHA-256 的耗时在毫秒级，更换几乎没有收益；在同一格式家族中
  混用两种算法，会增加格式实现与跨语言重建的负担。一个格式家族使用一种算法更简单。
- **为什么不统一改用 BLAKE3**：可移植规范制品的设计目标之一是跨语言可人工重建精确
  字节（见[可移植规范制品](../design/portable-canonical-artifact.md)）。宿主资产管线、
  第三方工具与人工复核流程普遍内置 SHA-256，BLAKE3 在部分语言生态中需要额外依赖。
- **为什么增加确定性派生摘要**：以哈希排序再取前 N 项、或将哈希位映射为有界比例，
  并不从哈希相等推出对象/内容相等。持久化要求结果可重建与变更可识别，不自动要求
  抗碰撞证明。单独列为角色能直接写明这一用途，同时保留其输入、碰撞及分布约束。
- **为什么不按数据大小划分角色**：用途的证明责任决定可用算法，前像大小与后端
  决定性能；二者须分别论证。相同重建方也可能同时消费完整性摘要和派生值。
- **为什么本文不直接迁移现有摘要**：现有 SHA-256 摘要多数已写入字节合同，迁移涉及
  格式版本、证据基线和派生版本，各自有独立的验证成本。逐项复核可以按收益排序，
  也避免一次性的大范围格式变更。

## 未采用的方向

- **保持 SHA-256 为全局默认，仅在热点处例外**：例外缺少统一标准，会重复出现“先用
  SHA-256、再逐个论证更换”的情况，且无法阻止新增摘要沿用惯性选择。
- **内部完整性摘要默认使用 XXH3-128**：见“取舍”；持久化后的证明力不足以支撑现有
  完整性声明。
- **允许调用方注入摘要算法**：ADR 0024 §7 已拒绝调用方哈希回调或可替换算法 trait。
  可替换算法会让同一合同存在多套字节结果，与单一权威冲突。
- **在摘要中携带算法标识并允许多算法并存**：1.0 前只保留一套权威；域分隔前缀与派生
  版本已足以区分算法更换，不需要在每个摘要值中重复记录算法。

## 验收与实施边界

本修订的设计验收包括术语、角色边界、LuST 精确派生合同与固定测试向量。算法依赖
仍由 §7 的根名单管理；具体生产消费者切换与证据重建按设计派生实现切片，不以设计
合入冒充实现完成。复核其他摘要若改变字节合同，须在对应设计文档中更新派生版本，
并按 G1 处理。

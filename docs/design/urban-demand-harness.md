## 1. 交付边界

#304 已冻结七套 case、两档规模、初态比例和有限验收矩阵。本文细化 #544 的实现输入，
不重新裁决产品定位、车型分类或性能达标条件。#542 的正式 LFCA 与路线目录是共同输入；
七套 case 改变调用方计划，使用同一档路网和正式 `PolicyPin`。

实现放在非发布的 `tools/laneflow-urban-harness`：复用 `laneflow-urban-generator`
的配置与目录类型，只有一个运行库，由命令行和后续 #545 驱动调用。运行库拥有稳定编号、
需求队列、命令排序和观测结果；`TrafficWorld` 拥有全部道路行为与提交状态。
不增加 Runtime、SharedNetwork、Adapter 公共接口、工作负载特判、通用插件框架或新 wire。
计划和结果是版本化验证文件，不作 1.0 后的兼容承诺。

交付分三项分别验收，任何一项不能替代另一项：

| 交付项   | 完成条件                                                                     |
| -------- | ---------------------------------------------------------------------------- |
| 计划冻结 | 七套版本化规则与两档展开计划可复核；具体命令、目标与必要触发在正式运行前提交 |
| 正确性   | 七个 case × 两档规模，每行两个独立运行，全部必需行为通过且重复结果一致       |
| 性能测量 | `MIXED-PEAK` 两档各三个独立进程轮次，记录正式窗口、分位值与实际规模          |

G1 接受不关闭 #544。小型试跑只用于检验计划可实施性；#544 关闭需要上述三项。
正式 correctness 计划只允许 10k/100k 制品；fixture 只允许 probe，CLI 与运行库共用
该准入规则。制品载入复用生成器 `Scale` 的固定 tile 数、个体数与步长定义，校验
标签和实际 manifest 数量一致。
#545 拥有 Adapter、保存/恢复和固定增容切换证据；#539/#305 拥有产品预算认证。

## 2. 共同输入与稳定身份

计划版本使用 `urban-demand-v3`，固定 `seed=544`、`world_id=544`。worker 数是
执行配置/测量来源记录（run 级 `--workers` 参数，记入运行 provenance 与
diagnostics），不属于 urban-demand-v3 交通需求协议本身：计划摘要、需求语义、
世界逻辑摘要与快照内容不随 worker 数变化（#707 测量入口切片修订；执行配置
独立于 `ResolvedPlan` 的交通需求语义）。
完整展开计划携带实际 `route_edges`；包括角色使用的局部目录路线，不只依赖路线名称。
seed 属于调用方；不改 LFCA 或 TrafficWorld 的规则。所有选择使用目录 key 的 UTF-8
字节序，禁止依赖哈希表迭代、墙钟或平台随机数。实体绑定使用目录 StableId，安装后
通过共享根得到 typed ordinal；虚拟入口/出口使用目录中的实际 anchor selector。

每 tile 固定 1000 个初始个体，编号为 `(tile, slot, incarnation)`，初始 incarnation
为 0；按此元组升序提交初态。后续请求另有递增的序号，成功原子替换 Completed 个体时
该槽位的 incarnation 加一，并保存新旧编号与句柄的对应关系。显式 spawn 同样递增；
请求编号不承担个体代次。离场、入场不改变个体编号；
句柄及分配槽位不是跨运行的稳定身份。#545 直接复用这个编号与映射。

每组十个 slot 的 profile 顺序固定为 `compact` 三个、`car` 六个、`van` 一个，
即 30:60:10；只有共同的 `road-vehicle` class。三种长度分别为 4000、4500、6000 mm，
外观不参与 profile、class 或需求数量。case 角色从这些 slot 选择，不另外改变车型总量。

初态与请求展开产生 `resolved-plan.toml`，至少含：来源/config/catalog 摘要、case/scale、
身份与 profile、实际边序列及 route occurrence、初始位置和停车目标、每条请求的 due tick、
目标、角色、序号、重试预算和预期观测种类。目录中出现的同一条边在不同路线上的 occurrence
分别保留，不按 LaneEdge 去重。路线按 key 升序注册，容量由实际路线长度和冲突出现项计算。

展开只用配置和已编译目录，不运行交通求解器挑选“会成功”的输入。展开文件在正式取证前
落盘并固定摘要；小试发现输入错误时修改计划版本及原因，废弃旧版本作为当前证明的资格。
禁止拿一次正式运行的结果回填 expected 或缩小必要触发数。

## 3. 初态分配

普通六个 case 每 tile 为 750 Active、250 Parked；`GARAGE-EGRESS` 为 250 Active、
750 Parked。两档分别使用 10/100 个 tile；Completed 和待提交请求初始均为 0。

Active 只从目录中长度 95000 mm 的外部进口 / 出口车道生成。每条车道最多 11 个
候选车头位置：`7000 + 8500 * j` mm，`j=0..10`，初速为 0。全车身留在道路臂上；
即使相邻都是最长 profile，也留有 2500 mm 净距。每 tile 188 条这样的车道，共 2068 个候选位置。
先为 case 角色分配有限位置，再按 `(slot 层, edge key)` 补齐背景；角色和背景共享同一
位置占用表，不能重复放置或通过跳过生成凑人数。

初态路线选择包含该臂的目录路线，优先 `cross-tile`、其次 `cross-cell`、最后
`junction`，同级取 key 最小者；记录实际 cursor 和剩余路段。不能把已经位于末段的
车辆统计为完成跨块行程。所有候选最终都经 `spawn_vehicle`；任一拒绝使初态校验失败，
不能把缺少的 Active 转成 Parked 或待提交请求。

Parked 分配固定到逐 tile 的合法目标，表中数字是实际 Occupied 数：

| 初态                            |                    显式泊位 | 十个 mixed 虚拟池                 | virtual-only 车库 | 合计 |
| ------------------------------- | --------------------------: | --------------------------------- | ----------------: | ---: |
| 普通六 case                     | 每 cell 的 bay0 各 1，共 10 | 每池 12，共 120                   |               120 |  250 |
| `GARAGE-EGRESS`                 |                 同上，共 10 | 每池 24，共 240                   |               500 |  750 |
| `GARAGE-INGRESS` 覆盖上述普通行 |                 同上，共 10 | c09 为 100；其余九池各 12，共 208 |                32 |  250 |

bay1 保留给实际到达；Ingress 的 c09 mixed 虚拟池从初态就真实满位。车库每 tile 有
1000 个虚拟位置，mixed 每池 100 个；不同设施和显式/虚拟池的空位不能互相借用。
所有 Parked 通过 `spawn_parked_vehicle` 建立 Occupied binding；retained cursor
使用该目标目录首个 departure anchor，它不表示道路 arrival。

初始化后读取每个个体状态和 binding，以及每个 facility 的分池计数，核对上述精确分配。
两档 Egress 必须实际得到 7500/75000 个 Parked binding。容量总数、预留内存和未提交
需求均不能代替这些绑定。

## 4. 有限需求与七套 case

### 4.1 背景需求和命令顺序

背景车完成短跨块行程后，由调用方提交下一次出发请求，使用 `replace_completed_vehicle`。
每组十个初始 Active slot 为一个出发组，周期为 64 个 528 ms 量子；组的偏移为
`(group_index + seed) mod 64` 个量子。同组请求同 tick 到期，编号升序处理。
只展开本次运行终点之前的有限周期，不运行无限需求循环。

`MIXED-PEAK` 每组十条计划出发使用七条向东、三条向西路线，依次取本 tile 目录的
`.cross.e.lN` / `.cross.w.lN` 路线并按 key 循环。起点使用首边 7000 mm、初速 0；终点为
目录路线的末端。其他 case 保持相同的分组、周期、profile 和方向比例。三类
Waiting/Conflict 行及 Burst 的背景路线从同一有序目录中排除“剩余后缀会穿过角色
cell”的候选，避免有限角色脉冲被持续背景流替代；这只是调用方输入选择，不改变
Runtime 规则。其余跨 tile 流量仍由真实跨 tile 路线提供，不创建独立世界，也不因
tile 边界切断 Runtime 更新。

Mixed 另在第一个观察周期提交每 tile 20 条车库离场请求，同样按七东三西的十条组编排。
入场从既有 Active 个体选择并预留前向可达目标；不额外生成车辆。70:30 的分母是观察
窗口内到期的计划出发请求，重试不重复计入；真实准入数及其方向比单独报告。

Mixed 的到达角色在初态中预先占用目标入口臂上的合法候选位置，前向有限空间不再
分配背景个体，其余 Active 按共同候选表补齐。首个提交边界 reserve；实际到达可以
发生在暖机期，但保持 Active/Reserved 等待预先冻结的观察期 park 边界。park 仍要求
真实 arrival，且最早在 arrival 后的下一个提交边界；只有观察期实际 park/leave 计作
该行停车转换。暖机 reserve/arrival 不计为观察期入场链证据。

普通可重试请求最多尝试 8 次，间隔 4 个量子；超出窗口不追加尝试。未 Completed、
无可安全准入的位置、离场受阻均保留原个体和请求。用尽预算的请求保留为 exhausted
积压记录，不继续调度、不改 due tick、不清账冒充成功。后续到期请求也不能覆盖旧记录。

每个提交边界依次处理：到期的 park/cancel、离场、Completed 原子替换、reserve，
最后调用一次 `step`。同类按 `(due_tick, tile, stable_id, request_sequence, attempt)`
排序。Step 返回的 arrivals 和领域事件在本边界记录，派生的 park 最早在下个边界提交。
`BOUNDARY-BURST` 的显式 despawn/spawn 作为独立命令组放在原子替换位置，不将两条命令
包装成 Runtime 原子事务。背景替换请求若命中角色拥有的 slot，由 caller 在读取 live
handle 前记录为 `role-held` 并按共同有限预算重试；因此相邻 despawn/spawn 边界之间的
暂时 absent 不会向 Runtime 下发命令，也不改变角色所有权。每次命令都保留结果、提交
游标和映射变化。

### 4.2 场景角色与必要观测

每 tile 使用现有对应模板安排下表角色。展开计划必须给出精确个体、路线、锚点和 due tick；
角色不是 Runtime 标签。信号相位的候选边界由已编译目录的 phase duration、cycle、offset
计算，时间位置为 `(time_ms + offset_ms) mod cycle_ms`；实际通过与拒绝仍由 Runtime 判定。
脉冲和释放安排在观察窗口内，不能只在暖机发生一次便记为观察通过。

| Case                 | 固定角色和输入                                                                                     | 每 tile 必须出现的有限观测                                                                          |
| -------------------- | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `MIXED-PEAK`         | 背景跨块行程、20 条车库离场，以及 bay1 和未满虚拟池各一个到达角色                                  | 至少一个真实跨 tile 完成行程、受信号约束的等待及随后通行、一次停车转换；统计方向、准入、完成和积压  |
| `GARAGE-EGRESS`      | 车库 20 个已停个体，交替使用两个已编译出口；其中一个出口安排有限占用脉冲                           | 两个出口各至少一次成功离场；至少一次安全拒绝及同一请求的成功重试，身份与原绑定在拒绝后保留          |
| `GARAGE-INGRESS`     | bay1 到达、未满 mixed 虚拟池到达、向 bay0 和已满 c09 池的预留请求                                  | 显式和虚拟各一次实际 reserve→arrival→park，以及各一次真实满位/排他拒绝                              |
| `WAITING-RELEASE`    | c00 的同一待转方向三个 FIFO 个体，配合按信号周期重放、最后保留完整释放相位清空的有限下游占用脉冲   | entry、容量拒绝、下游 storage 拒绝、后继相位 release 各至少一次；入队者按权威队列顺序释放           |
| `PERMISSIVE-LEFT`    | c01 左转角色和同绿对向直行脉冲，脉冲结束后保留可用间隙                                             | 与对向流相关的 no-grant 和后续 grant/通过各至少一次                                                 |
| `UNCONTROLLED-YIELD` | c04 主路脉冲、支路转入角色及相邻车库出口请求，主路脉冲有限终止                                     | 主路通过、支路因真实让行关系等待、空窗后的支路通过、车库成功离场各至少一次                          |
| `BOUNDARY-BURST`     | 在已选相位边界的前/后相邻提交边界编排 leave、reserve、park、Completed replace 和显式 despawn/spawn | 实际相位变化、至少一次 lifecycle 成功、一次安全拒绝及有限重试成功；分别记录两个边界，不用平均值代替 |

每个城市行按 tile 给出 required/observed 表，只有对应实例的实际观测可以满足该行；
不能由另一个 tile 的成功或 owner 小型测试补足。角色准入失败、脉冲未清空、窗口结束时
必要事件缺失都判失败，不延长窗口直到碰巧通过。背景个体仍逐 tick 执行同精度道路求解。

Waiting 占用脉冲在释放相位开始前一个提交边界准入，只有该完整释放相位能在观察终点
之前结束时才安排该次重放，不能提前裁掉整个末周期而漏掉迟入队者的 storage 拒绝。
保留相位只是固定输入安排，实际脉冲和资源清空仍须通过下述终态校验，不由时间余量推定。

角色准入逐条核对成功 replace 的请求序号、提交边界和新 incarnation；未来请求计数同时
覆盖背景、车库离场和角色再出发，不将尚未到期的角色遗漏。Waiting/允许左转/无控制
让行的有限交通脉冲在固定窗口末必须实际 Completed，且无 Waiting、机动遍历、
Conflict reservation 或残留 claim。车库出口占用脉冲按具体阻塞者、离场主体及请求序号
关联实际安全拒绝与随后成功重试，证明出口阻塞已解除；阻塞者可以继续行驶，不强制
它在有限窗口内完成解除出口占用之后的道路行程。

`GARAGE-INGRESS` 的成功入场角色先以未预留初态走完暖机行程，在观察期起点重新
准入并 reserve；背景后续路线避开这些受测入口臂，保留初始活动车辆总数。按同一
incarnation 关联观察窗口内实际 reserve、step arrival 和 park，不能用暖机 arrival
补足。显式排他与虚拟满池分别保留一次完整拒绝前后快照等价见证；角色尚未 Active
时的 `InvalidVehicleStatus` 不消耗这两类见证的候选预算，也不算所需拒绝已验证。

两种让行行从主体的实际 `ConflictOccupied` 决定出发，将所涉 passage 的 Policy
让行目标与同 tile 指定主路/对向脉冲持有的真实 claim 对齐，记录主体与脉冲的稳定
身份、冲突区和机动出现项。随后必须观测该脉冲清空、同一主体/机动获准及通过，
形成有序见证。其他 no-grant 原因仅作诊断，不能替代真实让行关系。这里验证固定
城市输入，不重实现 Runtime 的间隙求值器。

`BOUNDARY-BURST` 按具体命令核对实际提交边界：显式角色在前边界 park，虚拟角色在
前边界准入到已编译停车入口前 1 mm，初速度 1000 mm/s 并 reserve，经真实下一 step
arrival 后在后边界 park；该初速度与位置显式写入角色请求，不依赖零速起步瞬移。
指定 Completed replace 在前边界成功，两个相邻边界内至少一次 leave 成功，指定
despawn/spawn 各在其固定边界提交。其他生命周期成功或调用方延期均不能代替。
Yield 的背景后续路线避开受测车库出口臂，保留初始活动车辆总数和共同观察窗口。

Mixed 的“一次停车转换”是至少一次成功 park 或 leave，三种计数仍分别报告；不额外
要求该行同时成功离场、显式入场和虚拟入场。观察期内完整 reserve→arrival→park 与
两类拒绝由 `GARAGE-INGRESS` 对应行证明，不能用 Mixed 的分阶段角色代替。

待转区只在槽位 0 的干路左转共用段上，名义容量为 2。城市行固定三个候选并记录其
admission 顺序；在有限两周期窗口内，实际 release 序列必须是 admission 序列的有序
前缀，且至少有一次 release。两辆 4.0 m 或 4.5 m 车可以同时在区内，第三辆被拒绝。
不声称验证区内的完整排列；完整多成员 FIFO 精确断言复用 owner 测试。本体不为增加
这类组合而改写共同 LFCA。许可左转放在支路圆灯上。

安装必须读取 `urban-conservative-v1` 的实际 policy pin 和派生间隙：16 ms 的 lead/lag
为 5516/2500 ms，33 ms 为 5533/2500 ms。不能使用 #543 的空让行关系策略。
等值间隙不放行等精确边界复用领域 owner 小型测试；城市行证明真实让行和放行，不另行
制造任意几何/时刻/车型的笛卡尔积。

### 4.3 持续负载与验收边界

`SUSTAINED-ACTIVE` 是独立的持续负载场景，支持 probe 和 performance，不属于七套
正确性行。正式性能采用 §6 的完整窗口长度，与 Mixed 分别生成计划和记录结果。
每 tile 初始 1000 Active，停车、正确性角色及有限出发计划均为空。
场景身份只用于选择受控的场景配方（`ScenarioRecipe`）：初始活动人口、需求策略
（`DemandStrategy`）和正确性角色集合（`CorrectnessRoles`）分别声明。生成器按各部分
展开，不将一个 case 改写为另一个 case 来复用行为；路线候选和背景布车规则可共用。
新增场景必须显式选择这些组成及对应验证，新的行为再增加独立策略，不能靠隐含角色继承。

持续需求在计划中写入 `RecyclingPlan`，包含每 tile 的入口车道及其路线分组、候选位置、
每边界尝试上限和重试间隔；`candidate_order = "rotate-entry-and-position"` 随计划冻结，
未知顺序拒绝安装。只使用本 tile 的 95000 mm 外部入口车道，候选路线来自
跨 tile、跨 cell 和路口类别；入口和组内路线均按 key 排序。候选位置从 7000 mm 起，
每隔 8500 mm 共 11 处，初速为零，所有候选仍由 Runtime 的公共替换操作检查准入。
不展开周期出发组，也不使用有限总尝试预算。控制器在每个提交边界为实际 Completed
个体创建回收请求，同槽位至多一个。令 `base = slot + incarnation * 37`、
`offset = base + attempt - 1`、入口数为 `E`、位置数为 `P`，入口索引为
`offset mod E`，位置索引为 `(floor(base / E) + attempt - 1) mod P`，组内路线索引为
`(base + floor(offset / (E * P))) mod 组内路线数`。每次同时轮换入口和位置，避免边界
预算小于入口数时始终探测一个拥挤位置；入口选择不受组内路线数偏置。
每请求每边界最多尝试 64 个候选，均被拒绝后每 8 tick 继续，直到成功或窗口结束，
覆盖 16/33 ms 两种步长，不依赖 528 ms 量子转换。每次成功或拒绝保留实际路线和位置。
成功回收才释放该槽位的请求所有权；窗口末仍受阻的请求保留 pending。命令样本仅计
公共 Runtime 调用（含拒绝），候选计算、拒绝诊断与记账在该计时范围外；完整成本由
整轮墙钟承载，并与 step 样本及观测阶段样本分别报告。

全部请求在调度前登记，重试保留身份。唯一请求账本（`RequestLedger`）管理
Scheduled→Pending→Succeeded/Exhausted 状态，只有 Pending 可以重试或结束；结束的请求
移出账本、只计入计数，编号不再登记，账本大小只随在途请求而不随运行时长增长；普通有限
请求保留八次预算，回收请求按窗口终点停止调度。计数随状态转换更新，不从两个集合的
长度相减。有限计划保留已接受的请求标签，并在展开和安装前检查全部命令及派生停车
命令的编号唯一性、十个槽位的出发组及算术溢出；新回收请求由账本集中分配编号。
个体 incarnation 只按该槽位的实际成功生命周期递增，拒绝和重试不产生新个体。

计划结构校验拒绝向持续回收混入停车初态、有限需求、正确性角色及见证要求；重新展开
校验还核对策略、路线候选、初态和来源摘要。七套正式计划的展开保持其原有输入语义。
回归验证覆盖角色泄漏、重复编号、请求状态转换、同槽位重复回收、超过 64 次的入口受阻
重试及成功后释放、跨 worker 对拍和观察窗口负载统计。

观察窗口分别统计命令后 step 前的实际 Active（`N_intent`）及 step 后的实际 Active，
在 `result.json.active_load` 报告目标、样本数、min/p50/p95/p99/max 及低于目标的拍数。
完成行程和准入受阻仍可能降低 Active，窗口完成不证明持续负载达标。性能结论必须绑定
实际负载分布；策略修复前的测量不能作为修复后持续负载的认证，需按新计划重新测量。

正式持续负载要求观察窗口每拍 step 前的实际 Active 等于计划目标：一万或十万。
暖机不进入该门槛；step 后因本拍行程完成而下降的数量、分位和拍数继续分列，不能
声称所有边界时刻均保持目标。正式窗口末尾的 Pending 与耗尽请求均须为零；本拍刚
Completed、尚未在下一边界登记回收的个体不等同 Pending 请求。个体数量或出生/移除/
替换守恒不符也拒绝通过。
负载门槛失败时保留完整日志及 `measurements.toml`，回执标记
`performance-load-failed` 并记录错误，CLI 非零退出；这些样本不能参与通过的正式聚合。
双臂比较和三轮聚合重新核对计划中的目标、完整周期窗口及检查点，从逐拍日志重算
前后负载分布并与回执、测量样本交叉核对，同时核对末尾 pending/耗尽及实际成功回收数。
回收日志须为具有完整身份、代次、请求编号、重试边界和放置结果的 `replace`；其他成功
生命周期命令不得计作回收。校验拒绝重复请求、失效重试、非零拒绝副作用及错误的新个体。
每次候选必须符合本节冻结的入口、位置与路线轮换公式，而非只属于合法候选集合。
保留计划须维持对应规模的十/一百 tile、每 tile 一千个唯一身份，tile 内槽位区间为
`0..1000`，完整身份为 `(tile, slot)`；展平索引才使用 `tile * 1000 + slot`。
逐拍持续负载不能出现 Parked 状态。
命令按提交边界重建规范 JSON 数组，与下一 tick 的命令摘要及前后命令游标绑定；
事件按所属 step 重建数组并核对事件摘要，每拍须有完整决策批次记录。正式测量中的
command、step、observation 计时数组还须与 diagnostics 副本一致，不能以单份计时替换
产生通过报告。上述关系检查不构成执行环境真实性或整包一致伪造的密码学证明。
重算文件摘要不能掩盖负载或计数矛盾。该门槛只证明本轮实际工作量，预算与交通质量仍
须各自判定；没有七套正确性角色见证的持续负载不因此获得 correctness 结论。

## 5. 观测与校验边界

运行程序只读取公共已提交状态、`StepOutcome`、Parking 命令结果、Waiting/Conflict
决策、transition events 和快照。校验以下有限不变量：

1. 每次提交后，`live = Active + Parked + Completed`；初始 live 加成功出生减成功移除
   等于当前 live，原子替换同时计一次移除和一次出生。稳定编号、句柄映射一一对应。
2. Active 车身在实际 route occurrence 上投影到一维物理边区间，同边区间不得重叠；
   这是几何区间核对，不实现跟车、信号、Waiting 或冲突求解器。
3. 显式停车排他，虚拟池 Reserved + Occupied 不超容量，Parked 与 Occupied 对应；
   按静态设施归属汇总显式/虚拟绑定，与设施分池 reserved/occupied 和 total 对账；
   Waiting membership/容量/FIFO 和 grant/no-grant 的实际后果符合所选角色合同。
   按已提交 Conflict reservation 的资源身份核对互斥 claim，不另算间隙或决定 grant。
4. 每种必需拒绝选一个代表请求，比较拒绝前后完整 deterministic state digest；
   其余重试核对该个体、绑定、分池计数和提交游标。不对每个拒绝重复捕获整个城市快照。
5. 每个成功 tick 按稳定顺序摘要车辆状态、命令结果、决策和事件；在初态、暖机末及每个
   完整观察周期末，另用 `capture_snapshot` / `deterministic_state_digest` 核对完整状态。
   不把 Debug 文本、内存地址、计时或运行目录写进语义摘要。

逐拍状态与决策批摘要自 `urban-observation-v3` 起采用两级树形哈希：个体槽位和决策条
分别按固定块界 4096 分块，块界是摘要定义的一部分，与 worker 数无关；块内编码后各自
取 SHA-256 叶摘要，主线程按块序把叶摘要送入根哈希，状态摘要的尾部（等待区、灯色、
剩余资源声明）保持原始字节编码。同一计划以不同 worker 数运行的摘要逐字节一致；v3 与
更早版本的摘要值不同，跨摘要版本的运行不属于同一次比较。

命令成功引发的 park/leave/replace 生命周期变化在命令边界记录前后状态、稳定身份及
命令序号；step 引发的变化在 step 提交时记录，以 phase 区分。命令后仍独立采集
`step_before`，供意图计数、红灯等待和路线跨越观测使用，不能将它移到命令前。
命令以提交前边界计数，观察范围为 `[warm_up_ticks,end)`；完成 step 的 tick 是该边界
加一，决策/事件使用 `(warm_up_ticks,end]`，排除最后一个暖机 step、包含最后一个观察
step。显式启用诊断时，完整逐 tick 日志保留暖机与观察两段。

两个独立运行从同一 LFCA 和同一展开计划各自创建新世界，不用首轮快照启动第二轮。
比较输入摘要、逐 tick 状态/事件序列与完整状态检查点；首个差异保留 tick、稳定个体和
命令信息，运行失败返回非零。完整快照检查点不能代替逐 tick 摘要，反之亦然。
运行程序将非语义执行编号写入诊断记录，比较时要求编号存在且不同，以拦截误复制
同一次执行的目录。编号不进入确定性摘要，也不构成独立执行或防伪证明；真实独立运行
由取证流程保证。缺少编号的旧记录需重新取证，不补号转换。

逐域记录唯一已运行的 `road_motor_vehicle`：`N_individual=live`，`N_active` 为提交后
Active 实数，headless 的 `N_presented=0`，两个 aggregate 计数均为 0。Completed 仍属于
live；未来尚未到期和已到期 pending/exhausted 请求分别计数，均不进入 N_individual。

`N_intent` 对成功 tick 使用命令执行完、step 开始前的 Active 实数，并记录依据
`exact_active_before_step`：现有完整路径对每个 Active 调用运动控制更新，即使被阻停也
已计算控制意图。它不等于容量、初始人数或 step 后的 Active 数。step 失败时不声称所有
个体已经更新，记录 actual intent 为未测量，并保留失败；将来 Runtime 改成多频率路径后
本推导失效，需要重新审定观测口径。

## 6. 运行长度与结果包

### 显式诊断输出（#855）

详细日志属于调用方诊断能力，默认关闭。CLI 只有显式传入 `--diagnostics` 才创建并
序列化 `ticks.jsonl`、`commands.jsonl`、`events.jsonl`；运行库以 `Diagnostics`
枚举显式选择，默认值为禁用。禁用时继续执行同一世界、命令、逐拍观测和完整状态
检查点，仅保存计划、最小运行回执及执行计时，不分配详细日志缓冲，也不编码其内容。
失败时仍保存错误与最后提交拍，完整命令/事件明细遵守同一开关。
启用时三份日志各设置 10 MiB 流式缓冲，共 30 MiB，由调用方诊断拥有；禁用时为零。
窗口结束后先刷盘并释放这三份缓冲，再分配逐拍计时的输出缓冲，诊断缓冲同时驻留不超过三份。

结果载荷为 `urban-result-v8`，以必填 `diagnostics_enabled` 绑定实际诊断选择。
未启用详细日志的 probe 可以完成运行，但不能作为逐拍回放或完整语义比较证据。
双臂比较与三轮聚合均拒绝诊断禁用、记录缺失、版本错误或摘要不符的回执。
correctness/performance 必须显式启用诊断；未启用时在安装世界和创建输出前拒绝，
不自动为正式计划开启详细写出，也不在长测结束后才发现取证不完整。

文本诊断采用 Rust `tracing` 的结构化事件、级别与 target，由调用方配置 subscriber。
命令行只在显式启用诊断时安装 subscriber，并通过 `RUST_LOG` / `EnvFilter` 过滤；库
不得自行安装全局 subscriber。可过滤的文本事件不承担逐拍验收记录的完整性；详细
机器记录开启后保留全部规范 JSON 字节，不以过滤或丢弃日志取得性能收益。

日志缓冲、序列化与收尾成本归入 harness，公共 step 计时边界不变。取证时分列调用方
缓冲容量与 Runtime 资源，并区分最终 write/flush 和文件同步请求的完成边界。
`flush` 不是设备同步完成证明。

### 按需表现对照（#713）

Adapter 的宿主表现配置独立于交通计划。`FullValidation` 保留全量提取及原表现行为；
`FullValidationSelected` 全量提取、转换后应用指定身份窗口，作为匹配对照；
`SelectedPresentation` 在提取前按 live 个体身份形成有序选择，仅提取、转换并应用
其中具有已提交来源的车辆。窗口比例以 live 句柄数为分母，offset、stride、reverse
及模式写入证据。选择退出、virtual Parked 和 Completed 仅隐藏表现，真正身份变更
继续经过 typed 生命周期事务；应用前复核消费上下文与放置令牌。

`requested`、`extracted`、`applied`、全世界 `presentable` 与 `N_presented` 分别记录。
全量提取已发生时，不能用较小的 applied 替换 `N_presented`。选择路径保留完整交通
oracle，但不额外物化全量 pose；独立全量对照逐 tick 核对交通及实际 Transform 摘要。
选择、完整提取、转换、绑定维护、应用、验证分别计时，完整表现耗时从选择开始至
应用结束。宿主仍扫描 live 个体及累计绑定，不能据采样减少宣称整个链路 O(K)。

`evidence` 接受完整 correctness 或 performance 窗口；正式性能对照使用下述完整
performance 窗口。三轮正常 release 与独立 allocator、内部阶段插桩构建分开，均绑定
干净且远端可达的源码提交、工具链、输入、计划、窗口与策略。缓冲容量按当前所有者
记录，交换不消除两侧存储，逻辑复制字节不等于实测内存流量。编排及拒绝路径见
[按需表现取证](../../research/issue-713-selected-presentation/README.md)。

### 完整窗口

令 C 为输入中最长完整信号周期的 tick 数。当前目录最长周期 122496 ms，因此
10k 的 C=7656，100k 的 C=3712。所有 phase/offset/需求量子必须能被实际 fixed step
整除，输入变更导致不能整除时拒绝，不能由 harness 舍入相位。

| 运行               | 暖机         | 观察          |              独立次数 |
| ------------------ | ------------ | ------------- | --------------------: |
| 七套正确性行       | C            | 2C            |    每 case/scale 两次 |
| Mixed 正常性能行   | max(512, 4C) | max(4096, 8C) | 每 scale 三个独立进程 |
| 持续 Active 性能行 | max(512, 4C) | max(4096, 8C) | 每 scale 三个独立进程 |

对应正确性总长为 22968/11136 ticks，性能每轮总长为 91872/44544 ticks。
Burst 仍保留共同有限窗口，但重点另列两个提交边界的 raw 结果和安全重试；不从两个
样本伪造 percentile。正确性只做一个 seed、两档、当前固定工具链，不追加平台组合。

实现提供 plan、run、compare 三种操作；CLI 与 #545 使用同一运行库。输出采用新目录，
输入、命令日志与语义证据固定后，计时、环境和错误单独保存。结果包以完成初始化
（世界安装、路线注册、初态校验和初始检查点）为起点。初始化失败由库返回错误，
CLI 输出错误并非零退出；本段接受部分准备文件，不提供结构化初始化失败记录或
半成品世界状态。显式启用诊断的运行及受控执行/校验失败，其结果包最少包含：

- `resolved-plan.toml`：上述实际输入和预期触发；其摘要与来源制品四联进入结果。
- `commands`、`events`、`ticks`：实际顺序、结果和逐域计数，及用于重复比较的摘要。
- `result.json`：工作负载/计划/结果版本、case/scale、LFCA/config/catalog
  摘要、world/policy identity、实际窗口、逐 tile 触发、检查点及本次运行结论。
- `comparison.json`：比较结论、case/scale、计划摘要、比较区间、两臂起止与 worker 数、
  两个执行编号和两份 result 的 SHA256/字节数。CLI 必须指定新报告路径，成功比较才写入；
  两份原始 result 保持不可变。当前载荷为 `urban-result-v8`（显式绑定详细诊断开关；
  incarnation 与请求编号独立，持续负载显式报告实际 Active；v8 起记录存档、续跑来源与
  终点核对值，见 §7）/ `urban-comparison-v3`（见 §7.5），不转换旧记录。
- 正式性能阶段的 `measurements.toml`：git commit、`rustc -Vv`、`cargo -V`、target、构建参数、
  构建期实际 rustflags（`--remap-path-prefix` 来源端以 `<worktree>`/`<cargo-home>`/
  `<rustup-toolchain>` 占位符归一化）与 profile 设置、硬件/OS/电源角色、
  命令行、phase 耗时、计时范围、实际 Active/intent 分布、内存值及测量方法。

首段 Mixed 实现的具体角色、命令与摘要口径见
[运行程序说明](../../tools/laneflow-urban-harness/README.md)。短试跑和正确性运行的
`diagnostics.json` 提供执行编号、环境与诊断计时，不替代正式性能结果；其他 case 与
100k 仍需各自取证。

性能使用 CI 固定 Rust 版本的正常 release binary；正确性摘要、完整快照捕获和诊断
断言耗时不混入正常 tick latency。正式测量二进制由
`cargo +1.98.1 run --locked -p xtask -- build-measurement` 构建（#876）：该 xtask
命令执行冻结的 `cargo +1.98.1 build -p laneflow-urban-harness --release --locked`
并附加 `--remap-path-prefix`（工作树→`<worktree>`、Cargo 主目录→`<cargo-home>`、
rustup 工具链→`<rustup-toolchain>`，固定顺序）、钉住 release profile 各键与工具链内
rustc、显式 `CARGO_INCREMENTAL=0`，并要求依赖源码全部落在工作树或 Cargo 主目录内，
使封存二进制不含采集机本机路径、可原样作为公开证据制品发布。Cargo `trim-paths`
在固定工具链（1.98.1）尚未稳定，不作为映射入口。同一张映射表同时写出归一化记录
`LANEFLOW_MEASUREMENT_RUSTFLAGS`（来源端为占位符），由 harness 经编译期
`option_env!` 嵌入二进制——wire 审计禁止 harness 携带 build.rs，不能以构建脚本
生成代码；profile 记录由 `cfg!(debug_assertions)` 派生（`release;debug-assertions=off`），
钉住的 profile 键值由 xtask 构建入口承载。构建完成固定执行
`check-binary-paths` 扫描（ASCII 大小写不敏感、UTF-8/UTF-16LE 双编码）；发布前
以同一命令（`--evidence-root` 追加证据根）复扫通过才可上传，扫描回执只含占位符、
字节数与 SHA-256。
分别记录 TrafficWorld step、调用方命令与观测开销。
其中 command 只累计六类公共生命周期调用自身耗时，实际 Runtime 拒绝也计入，无调用
则为零；输入准备、延期/重试调度、快照、断言及调用方记账不在该计时范围内。
observation 累计 step 前的 `step_before` 采集、Active/intent 计数、红灯等待扫描，
以及 step 后的信号采集、事件/状态摘要和校验；两段均不含 step 调用。三项
不覆盖全部调用方工作，不能相加冒充整轮墙钟。该计时范围绑定
`urban-performance-measurements-v5`（v5 起 provenance 记录归一化构建 rustflags、
profile 设置与构建提交（build_commit），正式二进制限 `xtask build-measurement` 产出；v4 起观察窗口原始样本数组按 tick 顺序保留，v3 为升序；v3 起 workers 合法域 1..=16，v2 固定单 worker），不转换或合并旧口径载荷。
按性能合同逐轮计算 p50/p95/p99 后取三轮中位数，max 取三轮最坏值，不池化样本求分位；
合并报告 `urban-performance-comparison-v3` 显式记录该口径（v3 起记录三轮已验证的共同 worker 数；v2 及更早报告不转换），样本数仍报告三轮总数。
不能把两个正确性运行当性能轮次；工具链
变化须重跑用于当前判断的三个轮次。未测内存项写明未测量，不填 0。
正式运行在初始化前与窗口结束后核对来源；提交、干净状态、Rust/Cargo/target、构建参数、
构建期归一化 rustflags、profile 设置与嵌入的构建提交（build_commit）、OS/架构、硬件/电源角色、worker 和计时范围必须可用且不变。三轮合并逐项比较这些字段，
并核对各列样本数等于观察窗口长度；缺失、不可用、脏工作树或混合来源均拒绝。
三轮除计时/环境测量文件外的完整语义结果也必须相同：逐 tick、命令和事件文件摘要、
检查点、计数、角色见证及最终世界状态均逐项比较，不能只核对每个包自身文件摘要。
正式结果目录必须在 checkout 外或被 Git 忽略；初始化前验证未来目录不会使干净工作树
变脏，仍在窗口后复查全部来源，不排除任何源文件来绕过检查。
这些记录只作错用检测，不构成二进制构建来源或执行环境真实性的证明。

启用详细诊断时，另按完成的 tick 顺序保留 `timings.jsonl`，每行包含
`tick`、`step_ns`、`command_ns`、`observation_ns`、`tick_elapsed_ns`。
该诊断载荷标识为 `urban-tick-timings-v1`；各分量沿用上述计时范围。
整拍耗时独立计时，覆盖本拍 `advance`、逐拍日志缓冲写入、记账和本拍检查点，
不含初始化、结束后的序列化、最终刷盘及文件摘要；不能用三个分量相加代替它。
按计划拍数在循环开始前预分配记录空间（计入进程峰值），循环内只追加固定大小记录，结束后批量输出；
关闭诊断时不分配该空间、不增加整拍时钟读取、不生成该文件。
观察窗口的三类原始计时数组保留 tick 顺序，分位数只排序副本；逐拍曲线、滚动分位数
及 Active/回收事件关联以显式 `tick` 为键。该文件属于计时封套，不参与跨轮语义轨迹相等比较；
双臂比较与三轮聚合仍要求它及其摘要登记，缺失即拒绝；计时一致性统一由一个校验
入口负责：声明版本、每个完成拍恰好一行且 tick 连续、整拍耗时不小于三个分量之和、
观察窗三个分量与 diagnostics 原始样本逐项相等，正式臂（任何 case）的 measurements
样本也与这些逐拍值逐项相等。
现存没有逐拍计时文件的冻结记录只能作分布分析，不能恢复时间关联。

**威胁模型。** `result.files` 的摘要封套和上述交叉核对用于发现 harness 自身的错误、
不完整输出，以及同一运行内数据之间的不一致；它们不防有人刻意伪造。摘要与被摘要的
文件存放在同一可写目录，改动文件后连同摘要一起重算，本来就能通过任何自校验；
真实性依靠受控的运行环境、冻结的二进制与来源记录以及外部封存，不靠追加格式检查。
因此「改文件并重算摘要后仍被接受」本身不构成缺陷；只有当它揭示 harness 可能自行
产生、且现有校验发现不了的不一致时，才补充检查。
`build-measurement` 的 remap、扫描、配置审计与钉住同属这一边界：它们防的是诚实出错
（用错二进制、忘记映射、采集机残留配置污染构建），不防采集机被蓄意控制——能任意
改写构建过程的主机本来就能伪造全部记录。超出此边界的加固不在本设计内叠加。
嵌套构建使用环境白名单：代理类变量（`HTTP_PROXY` 等）不在其内，依赖须先按
`--locked` 预热 Cargo 缓存；白名单值本身错误时构建响亮失败，不静默产出。
干净判定同样在此边界内分三层：`status`（钉住 `--untracked-files=all`）抓未跟踪、
删除与真实编辑，`ls-files -v` 抓 skip-worktree/assume-unchanged 索引位遮蔽，
`hash-object --no-filters` 与索引 blob 的逐字节比对抓 text/eol 与 `filter.clean`
的转换遮蔽（防的是编辑器残留 CRLF 这类诚实失真：status 判净而 Cargo 编译的字节
与 commit blob 不同）。蓄意部署把脏内容映射回已提交内容的过滤器属采集机被控制，
出界。运行时测量窗口复查继承 git 的转换视图：构建侧已保证二进制按 blob 字节
编译，窗口内转换级漂移不影响已封存二进制，属接受残余。

每项证据显式记录通过、失败、未测量、依赖未交付或不适用，只有通过项参与整体通过。
性能超预算如实报告，不改变正确性预期；实际 Active 衰减或积压必须可见，不能继续用
初始 75% Active 给测量行命名。#544 的交付不包含新性能门禁、产品达标声明或 owner
组件的大范围优化；真实缺陷按组件形成可复现的问题，再决定相应修复范围。

## 7. 存档与续跑

**状态**：已实现（#874；G1 设计 #875）。依据 #861 长窗验收
（[`long-window-acceptance-results.md`](../../research/issue-707-city-parallel/long-window-acceptance-results.md)）。

### 7.1 目的与边界

运行程序是 `TrafficWorld` 的宿主。宿主存档由两部分组成：Runtime Snapshot 保存世界的
全部每世界可变状态（[快照](traffic-runtime-snapshot.md) §3），宿主自己的耐久状态由宿主
保存（快照 §6 回放身份；ADR 0021 的宿主边界）。运行程序已经在检查点捕获完整快照，
`transitions` 证据也在进程内做过保存、恢复与句柄重绑，但 `run` 不能在某一拍写出存档，
也不能从存档在新进程里继续同一计划。本节补上这一能力。

直接用途：长窗里 step 在暖机前约 9,000 拍爬升后进入平台。每次进入平台都要先跑完暖机，
十万规模约 12 分钟；从平台上的存档续跑只需恢复时间，并能在冷机器、新进程里检查平台
成本是否随交通状态而来。

范围：

- 只覆盖 `run` 的无界面宿主（`Host::Headless`）；Adapter 宿主不在本节。
- 存档绑定一个已展开的计划；续跑只继续同一计划，不换计划、不改窗口、不改需求。
- 续跑结果不是正式性能轮次，不参与三轮聚合或 #707 认证；正式轮次仍从第 0 拍的新进程
  开始。

### 7.2 存档内容

存档是输出目录下的 `saves/tick-<T>/` 目录，三个文件：

| 文件          | 内容                                                                        |
| ------------- | --------------------------------------------------------------------------- |
| `world.lfrs`  | 第 T 拍提交后的 `encode_lfrs(capture_snapshot())`                           |
| `caller.json` | 宿主耐久状态，载荷 `urban-save-caller-v1`                                   |
| `save.toml`   | 清单 `urban-save-v1`：身份绑定、两份文件的字节数与 SHA-256、第 T 拍的核对值 |

宿主耐久状态逐项来自 `Harness`，以稳定身份或快照局部标识表示，不写进程句柄：

- 个体表：每个槽位的 `IndividualId`、`crossed_tile`，以及所绑车辆的 `snapshot_vehicle_id`
  （无车辆为空）。车辆标识取自同一次捕获的 `live_vehicles()` 与 `live_order()` 一一对应。
- 路线表：目录路线 key 与 `snapshot_route_id` 的对应。`route_table` 的路线序号按目录
  key 升序注册，由制品重建而不入档；`claims` 中的路线以该序号表示，因此恢复后序号含义
  不变。停车目标、profile 由共享根的稳定标识重建，不入档；`transition_gates` 由制品
  重建。
- 需求：`schedule` 中每个未执行请求的全部字段（到期拍、原到期拍、槽位、序号、尝试次数、
  重试策略和命令），`RequestLedger` 的在途条目（结束的请求已移出）、下一编号、登记
  水位、已登记的预分配编号与 pending/exhausted 计数，回收控制器的 `pending_by_slot`。
- 观测与见证：`tile_evidence`、`red_waiters`、`claims`、`error_counts`、
  `atomic_rejections`、`watched`，以及替换、出生、移除三个计数。

不入档：`step_before`、本拍 `commands` / `events`、三项计时（都在下一拍开始时重建或
清零）；`last_signals` 在恢复后从世界读取，必须与存档时相同。

清单绑定：计划摘要、制品文件摘要（`Artifacts.files`）、fixed dt、拍号 T、命令与事件
游标、`deterministic_state_digest`、第 T 拍 `TickRecord` 的 `state_digest` 及其观测编码
版本（当前 `urban-observation-v3`）、存档时内存中宿主状态的摘要（与终点同一规范形式
`urban-caller-digest-v1`），以及两份文件的字节数与 SHA-256。续跑二进制的观测
编码版本必须与清单相同，否则 `state_digest` 无从核对，直接拒绝。v3 的摘要与 worker 数
无关，存档与续跑可以使用不同的 worker 数。生成存档的执行编号、源码提交、二进制摘要和 worker 数只作来源记录，
不参与续跑判据。

### 7.3 写出

`run` 增加 `--save-at <S>`（可重复，严格递增）。每个存档点必须落在本次实际执行的区间
内：普通运行 `0 < S <= E`，续跑 `T < S <= E`（E 为 `--until-tick`，缺省为计划终点），
否则在创建世界之前拒绝，不会出现运行完成却缺少所请求存档的情况。第 T 拍完成
`advance`、逐拍日志与检查点之后写出存档，写出时间不进入 step、命令、观测与整拍计时；
另记入 `diagnostics.json` 的 `saves`（拍号、捕获、编码、写出各段耗时与文件摘要）。
写出失败使运行失败并保留已有输出，不留半个存档目录被当成有效存档（先写临时目录，
三个文件和清单都完成后再改名）。

带存档的 performance 运行仍完成整个窗口，但回执记录存档拍号，三轮聚合拒绝它，避免
写出存档对后续拍的缓存与内存干扰混入正式轮次。

`run` 同时增加 `--until-tick <E>`：只推进到第 E 拍后结束，状态记为
`segment-complete`；预检要求 `0 < E <= end`，否则不创建世界即拒绝。它只用于取存档和
续跑分段；对 correctness/performance 计划使用时同样只得到分段，不做 case 校验、不写
`measurements.toml`，完整窗口仍要求跑到计划终点。

每次运行（含续跑）在终点 E 另外记录两项终点核对值，写入回执：第 E 拍的完整检查点
（与周期检查点同一摘要，E 恰为周期检查点时复用），以及宿主状态摘要。只取摘要，不写
存档文件。

宿主状态摘要不能直接取 `caller.json` 的字节：快照局部标识按捕获时的槽位顺序分配，恢复
会重排槽位（快照 §6：restore 的 Parked 先行 staging 会重排局部标识），逻辑相同的两臂编码出的局部标识可以不同。
摘要因此对宿主耐久状态的规范形式求 SHA-256，规范形式只含与槽位无关的值：

- 个体所绑车辆以该车在世界 live 序中的位置表示（live 序属于世界确定性状态，由完整
  检查点覆盖），无车辆为空；
- 路线表按目录路线 key 排序，每个 key 连同其所绑 Runtime 路线的稳定边序列编码，不含
  `snapshot_route_id`。只编 key 集合不够：完整检查点含路线记录但不含 key，两条无车
  使用的路线 key 互换时检查点不变，而后续命令按 key 选路会走错边；
- 其余字段（请求、账本、回收、见证、计数）本来就是稳定身份或整数，按 `caller.json` 的
  字段顺序原样编码。

规范形式的载荷标识为 `urban-caller-digest-v1`，与存档用的 `urban-save-caller-v1` 分开：
存档仍写局部标识，供恢复重绑。

### 7.4 续跑

`run <artifacts> <plan> <new-output> --resume <save-dir> [--until-tick E] [--workers N] [--diagnostics]`：

1. 校验清单与两份文件的字节数和 SHA-256、载荷版本，计划摘要与制品文件摘要必须与本次
   输入相同，且 `T < E <= end`（E 缺省为计划终点），保证续跑至少推进一拍；不等即拒绝，
   不尝试转换。
2. 由同一制品得到修订、已提交来源与 `WorldConfig`，以本次执行配置调用 `restore_lfrs`。
   worker 数不进入快照语义，可与存档时不同。
3. 结构核对，在重绑与任何使用之前完成。`caller.json` 里的每个下标、长度与引用都先核对，
   之后的代码才可以按下标访问；否则格式错误的存档会在观测或推进中 panic，而不是在
   恢复时被拒绝：
   - 个体表长度等于计划个体数，每个槽位的 `IndividualId` 与计划布局（tile、槽位）相符；
     `tile_evidence` 恰好每个计划 tile 一项；回收控制器 `pending_by_slot` 与个体表等长。
   - 路线绑定是目录路线 key 与快照路线 ID 之间完整的一一对应：key 集合等于目录全部 key，
     各 key 的快照路线 ID 互不相同，ID 集合等于 `restore_lfrs` 返回的全部路线 ID。
   - 车辆绑定同样是完整的一一对应：有车辆的个体所绑快照车辆 ID 互不相同，个数等于
     `restore_lfrs` 返回的车辆数，ID 集合等于其全部车辆 ID。
   - `claims`、`red_waiters` 引用的个体与路线序号都在范围内；排队请求的槽位在个体表内，
     命令引用的路线 key、停车目标 key 与 profile 都在目录中。
   - 宿主请求状态整体自洽，不等后续推进去暴露：
     - `schedule` 中每个请求的序号唯一、到期拍 `>= T`，并在 `RequestLedger` 中有对应
       登记：首次尝试为 `Scheduled { due }`，重试为 `Pending { attempt, next_tick: Some(due) }`，
       到期拍与尝试次数相同；
     - 反过来，每个 `Scheduled` 或 `Pending { next_tick: Some(_) }` 的登记项恰好对应
       一个排队请求；不存在 `Pending { next_tick: None }`（它只出现在单个请求执行过程中）；
     - pending 计数按登记项重算后与存档值相同；登记项序号低于登记水位或是已登记的预分配
       编号，下一编号大于全部已登记序号；
     - `pending_by_slot` 的每个 `Some(sequence)` 指向未结束的登记项，且其排队请求的
       槽位相同；排队中的回收请求反过来都在 `pending_by_slot` 中登记。

   车辆与路线绑定必须在重绑前核对：两个个体绑到同一个快照车辆 ID 时，若两辆原车逻辑
   状态相同（例如同 profile 的 Completed 车），Runtime 与观测摘要都不变，`slots` 却会
   丢掉一辆车；路线 ID 重复时 `route_table` 的句柄反查会丢掉一条路线，若该路线正被车辆
   使用，观测在查 key 时就会 panic。删掉一个排队重试但保留登记项（需求悄悄丢失）、改动
   登记的 `next_tick`（要到 `RequestLedger::begin` 处理它时才失败）、`tile_evidence`
   截短（要到该 tile 有活动时才越界）也都在这一步拒绝。
4. 按快照局部标识把路线 key、个体槽位重绑到新句柄：重建 `slots` 与 `routes`，
   `route_table` 按目录 key 升序以新句柄重建（序号与内容不变）；按稳定标识重建停车
   目标与 profile。
5. 语义核对：`deterministic_state_digest` 与清单相同；`observe::state` 与清单中第 T 拍
   的 `state_digest` 相同（它同时覆盖 `claims` 与稳定身份映射）；每个 key 所绑 Runtime
   路线的稳定边序列与目录中该 key 的边序列相同（无车使用的路线不进入上述两项摘要，
   必须逐条核对，否则 key 绑错要到下一条命令才显形）；生命周期计数、停车不变量与信号
   签名成立；恢复后的宿主状态摘要与清单相同（导出与导入任何不对称都在此显形）。任一
   不等即拒绝。

   威胁模型：运行程序是用户在自己电脑上运行的用户态程序，存档、回执与日志都是用户
   自己的文件。用户可以改动其中任何内容，也可以改动程序本身，这不是用户态程序应当或
   能够阻止的；核对不防蓄意篡改，摘要只用于身份绑定与发现意外损坏。核对针对三类真实
   风险：用错存档（计划、制品或编码版本不符）、文件意外损坏，以及本程序自身导出与
   导入的缺陷；并保证本程序写出的存档恢复时不 panic。续跑是否正确，最终以与不中断
   运行的分段比较为准（§7.5）。

   只核对边序列不够，所以第 3 步先要求路线一一对应：生成器为同一条边上的多个车位各
   生成一条路线，边序列相同、key 不同（只差锚点位置）。一一对应成立后，边序列相同的
   key 之间互换绑定在世界语义上不可区分，不再影响后续命令。

   `observe::state` 在恢复后调用时没有上一拍对照：`step_before` 不入档，恢复路径会清空
   它，而状态块对每个个体按下标读取它。核对前先把 `step_before` 置为与个体表等长、
   全部为 `None` 的缓冲。`step_before` 只用于生命周期比对与跨 tile 标记，不进入摘要
   编码，因此所得摘要与第 T 拍原值可比；全为 `None` 时不产生生命周期事件，也不改动
   `crossed_tile` 与证据计数，核对没有副作用。第一次续跑推进会在 step 前重新采集它。
6. 从第 T+1 拍起按原循环推进到 E（缺省为计划终点）。窗口、重试截止、观察期计数都按
   计划原样判断，因此续跑与不中断运行在重叠拍上执行同一逻辑。

续跑输出目录与普通运行相同；`ticks.jsonl` 等日志与 `timings.jsonl` 只含 T+1 到 E 的拍。
回执 `resumed_from` 记录存档清单的 SHA-256、拍号与来源记录，`completed_ticks` 仍是
世界拍号。续跑运行同样可以 `--save-at` 更晚的拍。

`timings.jsonl` 行格式仍为 `urban-tick-timings-v1`，校验改为按区间：起点取
`resumed_from` 的拍号 T（普通运行为 0），要求各行拍号从 T+1 连续到 `completed_ticks`、
行数为 `completed_ticks − T`；回执另记观察窗与 `(T, E]` 的交集，信封中的观察窗样本
只与该交集内的行逐项相等。普通运行 T = 0，校验与现行相同。

### 7.5 结果与比较

- 回执升为 `urban-result-v8`，新增 `resumed_from`、`saves`、分段终点、终点核对值与观察窗交集；状态新增
  `segment-complete`。旧版本回执不转换。
- 续跑运行和带存档的 performance 运行都不写正式 `measurements.toml`，三轮聚合拒绝。
  计时样本保留在 `timings.jsonl` 与 `diagnostics.json`。
- `compare` 增加分段比较：一份完整运行、一份续跑（或两份从同一存档续跑的运行），
  要求同一计划且两臂终点 E 相同，并且两臂确实从同一状态出发：完整臂与续跑臂比较时，
  续跑臂 `resumed_from` 的存档清单 SHA-256 必须出现在完整臂回执的 `saves` 中（即存档
  由完整臂在第 T 拍写出）；两份续跑比较时，两臂的存档清单 SHA-256 必须相同。不满足即
  拒绝比较——否则用同计划另一次执行的存档续跑，第 T 拍的差异若在区间内收敛，比较也会
  通过。满足后，在两者共有的推进区间 `(T, E]`（T 取两臂起点中较晚者）
  上逐行比较 `ticks.jsonl`、`commands.jsonl`、`events.jsonl`，首个差异保留所属推进
  与行。两臂的出发状态也必须相同：续跑臂由上述存档绑定保证；两臂都从第 0 拍起跑
  （T = 0）时，比较两臂第 0 拍的初始完整检查点，否则安装时的隐藏状态分歧若在首个
  周期检查点前收敛，日志与终点摘要都发现不了。逐拍日志之外还必须相等：区间内计划
  规定的全部周期检查点（两臂回执都必须完整
  记录这一集合，缺任何一个即拒绝比较，不能只比两臂碰巧都有的检查点——否则只体现在
  Runtime 隐藏状态、又在终点前收敛的分歧会因漏记检查点而通过）、第 E 拍完整检查点，以及
  第 E 拍宿主状态摘要（覆盖 `tile_evidence`、`red_waiters`、`watched`、生命周期计数等
  只观察、不驱动交通的累计量）。两份从同一存档续跑的运行比较可以替代完整运行作为 A/B
  的语义对照。
- 比较报告升为 `urban-comparison-v3`，载荷显式记录比较区间 `(T, E]`，以及每臂的起点
  （0 或 `resumed_from` 存档清单摘要与拍号）和终点。完整运行之间的比较是 T = 0、
  E = 计划终点的特例，同样写 v3；v2 不再生成，旧报告不转换。
- 比较状态：只要任一臂是续跑或分段（未跑到计划终点），通过时状态记为 `segment-match`，
  不沿用 `case-pass`、`performance-match` 等正式状态。它只说明两臂在区间内相同，不是
  正确性 case 通过、正式性能或认证证据（§7.7）；正式状态只留给两份从第 0 拍跑到计划
  终点的运行。
- 每行属于哪次推进由现有字段推出，日志格式不变：第 k 次推进先在边界 k−1 执行命令、
  再步进到第 k 拍。`commands.jsonl` 的行按 `boundary + 1` 归属；`events.jsonl` 中 `"phase":"command"` 的行按 `tick + 1` 归属，
  其余行（决策批、转移、步进期生命周期、停车到达）按 `tick` 归属；`ticks.jsonl` 按
  `tick` 归属。只按拍号筛选会漏掉续跑第一次推进的命令，或混入完整运行上一次推进的
  步进事件。

### 7.6 等价性与已知风险

Runtime 快照合同要求恢复后的世界与保存时逻辑相同，并以检查点逐点相等发现失同步
（快照 §6、§9）；`transitions` 证据在 fixture 规模比较过续跑与不中断运行。十万规模的
长段续跑尚无证据，首个实现切片必须在十万规模做分段比较，两臂都由实现后的 v8 二进制
运行：A 臂以 #861 长窗计划从第 0 拍跑到第 14,848 拍（`--until-tick 14848`），并在
第 11,136 拍 `--save-at`；B 臂从该存档续跑到第 14,848 拍。`compare` 在推进区间
(11136, 14848] 上按 §7.5 比较。不为此接纳 v7 回执：#861 长窗（`urban-result-v7`）
只作旁证，A 臂三个日志与长窗同区间的行按 §7.5 归属规则逐行对照，用于确认实现没有
改变交通，不经 `compare`、不进入判据。#861 长窗是 `urban-observation-v2`，A 臂是 v3，
对照时排除摘要类字段：`ticks.jsonl` 的 `state_digest` 与 `event_digest`，以及
`events.jsonl` 决策批行的 `digest`；其余字段与 `commands.jsonl` 逐字节相同。

可能的差异来源，出现时按 Runtime 或宿主缺陷单列，不在运行程序里掩盖：

- 恢复后句柄槽位与代次重新分配。Runtime 内部若有按槽位或代次决胜、且结果对外可见的
  逻辑（例如拒绝结果里报告的阻挡车），续跑的命令日志可能与不中断运行不同。
- 快照不保存的派生状态（frontier、本拍授予、占用与重叠索引、名单缓存）在恢复后重建，
  必须只影响耗时，不影响结果。

性能代表性：恢复后的进程内存布局是新的，派生索引首次查询会重建，前若干拍的耗时偏高；
平台段若有部分成本来自长跑进程的内存老化，续跑测不到。所以：

- 续跑分段的计时用于筛查与归因，丢弃恢复后的前若干拍（实现切片实测确定拍数后写入
  本节）；
- 保留下来的候选仍以从第 0 拍开始的完整长窗复核；
- 「从平台存档冷启动续跑的 step」与「长窗同拍的 step」相差多少，本身就是平台成本来自
  交通状态还是进程/主机状态的检验。

A/B 用法：两臂从同一存档续跑。候选改变快照格式或恢复不变量时存档会被拒绝，需要用
候选自己重新取存档；候选改变交通行为时两臂续跑的轨迹不同，只比较耗时，语义另行验收。

### 7.7 不做

- 不改 Runtime 快照格式、公共 API 或恢复规则；不在快照里加入宿主状态。
- 不支持换计划、换窗口或换制品续跑，不做存档版本转换。
- 不支持 Adapter 宿主存档；`transitions` 证据的进程内恢复改用本节的宿主状态序列化，
  只保留一条重绑路径。
- 不把续跑结果作为正式性能轮次、#707 认证或正确性 case 的通过证据。

### 7.8 测试

- 宿主状态序列化往返：fixture 规模的持续负载与 Mixed 计划，在暖机、观察期、有 pending
  重试与 role 见证的拍存档，往返后逐字段相等。
- 恢复后核对：清空 `step_before` 的恢复路径上调用 `observe::state` 不 panic，摘要等于
  第 T 拍原值，且不产生事件、不改动 `crossed_tile` 与证据计数。
- 续跑等价：fixture 规模多个存档点续跑到终点，三份日志与不中断运行在共有推进区间逐行相同，
  最终检查点、回执计数与 `tile_evidence` 相同；1 worker 存档、16 worker 续跑同样成立。
- 拒绝面分三层，都不写回执以外的输出：
  - 恢复前：清单或任一文件摘要不符、版本不符、计划或制品不同、`--save-at` 拍号不在
    递增顺序或不在本次执行区间（普通运行 `0 < S <= E`、续跑 `T < S <= E`，两种组合
    都覆盖）、`--until-tick` 不满足 `0 < E <= end`、续跑不满足 `T < E <= end`、
    清单观测编码版本与二进制不同，均在创建世界之前失败；
  - 结构核对（恢复出世界后、重绑与任何使用之前）：个体表长度或布局不符、`tile_evidence`
    截短或超长、`pending_by_slot` 长度不符、路线或车辆绑定不是一一对应（含两个边序列
    相同的车位路线 key 指向同一快照路线 ID；路线 ID 重复且被遗漏的路线正被车辆使用；
    两个绑定同状态 Completed 车的个体指向同一快照车辆 ID）、`claims` 或排队请求引用越界、
    删除一个排队重试而保留其登记项、改动登记项的 `next_tick`、`pending_by_slot` 指向已
    结束的请求。全部返回拒绝，不 panic。
  - 语义核对：`deterministic_state_digest`、`observe::state`、路线边序列、生命周期计数、
    停车不变量或信号签名不符；在 `caller.json` 里互换两条无车使用路线的局部标识。
  - 后两层失败时恢复出的世界都不发布、不推进第一拍。
- 计时边界：存档写出不进入四项计时；带存档的 performance 回执被三轮聚合拒绝；
  `T > 0` 的续跑 `timings.jsonl` 按区间校验通过，起点、行数或观察窗交集不符时拒绝。
- 比较：续跑臂的存档不在完整臂 `saves` 中（含同计划另一次执行写出的存档）、两份续跑
  的存档清单不同、任一臂缺少区间内计划规定的周期检查点，均拒绝比较；两个从第 0 拍
  起跑的臂初始检查点不同，比较失败；宿主累计量（如 `tile_evidence`）被篡改而逐拍日志相同的
  续跑，比较失败；终点
  检查点不等时比较失败；`urban-comparison-v3` 记录区间与两臂起止。

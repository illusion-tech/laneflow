# CI 受影响验证计划

## 1. 问题与原则

现行 CI 的 Rust 侧由单布尔门驱动：`Detect path changes` 输出 `rust` /
`bevy`，命中任何 Rust 相关路径即整组执行全部重活——`Rust checks`、
`Evidence fixture tests`、`Placement fixture tests`、`Urban harness tests`
与 `Wire toolchain audit`，测试步一律 `--workspace`。动机观察值
（2026-11-19 运行抽样，非稳定基线）：一条 xtask 注册表 JSON 加四个文档的
PR 全量跑了 2,712 项 workspace 测试与全部专项 job；一次合并至少三次全量
（最后一次 PR push、merge_group、main push）；`execution-evidence` 专项以
约 102 秒构建运行 3 项共 0.014 秒的测试。nextest 并行、sccache、lld 等
构建侧优化已到位后，继续压缩的方向只剩缩小实际构建与执行范围。

本设计确立四条原则：

- **验证成本与变更责任对等**：一次变更承担自身及其消费者的验证成本，不
  承担无关面的成本。叶子工具变更承担叶子工具的成本；底层合同变更承担
  广泛回归的成本——后者选出大半个仓库是正确结果，不是机制缺陷。
- **精确优先于启发**：影响范围由可计算的事实来源推导（Cargo 依赖图与
  显式声明的额外输入关系），不靠文件名猜测、目录近似或历史执行覆盖率。
- **无法判定即全量**：选择机制宁可多跑，不静默少跑（与 #1298 裁决的
  白名单制同一哲学）。
- **解释义务**：每次扩大或缩小执行范围，都能说清它保护了哪条依赖或
  哪项契约；说不清的范围变化按全量处理。

## 2. 验证任务的身份

一个验证任务的身份是「包或目标 × feature 配置 × 平台 × 检查类型」，
不是一条测试命令。现行任务举例：runtime 默认配置、runtime 开启
`placement-fixtures`、runtime 开启 `execution-evidence`、urban-harness
开启 `adapter`、bevy `native-example` 示例编译、wire 审计、cargo-deny。

- **配置是身份的一部分**。`placement-fixtures` 空特征全量重跑是 feature
  副作用护栏，不因测试名与其他配置重叠而合并、删减或跳过；某配置受影响
  时保持其约定的验证范围。
- **required check 接口恒定**。九个 required check 名称（PR 与
  merge_group 同名）不变；计划决定每个 check 内部执行什么，不改变 check
  的存在性与成功语义。计划为空集时该 check 以显式 skip 模式成功并记录
  原因（沿用现行非 Rust 路径的 skip 模式）。
- doctest 与 clippy 各有独立入口与受影响包集合，不随测试命令的收窄
  而消失。

## 3. 影响模型

影响模型由两部分组成：Cargo 能表达的依赖关系自动读取，Cargo 不能表达
的输入关系集中显式声明。不维护第二份 crate 依赖清单。

### 3.1 Cargo 图

- **事实来源**：`cargo metadata` 的 workspace 内部边，含依赖种类
  （normal / build / dev）与 feature 信息。取图须覆盖 CI 实际使用的
  feature 配置，不能只读默认特征——仅在某 feature 开启时激活的可选
  内部依赖不能因此缺边。
- **传播规则**：改动包 X，受影响集 = X 自身 ∪ 全部传递消费者（含测试
  目标）。方向论证依赖一个前提——其余包的有效构建配置不变：闭包外的
  包不依赖 X，编译破坏与行为破坏在依赖方向上都不可能落在闭包外；被改
  行为的破坏只会砸到依赖它的测试，而它们全部在闭包内。
- **前提由清单规则守护**：`resolver = "2"` 不取消普通依赖的 feature
  合并。修改任何 workspace 成员的 `Cargo.toml` 依赖声明（例如叶子包给
  共同依赖追加 feature），就可能改变该依赖及其全部消费者在
  `--workspace` 命令下的被测配置，而这些包未必位于改动包的反向闭包
  内。第一阶段因此把**全部 workspace 成员的 `Cargo.toml` 变更列入恒
  全量**（见第 6 节）；此后如需收窄，须以「解析后有效配置发生变化的
  依赖包及其受影响任务」扩充种子，且从 `--workspace` 收窄为 `-p` 时
  保持所选验证任务原有的有效 feature 语义。具体解析算法归 G2。
- **边类型化分两阶段**。第一阶段普通、构建与开发依赖同权传播——保守
  多选，但机制先成立、影子数据先积累。第二阶段将 dev 边类型化：dev
  依赖只使消费者的测试目标受影响，不再沿其生产链向更下游传播（Cargo
  语义本就如此）。两阶段的切换以影子期对照数据为依据，不预先承诺时点。

### 3.2 额外输入注册表

Cargo 图之外的输入关系集中在一个机器可校验的注册表中，形态沿用
`xtask/data` 数据注册表 + 校验测试的既有模式（#1459 先例）。已知类别
与实例：

| 类别 | 已知实例 | 影响指向 |
| ---- | -------- | -------- |
| 跨包 fixture 嵌入 | `runtime/tests/snapshot_replay.rs` 嵌入 `compiler/tests/fixtures/portable/**` | fixture 所属包的消费者测试 |
| 文档进可执行验证 | crate README 经 `include_str!` 进 doctest 与 clippy（`docs/` 零嵌入；tools 嵌入面按 #1298 清点） | 所属包 |
| 数据注册表 | `xtask/data/**` | 常驻 `Commit message` job 的校验测试 |
| schema 与生成源码 | `schemas/**` | Schema Codegen 任务 |
| 审计与全局输入 | wire 审计扫描面、cargo-deny 配置、nextest 配置 | 对应检查任务 |

- 注册表条目 = 路径模式 → 受影响任务或包；未落入任何条目的路径进入
  第 4 节的「未知」态。
- 注册表是归类的事实依据，其一致性不能靠事后发现：每次生成计划前，计划器
  对全仓 `include_str!` / `include_bytes!` 清点并与注册表对账；漏登记、
  登记失效或出现未经核对的非字面量实参时，受影响计划不成立，退回全量并
  列出差异。守门位置选在计划生成处而非校验测试：计划器所在的包不在多数
  变更的反向闭包内，按计划执行后它的测试不会随任意 Rust 变更运行。校验
  测试保留为开发期护栏；新增编译期嵌入位置仍在引入时同步登记，延续
  #1298 白名单制的维护责任，嵌入清单不靠人记。

## 4. 变更归类与失败关闭

每个变更文件必须归入三态之一：

1. **属于**某包或某验证任务——沿影响模型传播；
2. **有明确依据不适用**——如纯治理文档只触发文档检查与提交信息检查；
3. **不能确定**——扩大到完整适用套件。

「没有匹配到规则」不等于「不需要测试」；这纠正现行布尔门"未列入清单的
路径静默跳过重活"的边界。

失败关闭规则：

- 读取 diff、解析依赖、生成计划的任何一步失败，都不是空计划的成功：
  全量回退；无法回退时阻断（红）。
- 区分「成功计算后确实不适用」与「计算失败」：前者记录原因后允许 skip，
  后者不得出现绿灯。
- 现行 changes job「检测失败变红」的 fail-closed 语义保留，并延伸到
  计划层：计划器自身崩溃、注册表校验不过、输出无法解析，一律按全量或
  阻断处理。

## 5. 计划的生成与消费

- **计划器是 xtask 子命令**，纯函数：输入为变更文件清单与基线引用，
  输出为任务集及每项的触发原因。它不执行构建、不调度任务，构建与执行
  仍由 cargo、nextest 与现有检查承担。
- **输入语义**：PR 以 GitHub 合并快照对 base 的完整差异为准（含新增、
  删除、重命名与移动，不看最后一个提交）；merge_group 按自身 base/head
  重新计算，不复用任何单 PR 的计划——队列里的组合可能与单 PR 验证时
  不同。
- **消费**：CI 的门 job 从「输出布尔」演进为「输出计划」；各检查 job 按
  计划取本任务集（如 nextest 的 `-p` 与目标选择参数）。计划要求的任务
  集为空时显式 skip 并记录原因。
- **解释**：每次运行把「文件 → 包 / 注册表条目 → 任务」触发链、不适用
  判定与全量回退原因写入 Actions summary。单次运行的清单与测量流水
  不入仓（研究结论与过程数据边界不变）。
- **计划-结果核对**：聚合步核对计划要求的任务全部完成，无失败、取消、
  缺失或计划外跳过；不适用必须来自成功算出的计划。不依赖 YAML 条件
  表达式自身的正确性。

## 6. 全量时机与过渡

**恒全量的场合**：

- 全局构建配置（workspace 根清单与**全部成员的 `Cargo.toml`**、锁文件、
  `.cargo/**`、工具链文件、nextest / deny 配置；其中成员 `Cargo.toml`
  变更会改写 feature 合并结果，前提守护见 3.1）、workflow 自身、
  计划器代码与注册表自身的变更；
- 三态归类的「未知」；
- 注册表与全仓清点对账不一致；
- 周期性主干全量回归——发现选测规则遗漏与环境变化的安全网；
- 发布候选验证。

**过渡分三步，前一步的数据是后一步的前提**：

1. **影子阶段**：计划器只计算并输出「本次会运行什么」，CI 行为不变。
   对照案例覆盖注册表与纯文档、叶子工具、底层共享包、跨包 fixture、
   feature 配置、删除 / 移动 / 重命名、新增包、计划器自身变更，并加入
   针对漏选边界的反例验证。几次全量通过只说明那几个版本通过，不构成
   选择器正确的证明。
2. **PR 切换**：PR 运行按计划执行；merge_group 保持全量兜底。此阶段
   选择逻辑的 bug 只会推迟发现，不会产生假绿 main。
3. **merge_group 切换**：队列对实际集成候选重算并执行受影响计划。退出
   条件为连续 N 周周期全量与影子审计零漏选（N 在影子期数据具备后定，
   不预先承诺）；达成并留档后才切换。

main push 运行的职责拆分：测试计算、缓存生产（sccache / rust-cache 的
写回）与安全结果发布分别处理。**去重按任务逐项成立，不按事件总括**：
只有对应任务已在等价输入快照、相同有效配置与平台上成功完成，才复用
验证结果；未在 merge_group 执行的任务（如跨平台精确字节验证）、缺少
成功证据或无法确认等价的任务，继续在 main push 执行，或先明确迁入
merge_group。CodeQL 的独立政策不受本节影响：main push、定时与手工
触发仍执行全量分析（`security-scanning.md`）。

## 7. 度量与验收

六项指标及其回答的问题：

| 指标 | 回答的问题 |
| ---- | ---------- |
| PR 完成时间 p50 / p95 | 开发者是否更快拿到结果 |
| 累计 runner 时间 | 总计算资源是否真的减少 |
| 构建时间与测试执行时间分解 | 改善发生在哪一部分 |
| 选中包、目标与任务数 | 是否有效排除了无关工作 |
| 全量回退率与原因分布 | 规则是否仍然过粗或不完整 |
| 周期全量与漏选审计发现 | 选择机制是否可靠 |

记录载体为 Actions summary 与 gh api 查询；过程数据不入仓。验收标准以
issue #1464 为准，其中 merge_group 切换以第 6 节退出条件达成为前提。

## 8. 非目标

- 不做函数或代码行级的覆盖率选测：依赖历史执行覆盖，对新增路径、宏与
  外部数据输入存在漏选风险，留作远期可选优化。
- 不引入第二套构建平台或任务图系统；计划器保持小，只负责读变更、算
  影响、出计划。
- 第一阶段不改变 required check 名称、Ruleset 与各项检查的验证语义。
- 不因耗时理由移出容量计数、失败原子性、格式正确性等断言——先判定
  验证责任归属，再决定运行条件。

## 9. 适用性与实施边界

<a id="applicability"></a>

本文是机制合同：影响模型、变更归类、可靠性规则、全量时机与过渡策略。
以下内容归 G2 实施设计，不构成本文的冻结对象：计划器命令行接口与输出
格式、注册表文件的具体 schema、CI YAML 接线与聚合步实现、`cargo
metadata` 取图的具体 feature 组合、影子阶段的对照执行方式、N 值。

依赖约束：默认路线不新增第三方解析依赖——`cargo metadata` 的 JSON
输出由既有 serde 解析面处理（MSRV 1.99.1 无忧）；如评估引入
cargo_metadata、guppy 或 determinator，须先通过 MSRV 1.99.1 试构建与
依赖策略（cargo-deny）审查，determinator 的非包文件规则模型仅作设计
参考，不直接套用其默认忽略规则。

本机制的每一步缩小都对应第 1 节的原则；任何后续修订不得削弱第 4 节的
失败关闭语义。

# 准入候选名单复用入口 frontier

**文档状态**: Accepted（#861；第一步已实现）<br>
**最后更新**: 2026-10-10<br>
**适用范围**: `spawn_vehicle` 与 `replace_completed_vehicle` 运动安全准入里的候选名单
（冲突区申请者、排队进入者、格点到达）如何得到

**关联文档**:

- [`traffic-runtime-vehicle-placement.md`](traffic-runtime-vehicle-placement.md)
- [`traffic-runtime-near-gate-frontier.md`](traffic-runtime-near-gate-frontier.md)
- [`traffic-runtime-conflict-occurrence.md`](traffic-runtime-conflict-occurrence.md)
- [`traffic-runtime-waiting-zone.md`](traffic-runtime-waiting-zone.md)

不新开 ADR。公开 API、错误分类、数据格式、快照与 Adapter 都不变。准入规则只有
一处变化：格点 owner 的平局键统一为 `live_order` 序号（第 4.3 节）。除此之外，
同一已提交状态上名单里读到的每个值必须与全量重建相同。取舍以性能优先：能让各条
路径与求值顺序无关、省掉排序和扫描的做法优先。

## 1. 结论

1. 冲突区申请者名单和排队进入者名单，只对「已发布近门集合 ∪ 已发布失效名单 ∪
   本窗生命周期增量」里的车求值，不再对全部 live 车预览。
2. 格点到达改为按格点求值：第一次读取某个格点时，经 frontier 反向索引取得来源车、
   计算到达下界并缓存到名单失效；没有被读取的格点不求值。
3. 任一绑定条件不成立时，本次整份退回现行全量重建。全量重建仍是唯一的兜底路径，
   不是可选开关。
4. 分两步交付：先做申请者与排队进入者（第 3 节），再做格点按需求值（第 4 节）。
   每一步单独对拍、单独做普通 ABBA；前一步没有收益或证明不成立，不做后一步。

## 2. 现状与成本

`ensure_spawn_contenders` 在名单身份（世界世代、观测状态序号）对不上时调用
`rebuild_spawn_contenders`：按 `live_order` 逐辆读状态、做一次运动预览、计算贡献，
再写入三份名单和逐车贡献记录 `owners`。一次 `step` 之后第一次进入运动准入就会
重建；同一命令窗内成功生成后的增量刷新维持名单有效。

十万辆持续 Active、16 workers、512 拍暖机 + 1024 拍观察的插桩分解（#861 评论）：

- 观察窗重建 132 次、合计 10.32 s，平均 78.2 ms，占回收 API 时间约 60%；这些拍
  决定了命令耗时的尾部。
- 逐车约 0.74 µs，其中运动预览 0.23 µs、贡献计算 0.35 µs、写表 0.16 µs，没有单一
  热点。局部提速（#830、#834）没有可重复收益。
- 1319 万次逐车求值中 77.2% 贡献全空；22.8% 有时窗内格点到达；只有 3.4% 这一拍会
  申请冲突区，排队进入几乎为零。

准入真正读取的是：

| 名单                          | 读取方                                                 | 读取范围       |
| ----------------------------- | ------------------------------------------------------ | -------------- |
| 冲突区申请者 `best`           | 前序名次占用重放、共享下游的申请者、车身复核、排队挤占 | 全部冲突区     |
| 排队进入者 `waiting_entrants` | 排队授予、复核                                         | 候选所在排队区 |
| 格点到达 `cell_approach`      | 候选与后车的让行检查、复核目标                         | 只读具体格点   |

所以申请者与排队进入者必须完整，但只来自这一拍够得到门的车；格点到达只需要被
读到的格点。

## 3. 申请者与排队进入者来自近门集合

### 3.1 求值集合

记已发布近门集合为 `N`，已发布失效名单为 `I`，自上次发布以来记下的生命周期增量
为 `D`（`spawn_vehicle`、`replace_completed_vehicle`、`leave_parking`、已提交的
`rebind_parking_route`，以及其他调用 `note_active_source` 的位置）。重建只对
`N ∪ I ∪ D` 中仍然有效、`Active`、路线需要准入的句柄调用现有
`add_spawn_contender`。其余车辆不预览，不写申请者或排队进入者。

第一步交付时格点到达仍对全部车求值，但其余车辆只计算格点贡献，不做运动预览；
第 4 节交付后，其余车辆连格点也不再逐辆求值。

求值顺序按 `live_order` 序号，`ContenderRank` 的 `update_sequence` 仍取该车在
`live_order` 中的序号，与全量重建相同。句柄需要再核对一次：槽位已释放、generation
已变化或已不在 `Active` 的旧句柄跳过。

实现上，重建先按车辆槽位把 `N ∪ I ∪ D` 中仍有效的句柄标进一张可复用位图，再照旧
按 `live_order` 逐辆处理：位图内的车预览并写全部贡献，位图外的车只写格点贡献。
所以格点插入顺序与全量重建相同，第一步不改变任何读到的值。

现行全量重建在预览失败（路线或 profile 缺失、运动非有限）时以 `StopConstraint`
整份放弃名单。位图外的车不再预览，这类失败只会在它真正够到门、进入求值集合时
出现；它够不到门时，预览结果本来就不影响任何名单。

### 3.2 需要证明的覆盖

现行贡献只在下面任一条件成立时写申请者或排队进入者：

- 预览后游标越过某个 Gate hop，或预览后、预览前正好停在该门上（`contender_notes`
  的 `reaches_gate`）；
- 预览后游标越过某个排队区入口 hop（非成员）。

排队区入口 hop 在路线编译时校验为带门的 hop（`tables.rs` 中 `hop_gate` 与入口门
相等），所以两类都属于「这一拍够得到下一道门」。要证明：凡满足上述条件的车都在
`N ∪ I ∪ D` 中。

1. **同一状态。** 近门集合在运动写出下一提交状态之后分类，成功提交时发布；命令
   不能插进一次 `step`。所以两次 `step` 之间，已提交状态中没有被命令改写的车，
   正是分类读取的那份状态。被命令改写过的车都在 `D` 中，或已被移出 `Active`。
   实现前要逐一核对所有改写车辆位置、速度、路线、profile 或状态的命令都记了
   增量或拆除；漏一处即不成立。
2. **到门距离。** 分类用的门距从规范化游标起算（进度与余量为 0 时回到上一 hop），
   已越过的门距离为 0。现行贡献从同一规范化游标 `first_possible` 开始找门。
   两边的「下一道门」是同一处。
3. **一拍可达上界。** 近门判定是 `门距 ≤ v·dt + ½·a·dt² + 2 mm`，`a` 取缓存的
   最大加速度。要证明准入用的预览
   （`preview_active_vehicle_with_waiting_stop`）位移不超过这个上界：预览加速度
   不超过 profile 最大加速度，亚毫米余量小于 2 mm 余量，排队停车只会缩短位移。
   #740 的让行已依赖同一上界；这里在实现时逐条核对预览代码，并用夹具覆盖边界值，
   不只引用 #740。
4. **缓存对不上的车。** 没有有效槽位、句柄 generation 不同、路线或所在边变化、
   进度回退的车，分类时同时进入 `N` 与 `I`，不依赖旧门距。
5. **越过多道门。** 一拍越过第二道门必先越过第一道门，所以只看下一道门不会漏。

实测（不合入的覆盖探针，main `7e4fc6ea`）：十万辆持续 Active、16 workers、512 拍暖机
+ 1024 拍观察，全部 210 次全量重建找到的 5,226,563 条申请者与排队进入者记录都在
`N ∪ I ∪ D` 中，漏判为 0。每次重建的 `N ∪ I ∪ D` 中位数 9,043 辆（p90 9,489，最大
10,188），约为 live 车的 9%；`I` 平均约 86 辆。探针运行的交通文件与未插桩运行逐字节
一致。实测不能替代上面的证明；现有 runtime 测试几乎不走已发布名单，实现时必须补
第 7 节的定向夹具。

### 3.3 什么时候退回全量

以下任一条件成立，本次调用现行全量重建：

- 没有证明时窗（分类不运行，名单不存在），或没有路权策略；
- frontier 未发布、世界身份（`world_id`、`WorldGeneration`）与当前不符，或最近一次
  提交链接失败使名单标记为未发布；
- 快照恢复或修订切换后尚未完成一次成功 `step`；
- 求值集合的暂存区预留失败。

命令路径只读 frontier 的已发布名单、增量与槽位缓存，不写 `FrontierMaintenance`，
不清空增量，也不发布。下一次 `step` 看到的 frontier 与没有这次准入时相同。

## 4. 格点到达按格点求值

### 4.1 第一次读取时求值

格点到达的读取方是候选与后车的让行检查、复核目标收集，以及对每个复核目标重做的
运动比较（`reject_existing_hard_stop` → `placement_motion` → `admission_stop`，读的是
目标车自己路线上的让行格点）。读取地址只有在走到那一步时才完整，不另做一遍收集。

格点槽位旁加一张「已求值」位图。读取时位图未置位，就按 4.2 求值、写入槽位并置位；
已置位直接读。读取方现在持有只读借用，实现可以把读取改为可变借用，或只对格点
槽位与位图使用内部可变，以热路径开销较小者为准。命令路径单线程，不引入锁。

因为 4.3 的归约与插入顺序无关，格点在哪一次准入、被谁先读到，都不影响它的值。

### 4.2 一个格点的来源车

对地址 `c`，来源车是：

- frontier 反向索引 `by_cell[c]` 中、不在 `I ∪ D` 的车：剩余距离 = 缓存距离 −
  同一条边上的进度差；
- `I ∪ D` 中路线经过 `c` 的车。名单重建时对 `I ∪ D` 整段重走一次，把各车时窗内的
  出现项放进准入自己的暂存区，不写回 frontier 槽位；用按槽位的位图判断是否属于
  `I ∪ D`。

证明时窗与 frontier 相同，都取自策略绑定的 `horizon()`。缓存的出现项本身就限于
时窗内；更远的出现项因加速进入时窗时，分类已把这辆车放进 `I`。

每辆来源车的到达下界用现行 `PreparedApproachEta` 与 `PreparedSignalApproach`
计算，和 `contender_notes` 完全相同。需要证明或在实现中处理：

- 进度差超过缓存距离（本拍已越过该入口）时，现行贡献不再记这处出现项；按需
  求值必须同样排除，不能饱和成 0；
- 证明时窗外的出现项不记；
- 同一车辆在同一格点有多次出现时，先做车辆内归约，再参与格点归约。

### 4.3 归约与平局

格点只保留两个不同 owner，按 `(估计类别, 毫秒, update_sequence)` 排序。现行代码里
只有申请者与排队进入者的 `update_sequence` 是 `live_order` 序号，其余车以 0 写入，
估计相同时留下谁取决于插入顺序；增量刷新按槽位顺序重新归约，全量重建按
`live_order` 插入，两者在平局时可能留下不同的车，而复核目标读取的正是 owner 身份。

改为：所有 owner 的 `update_sequence` 都取该车在 `live_order` 中的序号。键成为全序，
「取最小的两个不同车辆」与插入顺序无关，于是：

- 全量重建、按需求值、增量刷新在同一已提交状态上得到相同的两个 owner；
- 按需求值不用按 `live_order` 排序来源车，可以直接按反向索引顺序处理；
- 增量刷新不再为了重新归约按槽位扫描全部逐车记录。

格点读出的估计值不变；变的只是估计相同时留下哪辆车，进而可能改变复核目标集合。
这是本文唯一的规则变化。验收时比较交通文件：逐字节一致就直接记录；不一致必须
定位到平局差异并在结果记录中说明，不能当成性能噪声。

序号取自 `LiveOrderIndex`；它对不上当前 live 前缀且准备失败时，退回全量重建。

### 4.4 生成成功之后

新车进入 `D`，它的出现项立即重走，并插入已求值的格点；未求值格点以后求值时自然
包含它。

已有车在同一命令窗内的格点贡献不随别的车生成而变：到达下界只取决于该车自己的
位置、速度、余量、最大加速度、证明时窗和信号放行下界，而生成不预写通行权、不改
信号、不改别的车的状态。实现时要逐项核对这一点。成立时，受影响旧车的刷新只撤销
并重算申请者与排队进入者，不触碰格点。

`note_inserted_vehicle` 用「名单里是否已有申请者或格点 owner」决定能否跳过刷新，
改为只看申请者、排队进入者和已求值格点；未求值格点以后按当前状态求值。

## 5. 逐车贡献记录

`owners` 现在为每辆求值过的车各保留一条记录，记下它贡献的冲突区、格点和排队区，
十万辆持续场景下几乎每辆车都有。按 4.3、4.4，格点不再需要按 owner 撤销或重算，
所以改为：

- 只为第 3 节求值集合中的车保留记录；
- 记录只含冲突区与排队区，不含格点。

外层仍是按槽位下标的向量，保持 O(1) 读写；它的长度跟随最高槽位，不随求值集合
缩小。下降的是记录条数和每条记录的堆容量。

## 6. 资源

- 求值集合、`I ∪ D` 重走结果和来源车暂存区放在可复用的派生容量里，计入现有
  retained-logical-bytes 账本；稳态不再分配。
- 「已求值」位图与 `I ∪ D` 位图按格点数和槽位数各一张，与名单一起失效、容量保留。
- 不新增常驻的逐车缓存。逐车记录的堆容量随求值集合下降；按槽位的外层向量长度
  不变。验收报告保留容量，不只报耗时。
- 预留失败的分类不变：申请者、排队、格点各自沿用现有 `AdmissionReserve` 注入点；
  可选暂存区失败时退回全量重建，不新增错误。

## 7. 测试与对拍

参考路径只存在于 `cfg(test)` / `placement-fixtures`：同一已提交状态上强制全量重建
（同样使用 4.3 的平局键），与本文路径逐项比较：

- `best` 每个冲突区的车辆、顺序、rank 与 hop；
- 排队进入者的车辆、顺序与接近距离；
- 所有被读取格点的两个 owner 身份与估计，包括增量刷新之后；
- 生成、拒绝结果和世界状态摘要。

定向夹具至少覆盖：

- 车停在门上、规范化游标停在上一 hop、刚好在一拍可达上界内外各 1 mm；
- 本窗新生成、替换、离开停车、改绑路线后立即成为申请者；
- 槽位被新 generation 复用后，旧句柄不能留在名单里；
- 排队区非成员越过入口；
- 已越过入口的出现项不计入格点；
- 相同估计的多辆车争同一格点，任意插入顺序留下同样两个 owner；
- 复核目标第一次读取自己路线上的格点；
- 生成后已有车的格点值不变；
- 没有证明时窗、没有路权策略、frontier 未发布、世界身份变化、快照恢复后各退回全量；
- 每个预留注入点失败后的错误类别与已提交状态不变。

性能按普通 ABBA（同一计划与输入，A1/B1/B2/A2），比较观察窗公共命令合计与分位数，
并核对四次运行的交通文件（见 4.3）。通过后再进入长窗验收。

## 8. 明确不做

- 不改变准入规则（4.3 的平局键除外）、错误分类或任何公开类型。
- 不在命令路径写 frontier，也不把 frontier 维护挪出 `step`。
- 不为准入另建一套近门集合或反向索引。
- 不扫描全部 live 车来补漏；覆盖不成立就退回全量。
- 不改 #707 的预算，不把短窗数字写成性能认证。

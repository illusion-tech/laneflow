# 准入候选名单复用入口 frontier

**文档状态**: Accepted（#861；三步均已实现）<br>
**最后更新**: 2026-10-10<br>
**适用范围**: `spawn_vehicle` 与 `replace_completed_vehicle` 运动安全准入里的候选名单
（冲突区申请者、排队进入者、格点到达）如何得到

**关联文档**:

- [`traffic-runtime-vehicle-placement.md`](traffic-runtime-vehicle-placement.md)
- [`traffic-runtime-near-gate-frontier.md`](traffic-runtime-near-gate-frontier.md)
- [`traffic-runtime-conflict-occurrence.md`](traffic-runtime-conflict-occurrence.md)
- [`traffic-runtime-waiting-zone.md`](traffic-runtime-waiting-zone.md)

不新开 ADR。公开 API、错误分类、数据格式、快照与 Adapter 都不变。准入规则只有
一处变化：格点 owner 的平局键统一为 `live_order` 序号（第 4.3 节）。除此之外，
同一已提交状态上名单里读到的每个值必须与全量重建相同。取舍以性能优先：能让各条
路径与求值顺序无关、省掉排序和扫描的做法优先。

## 1. 结论

1. 冲突区申请者名单和排队进入者名单，只对「已发布近门集合 ∪ 已发布失效名单 ∪
   本窗生命周期增量」里的车求值，不再对全部 live 车预览。
2. 格点到达改为按格点求值：第一次读取某个格点时，经 frontier 反向索引取得来源车、
   计算到达下界并缓存到名单失效；没有被读取的格点不求值。
3. 任一绑定条件不成立时，本次整份退回现行全量重建。全量重建仍是唯一的兜底路径，
   不是可选开关。
4. 分两步交付：先做申请者与排队进入者（第 3 节），再做格点按需求值（第 4 节）。
   每一步单独对拍、单独做普通 ABBA；前一步没有收益或证明不成立，不做后一步。

## 2. 现状与成本

`ensure_spawn_contenders` 在名单身份（世界世代、观测状态序号）对不上时调用
`rebuild_spawn_contenders`：按 `live_order` 逐辆读状态、做一次运动预览、计算贡献，
再写入三份名单和逐车贡献记录 `owners`。一次 `step` 之后第一次进入运动准入就会
重建；同一命令窗内成功生成后的增量刷新维持名单有效。

十万辆持续 Active、16 workers、512 拍暖机 + 1024 拍观察的插桩分解（#861 评论）：

- 观察窗重建 132 次、合计 10.32 s，平均 78.2 ms，占回收 API 时间约 60%；这些拍
  决定了命令耗时的尾部。
- 逐车约 0.74 µs，其中运动预览 0.23 µs、贡献计算 0.35 µs、写表 0.16 µs，没有单一
  热点。局部提速（#830、#834）没有可重复收益。
- 1319 万次逐车求值中 77.2% 贡献全空；22.8% 有时窗内格点到达；只有 3.4% 这一拍会
  申请冲突区，排队进入几乎为零。

准入真正读取的是：

| 名单                          | 读取方                                                 | 读取范围       |
| ----------------------------- | ------------------------------------------------------ | -------------- |
| 冲突区申请者 `best`           | 前序名次占用重放、共享下游的申请者、车身复核、排队挤占 | 全部冲突区     |
| 排队进入者 `waiting_entrants` | 排队授予、复核                                         | 候选所在排队区 |
| 格点到达 `cell_approach`      | 候选与后车的让行检查、复核目标                         | 只读具体格点   |

所以申请者与排队进入者必须完整，但只来自这一拍够得到门的车；格点到达只需要被
读到的格点。

## 3. 申请者与排队进入者来自近门集合

### 3.1 求值集合

记已发布近门集合为 `N`，已发布失效名单为 `I`，自上次发布以来记下的生命周期增量
为 `D`（`spawn_vehicle`、`replace_completed_vehicle`、`leave_parking`、已提交的
`rebind_parking_route`，以及其他调用 `note_active_source` 的位置）。重建只对
`N ∪ I ∪ D` 中仍然有效、`Active`、路线需要准入的句柄调用现有
`add_spawn_contender`。其余车辆不预览，不写申请者或排队进入者。

第一步交付时格点到达仍对全部车求值，但其余车辆只计算格点贡献，不做运动预览；
第 4 节交付后，其余车辆连格点也不再逐辆求值。

求值顺序按 `live_order` 序号，`ContenderRank` 的 `update_sequence` 仍取该车在
`live_order` 中的序号，与全量重建相同。句柄需要再核对一次：槽位已释放、generation
已变化或已不在 `Active` 的旧句柄跳过。

实现上，重建先按车辆槽位把 `N ∪ I ∪ D` 中仍有效的句柄标进一张可复用位图，再照旧
按 `live_order` 逐辆处理：位图内的车预览并写全部贡献，位图外的车只写格点贡献。
所以格点插入顺序与全量重建相同，第一步不改变任何读到的值。

现行全量重建在预览失败（路线或 profile 缺失、运动非有限）时以 `StopConstraint`
整份放弃名单。位图外的车不再预览，这类失败只会在它真正够到门、进入求值集合时
出现；它够不到门时，预览结果本来就不影响任何名单。

### 3.2 需要证明的覆盖

现行贡献只在下面任一条件成立时写申请者或排队进入者：

- 预览后游标越过某个 Gate hop，或预览后、预览前正好停在该门上（`contender_notes`
  的 `reaches_gate`）；
- 预览后游标越过某个排队区入口 hop（非成员）。

排队区入口 hop 在路线编译时校验为带门的 hop（`tables.rs` 中 `hop_gate` 与入口门
相等），所以两类都属于「这一拍够得到下一道门」。要证明：凡满足上述条件的车都在
`N ∪ I ∪ D` 中。

1. **同一状态。** 近门集合在运动写出下一提交状态之后分类，成功提交时发布；命令
   不能插进一次 `step`。所以两次 `step` 之间，已提交状态中没有被命令改写的车，
   正是分类读取的那份状态。被命令改写过的车都在 `D` 中，或已被移出 `Active`。
   实现前要逐一核对所有改写车辆位置、速度、路线、profile 或状态的命令都记了
   增量或拆除；漏一处即不成立。
2. **到门距离。** 分类用的门距从规范化游标起算（进度与余量为 0 时回到上一 hop），
   已越过的门距离为 0。现行贡献从同一规范化游标 `first_possible` 开始找门。
   两边的「下一道门」是同一处。
3. **一拍可达上界。** 近门判定是 `门距 ≤ v·dt + ½·a·dt² + 2 mm`，`a` 取缓存的
   最大加速度。要证明准入用的预览
   （`preview_active_vehicle_with_waiting_stop`）位移不超过这个上界：预览加速度
   不超过 profile 最大加速度，亚毫米余量小于 2 mm 余量，排队停车只会缩短位移。
   #740 的让行已依赖同一上界；这里在实现时逐条核对预览代码，并用夹具覆盖边界值，
   不只引用 #740。
4. **缓存对不上的车。** 没有有效槽位、句柄 generation 不同、路线或所在边变化、
   进度回退的车，分类时同时进入 `N` 与 `I`，不依赖旧门距。
5. **越过多道门。** 一拍越过第二道门必先越过第一道门，所以只看下一道门不会漏。

实测（不合入的覆盖探针，main `7e4fc6ea`）：十万辆持续 Active、16 workers、512 拍暖机
+ 1024 拍观察，全部 210 次全量重建找到的 5,226,563 条申请者与排队进入者记录都在
`N ∪ I ∪ D` 中，漏判为 0。每次重建的 `N ∪ I ∪ D` 中位数 9,043 辆（p90 9,489，最大
10,188），约为 live 车的 9%；`I` 平均约 86 辆。探针运行的交通文件与未插桩运行逐字节
一致。实测不能替代上面的证明；现有 runtime 测试几乎不走已发布名单，实现时必须补
第 7 节的定向夹具。

### 3.3 什么时候退回全量

以下任一条件成立，本次调用现行全量重建：

- 没有证明时窗（分类不运行，名单不存在），或没有路权策略；
- frontier 未发布、世界身份（`world_id`、`WorldGeneration`）与当前不符，或最近一次
  提交链接失败使名单标记为未发布；
- 快照恢复或修订切换后尚未完成一次成功 `step`；
- 求值集合的暂存区预留失败。

命令路径只读 frontier 的已发布名单、增量与槽位缓存，不写 `FrontierMaintenance`，
不清空增量，也不发布。下一次 `step` 看到的 frontier 与没有这次准入时相同。

## 4. 格点到达按格点求值

### 4.1 第一次读取时求值

格点到达的读取方是候选与后车的让行检查、复核目标收集，以及对每个复核目标重做的
运动比较（`reject_existing_hard_stop` → `placement_motion` → `admission_stop`，读的是
目标车自己路线上的让行格点）。读取地址只有在走到那一步时才完整，不另做一遍收集。

名单旁加一张「已求值」位图和一张已求值格点表。读取时位图未置位，就按 4.2 求值、
记入表中并置位；已置位直接读。读取方持有只读借用（`StepReadView`），因此这两张表
放在互斥锁里：命令路径单线程，锁从不争用，只是因为读视图要能跨线程共享。读视图
新增一个只在命令路径上存在的 frontier 引用，步进内部的读视图不带它，也不读名单
格点。实测十万辆短窗里一份名单从建好到失效平均只读到约 14 个不同格点（p90 35），
表按下标线性查找。表在第一次进入按需模式时才分配，空世界不占堆。

因为 4.3 的归约与插入顺序无关，格点在哪一次准入、被谁先读到，都不影响它的值。

### 4.2 一个格点的来源车

对地址 `c`，来源车是：

- 求值集合（第 3 节的 `N ∪ I ∪ D`）里的车：第一步已在重建时为它们预览并写全部
  贡献（含格点），读取时直接用，不重走；
- frontier 反向索引 `by_cell[c]` 中、不在求值集合的车：剩余距离 = 缓存距离 −
  同一条边上的进度差。句柄已过期、车已完成或停车的不计（全量重建同样不计）；
  Active 车的槽位缓存与当前路线、边或进度对不上时，前提不成立，这次读取按不可
  证明处理，不猜。

求值集合外的车没有经历生命周期变化，状态只随 `step` 改变；步进之外改变车辆状态的
命令都登记生命周期增量，使这辆车进入 `D`。这是 3.2 节已经依赖的前提，按需求值不
新增前提。

证明时窗与 frontier 相同，都取自策略绑定的 `horizon()`。缓存的出现项本身就限于
时窗内；更远的出现项因加速进入时窗时，分类已把这辆车放进 `I`。

每辆来源车的到达下界用现行 `PreparedApproachEta` 与 `PreparedSignalApproach`
计算，和 `contender_notes` 完全相同。需要证明或在实现中处理：

- 进度差超过缓存距离（本拍已越过该入口）时，现行贡献不再记这处出现项；按需
  求值必须同样排除，不能饱和成 0；
- 证明时窗外的出现项不记；
- 同一车辆在同一格点有多次出现时，先做车辆内归约，再参与格点归约。

### 4.3 归约与平局

格点只保留两个不同 owner，按 `(估计类别, 毫秒, update_sequence)` 排序。现行代码里
只有申请者与排队进入者的 `update_sequence` 是 `live_order` 序号，其余车以 0 写入，
估计相同时留下谁取决于插入顺序；增量刷新按槽位顺序重新归约，全量重建按
`live_order` 插入，两者在平局时可能留下不同的车，而复核目标读取的正是 owner 身份。

改为：所有 owner 的 `update_sequence` 都取该车在 `live_order` 中的序号。键成为全序，
「取最小的两个不同车辆」与插入顺序无关，于是：

- 全量重建、按需求值、增量刷新在同一已提交状态上得到相同的两个 owner；
- 按需求值不用按 `live_order` 排序来源车，可以直接按反向索引顺序处理；
- 增量刷新不再为了重新归约按槽位扫描全部逐车记录。

格点读出的估计值不变；变的只是估计相同时留下哪辆车，进而可能改变复核目标集合。
这是本文唯一的规则变化。验收时比较交通文件：逐字节一致就直接记录；不一致必须
定位到平局差异并在结果记录中说明，不能当成性能噪声。

序号取自 `LiveOrderIndex`；它对不上当前 live 前缀且准备失败时，退回全量重建。

### 4.4 生成成功之后

新车进入 `D`，它的出现项立即重走，并插入已求值的格点；未求值格点以后求值时自然
包含它。

已有车在同一命令窗内的格点贡献不随别的车生成而变：到达下界只取决于该车自己的
位置、速度、余量、最大加速度、证明时窗和信号放行下界，而生成不预写通行权、不改
信号、不改别的车的状态。实现时要逐项核对这一点。成立时，受影响旧车的刷新只撤销
并重算申请者与排队进入者，不触碰格点。

刷新仍按现行方式撤销并重算受影响的求值集合内车辆；新车写全部贡献后标进求值集合
位图，按需读格点时不再从 frontier 并入它的旧槽位。被重新归约的格点清掉已求值标记，
下次读取重新并入；其余已求值格点不受影响。`note_inserted_vehicle` 用「名单里是否
已有申请者或格点 owner」决定能否跳过刷新；按需模式下未求值格点可能有 owner，按
「有」处理，多做一次刷新但不会漏。生成追加到 live 序尾时同时补齐 live 序号表。

### 4.5 复核目标的路线索引

复核目标里有一类是「出现在某个冲突区申请者名单里、整条路线经过新车车身所在边的
车」。逐个冲突区扫描名单再逐条比对路线，十万辆短窗里每次准入平均遍历约 3 万条、
判定约 3,700 辆，最后只找到约 1 辆，占公共命令约 27%。改为两级索引直接查：

- 边 → 路线：按已注册路线建的压缩稀疏行，计数排序构建，查询是一段连续数组。注册与
  删除路线时直接作废，下次查询重建；删除后同一世代里另一条路线可能复用同一槽位，
  路线数和槽位表长度都不变，所以不能只看计数。另以 (世界世代, 已注册路线数, 槽位
  表长度) 兜底，世界切换换表时同样重建。重建按摊还推迟：作废后复核先逐区扫描并累计
  检查过的名单条目数，累计到不少于路线经过边的总次数（一次重建的代价）才重建，所以
  边注册路线边生成车辆不会每次整表重建，总代价不超过只扫描或每次都重建两者中较小者
  的两倍左右。偏移是 `u32`，总次数放不下时不建表，一直逐区扫描；
- 路线 → 申请者：按车辆槽位的侵入式双向链表，表头按路线槽位存放。只链入冲突区列表
  非空的逐车记录，写入与撤销记录时 O(1) 维护，名单重建时清空表头。

链表为空时没有申请者能成为车身复核目标，直接跳过，不查也不建「边 → 路线」。
查询从车身所在的一两条边出发，取出经过它们的路线上的申请者，跳过过期句柄，再按
它们在逐区扫描里第一次出现的位置（冲突区编号, 名单内位置）排序。复核按顺序逐个
检查，拒绝原因写出第一个被逼停的车，所以顺序必须与逐区扫描相同。找到的车通常只有
一辆，排序键现查。

两张表放在第一次重建名单时才分配的盒子里；预留失败（沿用 `RecheckScratch` 注入点）
时这份名单退回逐区扫描，结果相同。测试与夹具构建里每次走索引都再做一次逐区扫描并
断言目标序列逐项相同。不改规则。

## 5. 逐车贡献记录

`owners` 现在为每辆求值过的车各保留一条记录，记下它贡献的冲突区、格点和排队区，
十万辆持续场景下几乎每辆车都有。按 4.3、4.4，格点不再需要按 owner 撤销或重算，
所以改为：

- 只为第 3 节求值集合中的车保留记录；
- 记录仍含格点，生成刷新撤销与重新归约要用到；只覆盖求值集合，条数随之下降。

记录里的序号统一为 live 序号（4.3）。没有记录的车，复核目标配对和跟车比较读到的
序号改由占用索引查出，同样是 live 序号；此前只贡献格点的车记录里是 0。这属于 4.3
的同一项统一。

外层仍是按槽位下标的向量，保持 O(1) 读写；它的长度跟随最高槽位，不随求值集合
缩小。下降的是记录条数和每条记录的堆容量。

## 6. 资源

- 求值集合位图（按槽位）、「已求值」位图（按格点）和已求值格点表放在可复用的
  派生容量里，计入现有 retained-logical-bytes 账本；稳态不再分配。
- 已求值格点表与位图放在第一次进入按需模式时才分配的盒子里，空世界不占堆。
- 不新增常驻的逐车缓存。逐车记录的堆容量随求值集合下降；按槽位的外层向量长度
  不变。验收报告保留容量，不只报耗时。
- 预留失败的分类不变：申请者、排队、格点各自沿用现有 `AdmissionReserve` 注入点；
  可选位图失败（`ReachMask` 注入点，两步共用）时退回逐辆写格点，不新增错误。缓存
  一个已求值格点失败时这次结果照用，下次读取重算。

## 7. 测试与对拍

参考路径只存在于 `cfg(test)` / `placement-fixtures`：同一已提交状态上强制全量重建
（同样使用 4.3 的平局键），与本文路径逐项比较：

- `best` 每个冲突区的车辆、顺序、rank 与 hop；
- 排队进入者的车辆、顺序与接近距离；
- 所有被读取格点的两个 owner 身份与估计，包括增量刷新之后；
- 生成、拒绝结果和世界状态摘要。

定向夹具至少覆盖：

- 车停在门上、规范化游标停在上一 hop、刚好在一拍可达上界内外各 1 mm；
- 本窗新生成、替换、离开停车、改绑路线后立即成为申请者；
- 槽位被新 generation 复用后，旧句柄不能留在名单里；
- 排队区非成员越过入口；
- 已越过入口的出现项不计入格点；
- 相同估计的多辆车争同一格点，任意插入顺序留下同样两个 owner；
- 复核目标第一次读取自己路线上的格点；
- 生成后已有车的格点值不变；
- 没有证明时窗、没有路权策略、frontier 未发布、世界身份变化、快照恢复后各退回全量；
- 每个预留注入点失败后的错误类别与已提交状态不变。

性能按普通 ABBA（同一计划与输入，A1/B1/B2/A2），比较观察窗公共命令合计与分位数，
并核对四次运行的交通文件（见 4.3）。通过后再进入长窗验收。

## 8. 明确不做

- 不改变准入规则（4.3 的平局键除外）、错误分类或任何公开类型。
- 不在命令路径写 frontier，也不把 frontier 维护挪出 `step`。
- 不为准入另建一套近门集合或反向索引。
- 不扫描全部 live 车来补漏；覆盖不成立就退回全量。
- 不改 #707 的预算，不把短窗数字写成性能认证。

## 9. 第三步：近门车按路线按需求值

### 9.1 依据

前两步之后，十万辆短窗（512 拍暖机 + 1024 拍观察，16 workers，main `cbacab00`）的分阶段
计时探针（不合入）显示，观察窗公共命令里：

- 名单重建对求值集合逐辆处理占约 57%：每次重建约 8,810 辆，平均 23.8 ms，共 132 次。
  其中近门且缓存有效的车（在 `N`、不在 `I ∪ D`）约 8,770 辆，`I ∪ D` 约 40 辆；
- 命令 p99 约 45 ms 的拍基本就是重建拍。

同一状态上的计数探针（不合入，交通文件与未插桩运行逐字节一致）统计了两次重建之间
名单实际被读的范围：

| 读取                                      | 平均每段 | 中位数 | 最大  |
| ----------------------------------------- | -------: | -----: | ----: |
| 按冲突区读申请者名单（不同冲突区数）      |      2.8 |      0 |    66 |
| 其中读到的名单条目                        |      2.1 |      0 |    99 |
| 排队进入者名单                            |        0 |      0 |     0 |
| 遍历全部名单的读取                        |        0 |      0 |     0 |
| 车身复核经过的路线（不同路线数）          |      235 |     80 | 3,113 |
| 车身复核找到的申请者                      |       35 |     13 |   486 |

重建写出约 2.5 万个非空冲突区、2.8 万条申请者，被读到的极少。第三步把 `N \ (I ∪ D)`
中的车也改为读到时才求值，求值单位是路线。

### 9.2 求值集合拆分

重建时：

- `E = (I ∪ D)` 中仍有效的 Active 车照旧立即求值（预览、写全部贡献、标进
  `reach_mask`）。这些车的槽位缓存不可用，只能这样做；
- `P = N \ E` 中的车不求值，按路线槽位做一次计数排序，得到「路线 → 待求值车」的
  压缩稀疏行。代价是 O(路线槽位数 + |P|)，不预览、不读路线表。

`P` 中的车满足 frontier 分类的 `remembered` 条件：槽位有效、generation 与路线相同、
在同一条边上、进度未回退，且第一处被截掉的出现项在证明时窗可达距离之外（否则已进
`I`）。这正是第 4 节格点按需求值对「求值集合外的车」依赖的条件；而 `P` 不在 `D`，
重建以来状态只随 `step` 改变。所以 `P` 的格点贡献照样经 `by_cell` 并入，不需要先
求值。

### 9.3 物化一条路线

「物化路线 r」：对 `P` 中在 r 上、还没有逐车记录的车，按 live 序号调用现行
`add_spawn_contender(…, may_reach = true)`，写全部贡献（冲突区、排队区、格点、逐车
记录、路线申请者链表），并把它标进 `reach_mask`；然后标记 r 已物化。

正确性：

1. **单车贡献与名单无关。** `contender_notes` 只读这辆车自己的状态、路线表、策略、
   信号与已提交世界（预览读前车），不读任何名单。所以一辆车在什么时候、按什么顺序
   求值，写出的贡献都相同。前提是它求值时的已提交状态与全量重建所用的相同。物化
   发生在两次重建之间的某次准入里，此时世界可能已因本窗生成而改变；全量参考同样
   取「当前已提交状态上的全量重建」（第 7 节对拍在增量刷新之后进行），所以物化
   时读当前状态，与参考一致。
2. **插入与顺序无关。** 申请者名单按 `ContenderRank` 插入，名次以唯一的 live 序号
   收尾，是全序；排队进入者按 `(接近距离, live 序号)` 插入；格点按 4.3 归约，同一辆
   车重复并入按车辆去重。所以部分物化后再补齐，与一次全量写入得到的表逐项相同。
3. **冲突区只来自自己的路线。** 车 v 的申请者条目只写进它路线上 `admission_hop`
   为所到门的冲突区。所以冲突区 z 的完整名单 = `E` 中的贡献 ∪ 经过 z 的各条路线上
   `P` 车的贡献。物化经过 z 的全部路线后，z 的名单完整。
4. **格点不重复。** 物化时写入的格点贡献进入 `cell_approach`，同时置 `reach_mask`
   位，之后的 `by_cell` 并入跳过它；已经缓存的格点值早已经 `by_cell` 并入过这辆车，
   估计相同，不需要失效。
5. **复核顺序。** 车身复核按 (冲突区编号, 名单内位置) 排序。同一冲突区里名单按全序
   名次排列，部分物化不改变已在表中各车的相对次序，所以排序结果与完整名单相同。

### 9.4 读取方怎样触发物化

| 读取                                              | 上下文     | 物化范围                     |
| ------------------------------------------------- | ---------- | ---------------------------- |
| 复核按冲突区收集（`push_zone_contenders`）        | 可变       | 经过该冲突区的路线           |
| 车身复核（路线索引）                              | 可变       | 经过车身所在边的路线         |
| 让行挤占检查（`incoming_hard_stop` 读某冲突区）   | 只读       | 经过该冲突区的路线           |
| 排队授予、复核排队进入者                          | 只读或可变 | 全部                         |
| 前序名次占用重放、共享下游申请者、逐区扫描退路    | 只读或可变 | 全部                         |
| 生成后刷新（受影响者、撤销）                      | 可变       | 不物化，只处理已物化的车     |

**可变上下文**直接物化后读取。

**只读上下文**（`StepReadView` 上的运动比较）不能写名单。读到未物化的冲突区时，
记下缺口并按空名单继续，调用方在只读计算返回后检查缺口：有缺口就丢弃这次结果、
物化、重新执行。只读计算没有可见副作用（格点缓存只是记忆化），重新执行得到的就是
「名单完整时」的结果。同一次调用第二次缺口直接物化全部，重试次数上界为 2。缺口
记录放在名单旁已有的延迟分配盒子里，用锁保护，理由同 4.1。

**刷新不物化。** 生成后的受影响者只可能是已物化的车：未物化的车以后求值时直接读
当前状态，本来就包含新车的影响。撤销与 `members_in_zones` 只遍历已在表中的条目。
`cache_has_contender` 在还有未物化路线时按「有」处理，与 4.4 相同。

**「经过冲突区 z 的路线」** 用与 4.5 「边 → 路线」相同方式维护的「冲突区 → 路线」
压缩稀疏行：大小为已注册路线的冲突出现总次数，注册与删除路线时作废。未就绪时该次
读取物化全部，并把这次求值的车数记作欠账；欠账不少于已注册路线数（一次求值大致走
过一条路线的冲突出现，重建要走遍全部路线）时才重建。`u32` 偏移放不下时不建表，
一直物化全部。车身复核在「边 → 路线」未就绪时同样物化全部，求值的车数乘以每条路线
平均经过的边数计入 4.5 节的扫描欠账。

名单作废时延后状态一并清除，作废的名单不再物化。

实测：十万辆短窗观察窗里只读路径从未出现缺口。复核阶段（可变上下文）先物化了候选
所在冲突区和车身所在边的路线，之后的只读运动比较读到的都已完整。只读重算由定向
测试覆盖。

**车身复核的短路**（链表为空时跳过）改为：链表为空且没有待物化的车。

### 9.5 失败

物化中的预留失败与预览失败沿用现行分类（`OccupancyAlloc`、`StopConstraint`），
在触发物化的那次准入中返回，并把名单整份作废（与现有刷新失败相同）。延后工作区的
预留失败（新注入点 `AdmissionReserve::Deferred`）时这份名单照常立即求值，不报错。

与全量重建的差别：全量重建在重建时遇到任一车预览失败即整份放弃，这次准入被拒；
按路线物化时，从未被读到的路线上的这类车不会使准入失败。预览只会因路线或 profile
缺失、运动非有限而失败，都是已提交状态自身违反不变量的情形；第 3 节对求值集合外
的车已经接受了同样的差别。

### 9.6 重建时清表

物化之后名单大多为空，重建清 11.56 万个冲突区列表与全部格点的固定代价（约 2.7 ms，
占公共命令约 6%）变得显著。改为记下本份名单里由空变非空的冲突区、排队区与格点
下标，重建时只把这些表项恢复为空（名单缓冲区照旧释放），表的尺寸变了或记录不完整
时整表清理。记录预留失败时本份名单标为不完整。三张表的预留注入点在两条路径上相同。

### 9.7 资源

- 「路线 → 待求值车」：路线槽位数 + 1 个 `u32` 偏移与 |P| 个 `u32`，每次重建复用。
- 「冲突区 → 路线」：冲突区数 + 1 个 `u32` 偏移与路线冲突出现总次数个 `u32`，随路线
  注册表变化按摊还重建。
- 「路线已物化」位图、缺口记录、脏下标表：随路线数、冲突区数与本份名单写入量增长，
  容量复用。
- 都放在现有延迟分配的工作区盒子里，计入 retained-logical-bytes 账本，空世界不占堆。

### 9.8 测试与对拍

实际交付的验证：

- 名单指纹（`contender_fingerprint_for_test`）先物化全部再输出；规模夹具上延后求值
  的名单与全量重建逐项相同，含格点。
- 同一命令窗口里反复生成再腾出槽位，与注入 `Deferred` 立即求值的同一世界逐次比较
  生成结果与名单，并断言生成过程中确有延后的车被物化。
- 只读计算读单个冲突区与读全部冲突区各有一个定向测试：直接读得不到延后的车，经
  缺口重算后读到完整名单。
- `冲突区 → 路线` 偏移超限、作废后欠账未够时退回物化全部；物化中预留失败作废名单。
- 测试与夹具构建里每次只清写过的表项后断言三张表全空。
- 现有对拍、证明覆盖与全部生成类测试保持通过。
- 十万辆短窗交通文件与 main 逐字节一致；之后普通 ABBA，再按 #861 进入长窗验收。

设计时设想的「每次物化后与全量重建逐冲突区比较」没有做成运行时断言：测试构建里
在物化点另建一份全量名单代价过高，改由上面的整表对拍与生成对拍覆盖。

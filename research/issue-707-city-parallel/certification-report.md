# #707 首版单世界并行：城市性能与资源认证报告

**日期**：2026-10-18；Refs #707。

## 1. 结论

在研究机器上，合入 #970 / #971 后的 main `10c625ae` 以 16 worker 运行。四种城市负载的
Core（`TrafficWorld::step`）p95 按同条件三轮中位数全部在产品预算内：

| 负载                  | Core p95 三轮中位数 | 预算  | 余量    |
| --------------------- | ------------------- | ----- | ------- |
| 稳定 Active 10k       | 1.60 ms             | 2 ms  | 0.40 ms |
| 活动衰减（MIXED）10k  | 1.31 ms             | 2 ms  | 0.69 ms |
| 稳定 Active 100k      | 14.89 ms            | 16 ms | 1.11 ms |
| 活动衰减（MIXED）100k | 9.22 ms             | 16 ms | 6.78 ms |

- **能否达标取决于 worker 数。** 8 worker 时稳定 Active 100k 为 19.94 ms，超出预算；稳定
  Active 10k 为 1.97 ms，只差 0.03 ms 就超线。所以本认证只覆盖 16 worker。
- **并行收益。** 单 worker（P1）到 16 worker（Pp），Core p95 在 100k 上降低 5.0–6.0 倍，
  在 10k 上降低 1.8–2.8 倍。
- **串行与资源。** 证据构建下，协调线程串行时间占拍内阶段墙钟的 32–42%。最大的串行
  热点是 Conflict 准备。100k 的 Runtime 资源账合计约 410–413 MiB（含共享静态根，
  不含线程栈）。
- **R0 / R1 未测，原因见第 4 节。** 因此算法收益（R0/R1）和架构开销（P1/R1）没有结论；
  本报告只给出 P1/Pp 的并行收益。

**证据尚未归档。** 第 9 节所列证据目前只在采集机上，在 #975 归档并补齐下载索引之前，
不能从仓库或制品独立复核本报告的数字。

**这不是 #707 的整体结论。** 首版功能已经交付；性能认证只在本机硬件角色、16 worker
的条件下成立。几项资源维度仍未测（第 7 节）。

## 4. 四基线（验收标准 1）

### 4.1 P1 / Pp：worker 扫描

扫描沿用第 2 节的二进制、计划与输入，只改 `--workers`。1 / 2 / 4 / 8 worker 各跑一轮，
16 worker 取第 3 节的三轮中位数。

- **运行状态。** 16 臂全部 `performance-round-complete`，交流供电，厂商模式 2/2。
- **结果与 worker 数无关。** 每种负载的最终检查点与事件摘要，在全部 worker 数下都与
  16 worker 认证逐项相同。

Core 观察窗口 p50 / p95 / p99 / max，单位 ms：

| 负载             | 1 worker（P1）              | 2                           | 4                          | 8                          | 16（Pp）                   |
| ---------------- | --------------------------- | --------------------------- | -------------------------- | -------------------------- | -------------------------- |
| 稳定 Active 10k  | 3.83 / 4.51 / 5.05 / 8.12   | 3.46 / 4.19 / 4.63 / 6.83   | 1.75 / 2.35 / 2.67 / 3.47  | 1.46 / 1.97 / 2.20 / 3.16  | 1.34 / 1.60 / 1.72 / 7.57  |
| 活动衰减 10k     | 2.13 / 2.41 / 2.62 / 4.76   | 1.83 / 2.40 / 2.75 / 4.00   | 1.10 / 1.53 / 1.77 / 2.72  | 0.95 / 1.35 / 1.53 / 2.12  | 1.01 / 1.31 / 1.63 / 3.81  |
| 稳定 Active 100k | 84.27 / 89.39 / 91.72 / 122 | 67.06 / 71.21 / 73.32 / 177 | 28.40 / 29.92 / 30.65 / 40 | 18.66 / 19.94 / 20.50 / 26 | 13.55 / 14.89 / 15.66 / 23 |
| 活动衰减 100k    | 43.18 / 46.52 / 48.17 / 62  | 34.28 / 36.70 / 38.00 / 44  | 15.86 / 17.09 / 17.66 / 21 | 11.28 / 12.36 / 12.83 / 16 | 8.13 / 9.22 / 9.85 / 15    |

P1 → Pp 的 Core p95 并行收益：稳定 Active 10k 2.83 倍，活动衰减 10k 1.83 倍，稳定
Active 100k 6.01 倍，活动衰减 100k 5.05 倍。

- **P1 只跑一轮，Pp 是三轮中位数。** 按同口径（P1 单轮对 16 worker 第一轮）的比值为
  2.84 / 1.96 / 6.16 / 5.23 倍，结论不变。
- **不确定性。** 本机同代码不同时段的 p95 差异约 0.3–0.6 ms：对 100k 不到 1%；对 10k
  会让比值有约 ±0.3（稳定 Active）到 ±0.5（活动衰减）的浮动。“16 worker 明显快于
  1 worker，但 10k 的收益远小于 100k”这一结论不受影响。
- **预算判定只用 Pp。** 预算判定（第 3 节）只依赖三轮的 Pp，不依赖 P1 的精确值。

- **2 worker 收益有限。** 10k 几乎没有收益（稳定 Active 4.51 → 4.19，活动衰减 2.41 →
  2.40）。100k 降约 20%（89.39 → 71.21，46.52 → 36.70），远小于 4 worker 的降幅。原因是
  协调器分段并行（占用重建、前沿、Conflict 发现等）要求池线程不少于 4 个，2 worker 时
  只有 P2 / P3 / P5 的独立计算分发。
- **10k 从 8 到 16 worker 收益很小**（p95 1.97 → 1.60，活动衰减 1.35 → 1.31）。每拍约
  23 次分发的固定成本和协调线程串行段在 10k 上占比高，见第 5 节。
- **满足预算所需的最少 worker 数。** 10k 为 8（稳定 Active 8 worker 只余 0.03 ms，实际
  按 16 计）。100k 为 16。

### 4.2 R0 / R1：未测

- **R0（历史串行）。** 构建窗口已过；当时城市 harness 不存在；结果载荷版本低于现行
  `compare` 可接受的版本，跨版本比较被拒绝。
- **R1（局部算法优化后、并行组织前）。** 新并行架构首个提交 `55b619d9` 的父提交跑不了
  现行冻结输入，原因有三：
  - 当时还没有稳定 Active 负载；
  - 路网其后改为多车道；
  - Runtime 其后有一次破坏性语义修复。

  即使把现行负载移植过去，交通语义不同，整步不可比。提交历史里也没有独立的“局部算法
  优化”切片。
- **影响。** R0/R1 的算法收益和 P1/R1 的架构开销没有实测结论，只报告 P1/Pp 的并行收益。
  这与[实验计划](experiment-plan.md)和 [`baseline-manifest.toml`](baseline-manifest.toml)
  中此前登记的状态一致。

## 5. 调度与串行（验收标准 4）

### 5.1 证据入口与运行

- **证据构建。** 用 Runtime 证据构建 feature `execution-evidence`（#972 / #973，main
  `ff113a1c`）构建 harness，二进制 SHA-256 `664c96ad78d7b7e2de0997acfa9bd03a276e85a6b34e6ffc3700692f2ade7397`。
  计划、输入与协议同第 2 节，16 worker，每种负载一轮。
- **只覆盖观察窗口。** 预热结束时清零账本，所以证据只覆盖观察窗口。
- **非正式段运行。** 证据构建不是 `build-measurement` 产物，harness 拒绝把它当作正式性能
  运行，因此停在计划末拍的前一拍，作为非正式段运行。证据少计观察窗最后一拍。
- **与正常 release 延迟分开。** 插桩构建的整步 p95 为 1.62 / 1.51 / 14.37 / 10.53 ms，
  与第 3 节正常 release 相近，但不作为认证计时。#973 的 3,000 拍对照中，证据构建与默认
  构建的事件、命令与逐拍文件逐字节一致。

### 5.2 拍内阶段（µs / 拍，观察窗口均值）

记号：

- **串行**：阶段墙钟减去阶段内分发墙钟，即协调线程上的时间。
- **关键路径**：每次分发中，单个线程块时间之和的最大者。
- **等待**：分发墙钟减去关键路径，即屏障、调度与不均衡等待。
- **最长单块**：观察窗口内该阶段单个块的最长计算时间（µs），是尾部值，含操作系统
  调度抢占的影响；不按拍平均。
- **并发**：块计算时间除以分发墙钟。

  缓冲，不含栈）在 100k 约 410–413 MiB。第 3 节的整进程工作集还包括 harness 的观测、
  日志和映射。按 Runtime 计账口径，世界绑定只含来源引用与策略选择；
  共享的路网修订另列为共享静态根。

## 8. 热点与后续

各项按影响排序：

1. **Conflict 准备的串行段是最大热点。** 稳定 Active 10k 为 0.25 ms，100k 为 2.04 ms，
   占协调线程串行时间的 44–45%。
2. **10k 的分发固定成本与等待。** 每拍约 23 次分发，等待约 0.23 ms，与稳定 Active 10k
   的 0.40 ms 余量同量级。8 → 16 worker 只降 0.37 ms。可以考虑两个方向：合并相邻分发段，
   或按工作量减少参与线程。
3. **100k 的其他串行段。** 提交 0.58 ms、Conflict 收尾 0.47 ms、Frontier 分类
   0.38 ms、Waiting 收尾 0.30 ms，合计约 1.7 ms。
4. **余量与运行间差异。** 稳定 Active 10k 的余量（0.40 ms）与本机同代码不同时段 p95 的
   差异（0.3–0.6 ms）同量级；稳定 Active 100k 余量 1.11 ms。在其他时段或其他机器上可能
   擦线，需要继续压缩上面三项。
5. **活动衰减 100k 的工作区增长**（窗口内 +12.5 MiB）原因未查，需要确认是否单调。
6. **未测与部分项要单独立项。** 切换场景（候选 / 退休计划、静默窗口）、线程栈实际字节、
   scratch 与队列的连续高水位、P4 单独计时，都需要新的入口。

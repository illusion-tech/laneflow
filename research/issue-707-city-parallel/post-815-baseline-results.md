## 执行与负载结果

按一万 w1、一万 w16、十万 w1、十万 w16 顺序串行执行。各自为全新进程，0 暖机、
256 个观察拍。一万步长 16 ms，共 4.096 秒仿真；十万步长 33 ms，共 8.448 秒仿真。
两档的 `compare` 均为 `probe-match`；逐拍、命令、事件和展开计划的文件摘要分别相同。

一万两臂的 step 前后 Active 全窗均为 10000，尚无 Completed 或回收，不能据此
证明一万规模的长期回收能力。

十万两臂的负载统计完全相同：

- 第 207 拍首次出现 step 后 Active 低于 100000。
- step 前 Active 最小 98822，46/256 拍低于目标；step 后最小 98523，48/256 拍低于目标。
- 第 256 拍为 Active 98822、Parked 0、Completed 1178，pending 为 1178，exhausted 为 0。
- 共 3445 个回收请求、6331 次尝试；2267 次成功，出生与移除各 2267，窗口末 1178 个
  请求仍待准入。所有已记录 tick 满足 `live = Active + Parked + Completed = 100000`。
- 按请求编号核对了重试身份、原始到期边界、递增 attempt、8 tick 间隔和成功终态，均通过。
  这里验证的是本次有限轨迹，不能替代完整资源或失败原子性认证。

## 回收阻塞的证据

拒绝原因为 `entry-blocked` 4062 次、`unsafe-follower` 2 次。3647 次拒绝的阻塞者是
已经回收成功的车辆。窗口末 pending 请求分布在 1038 条入口车道，单入口最多 3 个。

当前控制器按 `(slot + incarnation * 37) mod 路线数` 固定下一路线，位置为其第一个
路段的 7000 mm，静止起步；拒绝后沿用同一路线与位置，每 8 tick 重试。
入口被已有车辆占用时，Runtime 拒绝替换，原个体保持 Completed，所以 Active 下降。
上述有限轨迹没有出现请求丢失、耗尽退出或 worker 之间的语义分歧。

证据支持“当前回收入口准入能力不足以维持这个负载窗口”。尚未证明仅调整路线分布、
候选位置或重试节奏中的任何一项就能恢复目标；本轮未更改这些输入，也未放宽安全拒绝。

## 收口与下一步

预定的十万 512 暖机 + 4096 观察拍计划已生成，但 8→16→16→8 四进程矩阵未启动。
这是负载前置门槛失败后的停止，不是性能矩阵通过。#707 的正式验收保持未完成。

下一切片应先冻结持续负载输入的准入方案：量化每个入口的回收需求与可准入位置，
评估按入口车道均衡的路线选择和合法候选位置，所有准入仍经过现有 Runtime 安全检查。
在短窗和覆盖回收阶段的窗口里验证 step 前实际 Active，再决定是否扩大测量。
若只能支持带波动的稳定负载，必须先明确实际下限与统计口径，不能直接改名为持续十万。

只有负载口径成立后，才继续四进程诊断矩阵和正式取证协议。当前 `SUSTAINED-ACTIVE`
只接受 probe；#707 的三轮完整窗口、R0/R1/P1/Pp 分解、五档扩展性及资源账本仍是
保留义务。十万预算仍为 33 ms 仿真步长下 Runtime 整步 p95 不高于 16 ms。

测量导出修改的验证：13 项报告测试、严格 Clippy、格式与 diff 检查通过；四次真实
运行的新增样本及分位值均由独立审计重算核对。证据脚本留在仓库外，不作为仓库工具引入。

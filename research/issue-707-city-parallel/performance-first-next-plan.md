## 1. 决策依据与评估修正

4 workers、tick 65–512、开启诊断时，Core 均值 71.358ms，Conflict 准备
31.928ms，其中 frontier 重建 18.764ms、P3 消费 4.996ms、P4 约 1.001ms。
Waiting 准备和 Motion 已分别获得约 2.6 倍阶段加速。下一轮主线应减少工作与
改变信息表示；P4 并行和继续增加现有 worker 数不是首选。

源码核对给评估增加以下限定：

- 冻结源码的 [`artifacts.rs`](../../tools/laneflow-urban-harness/src/artifacts.rs) 强制原城市
  gap profile 的 lead 为 `5500 + dt`、lag 为 `2500`。当前 dt=33ms，lead=5533ms，
  [`policy.rs`](../../crates/laneflow-runtime/src/kernel/policy.rs) 推导 proof horizon=5534ms。
  因而“将全局最大时窗换成各路口局部时窗”在原单 profile 夹具中没有时窗差异可利用；
  主动缩短它属于行为变更，必须另设实验，不能作为免费收益。
- [`PreparedApproachEta`](../../crates/laneflow-runtime/src/kernel/conflict.rs) 已在
  开平方前执行可达距离筛除。替换精确 ETA 的潜在收益取决于实际进入有限 ETA
  求解的数量，不能假定所有出现项都付出了同样成本。
- frontier 的 18.764ms 是重建函数的整体墙钟；不含调用前清理，也没有分别量出
  路线定位、距离查询、ETA 和 owner 归约。不能把这整个数字归因于定向舍入。
- 每个 frontier cell 保留两个不同 owner，插入时至多整理三个候选；没有证据
  证明这里存在随车辆数增长的 owner 列表或平方复杂度。重要成本可能是每拍重复
  扫描及求解的总量。
- P3 确有 cells/claims 向 work 与 candidate 的重复物化，但整个消费阶段约 5ms
  还包含其他工作；去掉复制不等于省下全部 5ms。

只作均值算术：frontier 全免费仍剩 52.594ms，理想四倍加速仍剩 57.285ms，
整个 Conflict 准备全免费仍剩 39.430ms。这些不是性能预测或算法下限；说明
33ms 和 16ms 都需要 Conflict 之外的降本。preflight、Conflict finalize、
Waiting outputs 合计均值 16.215ms，也应进入后续工作集维护研究。

## 3. 主线原型：入口队列、局部许可与多频更新

F3 是主要的模型变化方向：把“所有相关车辆每拍证明未来到达”改成入口附近
队列参与局部通行决策。入口队列、许可和错峰更新可在同一最小原型中组合，
以相同原型的单频配置作消融参照；不把单频版本通过旧测试作为多频实验前提。

1. **入口队列**：从真实路线和入口关系维护每个入口前 K 个候选，K=2/4/8
   作为筛查参数；同一车道的不同转向、连续近邻路口和队尾追近须有覆盖。K
   不先验保证足够，以漏判、吞吐和排队结果决定是否保留。
2. **局部许可**：利用静态 movement 冲突关系及下游容量发放许可。非冲突
   movement 可以同时通过；同一 movement 多车占用须按 owner/计数跟踪，
   车头离开不能提前释放仍被车尾占据的资源。避免只用一个易误清除的布尔位。
3. **增量维护**：队首变化、路线或信号变化、车辆接近入口、替换/离场触发更新。
   只缓存两个最早 owner 不足以支持任意删除，第二名删除后还需知道新的后继。
   缓存失效、generation、修订切换与资源释放需要明确处理。
4. **多频决策**：直接比较 33/99/198ms 决策间隔。运动和
   必要的近距离纠正仍每拍运行；按路口错峰，并允许关键事件唤醒，避免每第六拍
   全部重算。观测反应延迟、纠正次数及尾部耗时，而不只看平均节省。

区分决策间隔与仿真步长有现成实践：[SUMO 的 actionStepLength 文档](https://sumo.dlr.de/userdoc/Car-Following-Models/)
说明二者可以分开，并会影响反应与计算成本。它只支持这个实验方向，不证明
LaneFlow 使用相同间隔后满足所需行为或性能。

随后评估 preflight、Conflict finalize、Waiting outputs 的变更集合更新，
记录每拍真正变化的对象数和额外维护成本。允许把昂贵全量检查移到构造/命令
边界、诊断构建或抽样检查，并通过有意构造的失败场景验证新处理方式。检查位置
改变需要记录，但无需保留每拍旧首错；高变更率下同时比较增量维护与批量重建。

frontier 的分块局部 top-2 再合并（F1b）保留为过渡候选，仅在 F0/F2 表明仍
有大量值得保留的计算时实施。合并只保留新模型需要的 owner 和归约含义，不为
旧规范顺序额外排序；同时测 worker×cell 内存和清理成本，不假设理想四倍加速。
它不阻塞 F3。GPU、通用 checkpoint 和远场中观化均不纳入第一轮原型。

生命周期 B1（LiveOrderIndex）和 B2（成功替换后的 Active 维护）继续单独
登记，复用已有公共接口夹具。它们改善命令链路，不记作 Core frontier 收益。

## 4. 如何判断“更快且值得采用”

### 统一以结果验收

所有候选采用同一口径：固定外生路网、OD/到达请求、seed、信号输入和初态，
比较服务时间、实际处理量和交通结果。内部到达、重试、裁决及摘要允许改变。
旧版摘要、事件顺序和首错不作为通过条件，跨 worker 也不要求逐拍字节一致；
不同 worker 配置分别重复测量，报告结果分布、质量和收益。

Harness 记录真实拒绝、积压与完成情况，用结果指标替代依赖旧轨迹的断言。
原版 A/B 只用于解释变化，不是以原版输出作 oracle；新结果也不冒充旧口径
`performance-match`。原始日志和输入身份用于复核事实，不用于强制执行等价。

新模型仍需有效句柄和代次、有限数值、受控内存、可解释的车辆守恒及资源释放。
失败后回滚、可重试或明确终止世界应有一套定义；不能默许半提交后继续运行。
确定性只有在实现便宜或实际产品能力需要时才保留，不是本轮优化门槛。
需要复现实验时记录输入、构建、配置、统计和可用日志，不强求逐拍一致。

行为测量至少覆盖：完成吞吐、实际 Active 工作量、旅行时间和排队分布、最长
等待及停滞车辆、重叠幅度/持续时间、纠正次数与跳变、命令拒绝和资源滞留。
吞吐下降导致车辆不动、减少 Active 或积压外生请求，都不能只报 Core 变快。
本轮用速度与行为指标共同筛选候选；尚未约定的质量容差不填成“已通过”。

### 工作负载与计时

1. 原计划 512 拍前缀用于成本筛查和行为观察，不能代表 D2/L3 后段。
2. 公共接口构造稠密排队、空/忙入口、连续冲突、混合转向、同 movement 多车
   尾部释放、临界 ETA 和生命周期失效场景；不直接改内部状态冒充晚窗。
3. 候选有明确净收益后，再从初态演进到代表性后段采短窗。现有 checkpoint
   摘要不是完整可恢复状态，不以改 tick/位置替代真实命令队列、随机与重试状态。
4. 候选收敛后再补稳定 100k Active 与代表性长窗，验收项按新模型的结果目标
   更新，旧认证中的等价条款不再继承。现有混合 100k 的前缀 Active 仅
   66597–74492；不能改名为 100k Active 达标。

先完成小规模边界/失败测试、原型 smoke 和有代表性的短窗。正式计时串行执行、
停止本任务其他构建/采样，同 worker 用原版/候选的平衡次序重复，例如 A-B-B-A
并反转起始次序。用无插桩 release 记录每轮 mean/p95/p99、峰值、分配与内存；
不把逐阶段 p95 相加，也不把一次约几个百分点的差异认证为收益。持续收益须
超过本次重复运行的波动，并报告每轮结果，不以固定百分比代替测量。

## 5. 16ms、33ms 与宿主链路

原 #707 的 100k、33ms 固定步长、Core p95 16ms 目标继续单列为未达标。
研究允许提出 33ms Core 阶段里程碑，但不能直接替换原验收或宣称实时。

即使宿主真正异步运行仿真，33ms 步长仍要求持续服务率跟上约每秒 30.3 拍。
Core 本身用满 33ms，不给命令、发布、调度与长尾留余量；Core p95≤33ms
也不证明长时间没有积压。需要测生产链路 `command + Core + publish`、队列
年龄/长度、积压恢复、展示延迟及宿主帧时间。异步只改变等待关系，不减少工作量。
当前同步 step/宿主接入不能直接描述成“已经与游戏线程分开”。

完整研究 Harness 的 observation/写出成本单独报告，不等同生产发布成本；
同样不能忽略它并将 Harness 墙钟说成游戏实时性。是否保留 16ms 作为产品目标，
应由新模型结果和明确宿主运行方式决定；目前没有证据证明 16ms 算法上不可能，
也没有证据证明把预算放宽到 33ms 就足够。

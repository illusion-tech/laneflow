# 复核目标经路线索引查找：结果

**日期**：2026-10-10；Refs #861，父任务 #707 继续开放。设计见
[`traffic-runtime-contender-frontier.md`](../../docs/design/traffic-runtime-contender-frontier.md)
4.5 节。

## 1. 结论与交付范围

复核目标里「出现在冲突区申请者名单、整条路线经过新车车身所在边」的车，不再逐个
冲突区扫描名单并逐条比对路线，改为从车身所在边经「边 → 路线」压缩稀疏行与
「路线 → 申请者」侵入式链表直接取出，按逐区扫描中第一次出现的位置排序。目标序列
与原路径逐项相同；不改规则、公共 API、错误分类、格式或资源所有权。

普通 ABBA 观察窗公共命令合计下降 26.1%–27.6%，命令 p95 下降约 15%，p99 下降约
56%–59%；step 分位无一致方向。四次运行的交通文件逐字节一致。本交付不宣称 16 ms
达标或 #707 完成认证。

## 2. 依据

分阶段计时探针（不合入）在格点按需求值之后的 main 上拆分观察窗公共命令：

- 复核目标收集约占 28%，其中逐区扫描约占 27.5%；
- 每次准入平均遍历约 3.06 万条名单条目、判定约 3,700 辆车，最后只找到约 1.2 个
  复核目标。

## 3. 实现与正确性

- 「边 → 路线」：按已注册路线计数排序建压缩稀疏行。注册与删除路线时直接作废（删除
  后同槽复用时计数签名不变，由 `recycled_route_slot_rebuilds_the_edge_route_index`
  覆盖），另以 (世界世代, 已注册路线数, 槽位表长度) 兜底。作废后先逐区扫描，累计
  扫描量抵得上一次重建才重建；申请者链表为空时直接跳过；路线经过边总次数超出 `u32`
  偏移时不建表、一直扫描。这三项在 ABBA 之后加入，未重新计时；被测场景的路线在
  开局一次注册，只有最初少数准入逐区扫描，之后与被测提交走同一条索引路径。
- 「路线 → 申请者」：按车辆槽位的侵入式双向链表，只链入冲突区列表非空的逐车记录，
  写入与撤销记录时 O(1) 维护，名单重建时清空表头。
- 复核按顺序逐个检查，拒绝原因写出第一个被逼停的车，所以找到的车按
  （冲突区编号, 名单内位置）排序，与逐区扫描的先后相同。
- 两张表在第一次重建名单时才分配；预留失败（沿用 `RecheckScratch` 注入点）时这份
  名单退回逐区扫描。
- 测试与 `placement-fixtures` 构建里每次走索引都再做一次逐区扫描并断言目标序列逐项
  相同；现有全部生成类测试都经过这条断言。
- Rust 1.98.0：Runtime 默认与 `placement-fixtures` 两种配置全量测试通过；Clippy
  两种配置 `-D warnings` 通过；`fmt` 通过。`spawn_overlap_allocation` 打印的两行
  断言信息与 main 相同，测试通过。

# P5 直接 Active 投影的采用证据

Refs #775、#707。采用本次内部优化：100k 三组平衡对照的全窗与 65–256 拍
mean 均同向改善，且每组收益都大于同组两臂各自的重复差；10k 未观察到净回归，
但只有第一组充分分离重复波动。正确性边界、完整 join、失败零提交、重试、资源
转移与生命周期矩阵均通过。这里的短窗结果支持合入，不构成最终城市性能或长期
交通质量认证。

## 改动与身份

- 基线：`2b5431201bb64d82f38ea8228076c54941fd2af3`。
- 实测候选：`baa60104d4ae93c4ee796887253c7e95bd5667bd`。
- 干净且可达的 Rust 采集器：`2345536b353bd71174690def6bcd740d5379892f`；
  协议 `p5-direct-active-abba-v1`。
- 删除 `TickWorkspace::motion_inputs` 及其预留故障面和保有内存计账。Pool 任务直接
  索引 C(T) 的 `active_order`，读取完整 `VehicleHandle` 后调用代次感知的
  `vehicle_state`。输出槽位继续独占、完整 join，并由协调器规范消费。
- 无公开 API、格式、领域算法或 Adapter 变化；没有新增依赖或非 Rust 程序代码。

## 正确性与边界

`laneflow-runtime` 全量 lib 测试为 517 passed / 15 ignored。已有测试明确覆盖：

- workers 1/2/4/8/16 的融合/分发逐拍对拍、真实多线程参与与阈值强制路径；
- Active 中的 Parked/Completed、同槽位新代次 respawn 与完整句柄核对；
- Waiting/Conflict 持有、释放、近门、停车到达、跨块首错与完成前沿；
- 到达真实预留失败优先于后车运动错误，整拍零提交，清除注入后的 retry；
- 结果槽位首次尝试及已建容量上的预留失败均回退相同融合原语；
- `Pending` / 调度 `Skipped` 仍是完成前沿错误，失效身份使用独立的
  `Done(Ok(None))`，不会把未计算槽位误报为正常跳过。

Runtime all-targets Clippy（warnings denied）、格式和 diff check 通过；新 Rust 采集器
4 项测试与 Clippy 通过。发布 JSON 由 `verify` 原样复算成功，SHA-256 为
`2325787292c1c13512f6f04fceebaf5612381234b2988ef42d706ad1fc5ef6ac`。
基线/候选二进制 SHA-256 分别为
`c9652f6d6252a64266a747320cb3cdafdf67eb3ed6468cdfcaf891b9b8b69fa5`、
`b95623a0d483afbbd41f8f412d22b9542bf2ae7627c15427da18bb51883e38a2`。

## 测量边界

采集机器为 Ryzen 9 9955HX（16 核/32 逻辑线程）、Windows 11 build 29671、
BIOS N.1.09MRO07、平衡电源方案、电池 100% 且接通电源；未逐轮锁定温度、功耗或
厂商性能模式。Rust 1.98.0，两个 release/locked/offline 构建使用独立 target，
构建全部完成后才串行计时。

本次问题是逐拍输入暂存与状态复制的净成本，现有正确性测试和三组平衡短窗已直接
回答是否采用。没有遗留一个需要 44,544/100k 长窗才能发现的具体风险，因此不追加
全天认证。#707 的正式规模、信号多周期、长等待与长期交通质量结论仍单独验收。

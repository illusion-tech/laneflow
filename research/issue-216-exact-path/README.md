# TrafficWorld occupancy / leader 有限精确路径研究

本报告交付 [#216](https://github.com/illusion-tech/laneflow/issues/216) 当前重启范围，
不是历史 CoreWorld 候选的恢复，也不是城市级性能认证。
生产基线冻结为 `6fefd582364685c07ed83af79b2bec80f5223fc5`；
[当前 G2](https://github.com/illusion-tech/laneflow/issues/216#issuecomment-5581912546)
限定测试专用归因和一个有依据的精确候选。生产算法、公开 API、数据格式、线程模型、
车辆更新频率均不改变。批次 / 配对 / 等价数据的研究补丁冻结在
`406813daaaf0703ab08019432bb4c349253215a0`，逐文件 Git blob 与二进制 SHA-256 位于
[`environment.json`](evidence/environment.json)。后续只补充同输入的批量查询回放，
其独立源码与二进制记录见
[`查询回放环境`](evidence-query-replay/environment.json)；没有重新选择既有配对轮次。

## 1. 结论

**不建议把本轮“生成一次、暂存后分桶”候选接入生产路径。**

- 候选与基线的逐拍状态、事件、occupancy 记录、后缀索引及失败重试一致；没有用近似查询换性能。
- 四组交替顺序的短对照没有一致的整步收益；三组的配对 p50 中位变化为变慢约 3%，
  另一组变快约 2.4%。这些差异处于本机轮间波动内，不能承诺生产加速。
- 暂存使第二遍分桶更便宜，但把生成、增长检查和额外写入搬进第一遍；没有消除整个重建成本。
- 暖机后的 48 个配对窗口均为零分配流量，但候选额外保留 24 / 384 / 384 / 48 KiB。
- 本轮到此停止候选扩展，不追加第二套布局、完整 100k 矩阵或并行实现。

## 2. 输入与测量边界

前三组沿用 [#583](../issue-583-runtime-profile/README.md) 的固定道路输入：
1k / 256 占用边、10k / 256 占用边、10k / 16 占用边。
物理边长 8 km，4.5 m 车辆、10 m 初始车头间距、零初速、15 m/s 限速；路线各含一条边。
静态路网仍有 256 条边，不能把“实际占用边数”当成路网总边数。

唯一新增多边输入为 64 个独立环，每环 32 条 10 m 边，共 2048 条物理边；
每条路线显式列出两圈，共 64 个出现项。1000 辆车分布在 64 条路线，
初始车头间距 20 m，首车从 5 m 开始。车辆配置仍为 4.5 m、零初速，限速 15 m/s。
从受检的编译器原生输入构建共享根；不修改编译器、准入规则或 Traffic Runtime 的路线规则。
这个窗口包含车身跨边和后续出现项查询，但不是资源密集型城市路网。

四组均先暖机 40 拍，再观察 64 拍；固定步长 100 ms，窗口内全部车辆保持 Active。
`N_individual=N_traffic_active=N_intent`，`N_presented=N_aggregate=0`。
不运行 reduced-rate、Spatial、Adapter、renderer、宿主需求模型或完整城市 harness。

2026-09-08，Windows 11 x64 build 29648，AMD Ryzen 9 9955HX，Rust 1.98.0，
release 默认配置、平衡电源计划、接通电源。编译完成后串行执行测量，脚本检查没有
Cargo/rustc/link 或其他已知 Runtime 测量进程；没有绑定 CPU、锁定频率或控制操作系统调度。
因此以下是开发机有限研究数据，不是跨机器或长时间尾延迟保证。

| 入口                                  | 用途                                   | 不可混淆的边界                                                          |
| ------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------- |
| `runtime_profile_wall_clock`          | 冻结基线的未插桩生产库整步墙钟         | 没有候选；不能与测试构建候选直接组成 before/after                       |
| `runtime_profile_stages`              | 既有 11 个批次阶段墙钟                 | 测试构建的 inclusive 阶段，不是独占 CPU                                 |
| `occupancy_exact_attribution`         | 重建四段批次计时、每 67 次查询采样一次 | 查询读时钟成本不可忽略，不可外推为整步占比                              |
| `occupancy_exact_paired_windows`      | 同一测试二进制的候选 / 基线六轮配对    | 内部计时关闭；保留测试 hook 和 `StatsAlloc<System>`，不是未插桩生产候选 |
| `occupancy_exact_equivalence_windows` | 四组输入逐拍状态、事件和索引比较       | 快照、校验和输出均不计入上述整步计时                                    |
| `occupancy_exact_query_replay`        | 同输入按查询族分批回放                 | 输入预收集、缓存顺序改变；不等于真实整步的独占成本                      |

配对每轮重建两个相同世界，偶数轮基线先运行、奇数轮候选先运行。
每拍只把 `step` 调用计入延迟；样本整理、查询工作量读取、摘要、内存账本和日志输出在计时外。
分配统计覆盖同一稳态窗口，48 个窗口均未触发分配器操作；安装、暖机、快照不在统计内。

## 3. 归因结果与可靠性

当前三组单边输入的 occupancy 重建占同轮批次插桩整步约 **5.27%～6.05%**；
`motion_loop` 约 **56.37%～58.82%**，但它同时包含 leader、controller、约束、advance 和 store。
不能把后一个比例全部交给 #217，也不能与历史 CoreWorld 百分比相减。

下面是重建子段每拍平均时间的三轮中位数，单位 µs。各列独立取中位数，
不把它们的和冒充一个独立测量值。候选的 `count` 包含暂存写入，`fill` 则是连续暂存区的分桶。

| 输入         | 基线 count | 基线 fill | 候选 count + 暂存 | 候选 fill |
| ------------ | ---------: | --------: | ----------------: | --------: |
| 1k / 256 边  |       3.68 |      5.22 |              7.95 |      1.43 |
| 10k / 256 边 |      40.19 |     55.15 |             84.86 |     16.87 |
| 10k / 16 边  |      35.45 |     46.98 |             79.07 |     16.43 |
| 1k / 多边    |       5.83 |      7.00 |              9.63 |      2.22 |

这解释了为什么“少一次车辆 / 路线遍历”并不自动等于整步加速：候选增加了暂存写入、
容量检查和额外读取。保留原有排序及双后缀最小值表，leader 查询算法没有改变。

工作量是各轮一致的精确计数，不是时间外推：

| 输入         | 每 64 拍占用记录总数 | 后缀记录检查总数 | 后续出现项行走总数 |
| ------------ | -------------------: | ---------------: | -----------------: |
| 1k / 256 边  |                64000 |            47616 |                  0 |
| 10k / 256 边 |               640000 |           623616 |                  0 |
| 10k / 16 边  |               640000 |           638976 |                  0 |
| 1k / 多边    |                93024 |           345096 |             496288 |

“后缀记录检查”沿用既有 `inspections`，不包含 `partition_point` 内的二分比较次数，
因此不是全部内存读取次数。多边组平均每车每拍行走约 7.75 个后续出现项；
前三组没有执行该路径，不能拿单边结果声称 route-distance 已不重要。

本轮空时钟读的观测均值为 **54.09 ns**，单次查询采样值多数仅为约 36～68 ns，
甚至低于该控制值。它们受到时钟粒度、计时器成本和编译器调度影响，**不支持可靠的
leader/horizon/route-distance 独占耗时排序或占比**。原始值完整保留，不扣除时钟后制造
“净耗时”，也不把 `motion_loop` 减去这些估计值来定义 #217 的成本。

为得到可分辨的查询成本量级，另对同一窗口做三轮**批量查询回放**：每拍重建相同的
occupancy、预收集输入，再分别批量执行路线 / 配置定位、前视窗计算、leader 查询、
路线终点 / 信号 / 停车距离查询。每批只有一对时钟，以 `black_box` 消费输入和输出。
预收集与重建不计入查询批次；真实 `step` 随后推进同样命令流。
所有记录数、后缀检查数、出现项行走数和最终摘要与前述窗口一致。

下表是批次总时间除以实际查询次数后的三轮中位数，单位 ns / 查询；
这是**回放口径**，不是逐车计时，也不是生产运动循环中的独占成本。

| 输入         | 路线 / 配置定位 | 前视窗 | leader gap | 路线终点 / 停车 / 信号距离 |
| ------------ | --------------: | -----: | ---------: | -------------------------: |
| 1k / 256 边  |           10.81 |  14.12 |      16.53 |                       8.69 |
| 10k / 256 边 |           10.06 |  12.60 |      27.84 |                       8.03 |
| 10k / 16 边  |           10.16 |  14.22 |      38.17 |                       8.02 |
| 1k / 多边    |           10.73 |  12.95 |      43.46 |                      10.09 |

在这个回放口径内，leader 查询随桶集中和多边行走增加，值得保留为 workload 相关的
成本项；不能仅因为 occupancy rebuild 约 6% 就把 #216 全部成本当成 6%。
这里预热了输入与查询缓存、改变了真实循环的交错顺序，且路线距离组没有活动停车预约或
信号 stop，因此不把表中数字换算成整步占比，也不泛化到资源密集城市输入。
原始批次总量见 [`query-replay.txt`](evidence-query-replay/query-replay.txt)。

## 4. 配对整步、尾部与内存

变化为每轮 `candidate / baseline - 1` 后取六轮中位数；正数表示变慢。
“更快轮数”按该轮 p50 判断。它与“两个组各自中位数之比”不是同一个统计量。

| 输入         | 配对 p50 变化 | 配对 p95 变化 | p50 更快轮数 | 额外保留暂存 |
| ------------ | ------------: | ------------: | -----------: | -----------: |
| 1k / 256 边  |        +3.14% |        +3.94% |        2 / 6 |      24576 B |
| 10k / 256 边 |        -2.44% |       -10.71% |        4 / 6 |     393216 B |
| 10k / 16 边  |        +3.23% |        +0.91% |        2 / 6 |     393216 B |
| 1k / 多边    |        +3.02% |        +2.05% |        2 / 6 |      49152 B |

10k / 16 边的逐轮 p95 变化范围为约 -30.4%～+96.6%，说明尾部样本不足以证明稳定收益。
64 拍的 nearest-rank p99 就是当轮最大值。完整各轮数据、p99、max、五分区账本及
分配字段见 [`pairs.txt`](evidence/pairs.txt) 和 [`summary.json`](summary.json)。

内存沿用 `WorldMemoryLedger` 的逻辑 backing 口径：capacity × 元素大小；
共享根单列，不计容器固定字段、分配器 / HashMap 桶开销，不是进程 RSS 或峰值。
候选额外字节全部归于 Workspace 的 `exact_pending`；生产构建没有该字段。
暂存 Vec 的几何容量大于有效记录数，因此 10k 场景不是简单的 10000 × 24 B。

未插桩生产基线的 p50 三轮中位数分别为 0.1873 / 2.1055 / 2.4426 ms，
只作为当前绝对成本锚点；它们不能与上表测试构建候选直接相除。
较早探索运行也有明显轮间波动，保留在本地 `target/issue-216-baseline/`；
本报告固定使用 `406813da` 对应的 `evidence/`，没有据此选择更好看的轮次。

## 5. 精确性与失败边界

- 四组各 64 拍逐拍比较 `StepOutcome`、全部车辆状态、完整快照、Waiting/Conflict 决策、
  转移事件、occupancy 记录与两个后缀表；全部一致。所有归因 / 配对轮次最终摘要也一致。
- 复用已有全扫描 oracle，覆盖跨边车身、重复边、分岔悬伸、已停车 / 已完成车辆和前视窗边界。
- 暂存增长失败按实际增长点逐个注入，失败不发布状态或事件、不替换 occupancy 记录；
  移除故障后重试与全新基线相同。
- 暂存分配失败后仍完成原来的路线完整性检查，保留 `OccupancyIntervalIncomplete`
  对分配错误的首错优先级。坏路线修复后可重试，不遗留部分暂存污染。
- 复用既有 Waiting / Conflict / 信号、日志武装 / 溢出、grant / transition 失败与恢复轨迹；
  候选仍匹配固定历史语义摘要，不从候选实现生成新的“期望答案”。

现有生产 `build_occupancy_index_for` 与切换算法未修改；不把一个测试候选的成功视为
已完成生产切换优化或所有错误组合认证。

## 6. 复现与后继输入

先编译，再串行测量。Windows 脚本不覆盖已有证据目录，并在测量前后核对源码与二进制。
`--no-run` 会打印当前机器上的两个 exe 路径，把它们传给脚本；离线缓存完整时可加 `--offline`。

```powershell
cargo +1.98.0 test --release --locked -p laneflow-runtime --lib --test runtime_profile_evidence --no-run
./research/issue-216-exact-path/run.ps1 -TestBinary <unit-test-exe> -ProductionBinary <runtime-profile-evidence-exe>
python research/issue-216-exact-path/analyze.py <new-evidence-directory>
cargo +1.98.0 test --release --locked -p laneflow-runtime
cargo +1.98.0 check --release --locked -p laneflow-runtime
cargo +1.98.0 run --release --locked -p xtask -- check-runtime-architecture
```

脚本默认运行全部六个入口；如只复现补充查询回放，可增加 `-QueryReplayOnly`，
并使用新的输出目录。分析仓库内已存记录时省略分析器的目录参数，它会读取两份独立证据。

本地已运行 Runtime 完整 package 测试（445 通过、0 失败、22 个手动入口默认忽略），
并单独成功运行上表六个手动研究入口；`cargo check`、`cargo fmt --check`、Runtime 架构检查、
Markdown 表格检查及两份测量源码清单核对均通过。全 workspace / CodeQL 由 PR CI 验证，
不把本地 package 测试冒充这些门禁。

[`analyze.py`](analyze.py) 只读取固定原始记录，验证数量、采样次数、精确工作量、
各入口摘要、配对顺序、分配与内存账本，再输出汇总。批量查询回放也核对工作量与摘要，
不与不同口径的计时相加。它不运行基准，也不设置 CI 延迟门禁。

给后继的结论：#217 应继续拆分 controller / 约束 / advance / store，但上述探针与回放没有
给出可直接相减的 leader 独占占比；#220 可以消费多边查询的实际工作量与此候选的负结果，
不能把它当成 worker-count、halo、barrier 或多核加速证据。
#544 的城市 harness 计数 / 计时问题与完整城市性能 Gate 仍独立存在。

## 7. 补充 CPU 采样归因

[`cpu-profile.md`](cpu-profile.md) 使用生产库优化构建的真实 `step` 调用栈，
补充函数与内联源码归因。10k / 256 和 10k / 16 中，仅重建、leader 查询、horizon
三个不重叠子树合计为 18.52% / 21.43% 的 CPU 采样权重，不能用约 6% 的重建墙钟
概括整条 exact path。该采样与上文探针/回放口径不同，不相减、不混算。
原候选负结果不变；这不是新的生产优化或 100k 城市证据。

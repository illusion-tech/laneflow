## 守恒与校验核对
- 每轮 `runtime_command_ns + harness_command_bookkeeping_ns + harness_other_ns + residual_ns == lifecycle_ns`（`conserved=true`），六轮残差恒为 0。
- 六轮 `command_receipts_equal=true`；全部 checkpoint `oracle_equal=true` 且携带 64 位十六进制 `public_state_digest`——F2 公开摘要通道在测量端与 oracle 端逐检查点核对通过。本轮输入 `blocked_commands=0`（未产生拒绝命令），F2 的拒绝分支未在数据层面触发，其正确性由 harness 测试覆盖。

## 结论
- lifecycle 区间内 **runtime 命令 API 执行段占约 96.9%–97.4%（10000）/ 99.90%–99.92%（100000）**；harness 侧合计约 2.6%–3.1% / 0.08%–0.11%。
- harness 命令记账随命令量近似线性放大（600→6000 命令，约 0.38–0.45 ms→4.4–9.4 ms），harness 其他基本持平（3.1–3.3 ms→4.2–4.5 ms）；规模放大后两者占比合计降至 0.11% 以下，突发主体即 runtime 命令执行本身。
- checkpoint 校验成本独立：10000 约 43.5–47.1 ms，100000 约 347.5–530.0 ms。

## 局限与后续
- **准入检查 / 索引维护 / 实体映射**位于 runtime 命令 API 内部，本迭代未单独分段（并入 `runtime_command_ns`）；如需按方案稿 §4.1 六维拆分，需在 runtime 命令路径增加 `execution-evidence` 阶段探针（feature 内、零快路径影响），列为后续。
- 本测量未启用 `allocation` feature（`instrumented=false`）；allocation 诊断单列，未计入上表。
- 绝对时长受机器负载影响（见口径与配置），跨配置比较应以分段占比与守恒为准。

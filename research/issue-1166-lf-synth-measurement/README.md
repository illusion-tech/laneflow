# LF-SYNTH-v2 表现接线与正式测量

2026-10-30，交付 [#1166](https://github.com/illusion-tech/laneflow/issues/1166) 的
车辆特化研究测量。**60 个标称窗口、3 个 stretch 窗口和 20 个独立分配诊断窗口
均完整完成；83 次运行的原始数据与聚合通过独立复核。** 运行完整不等于预算通过，
`Product TBD / Uncertified` 保持不变，不能据此关闭 #539 或认定完整游戏达到 60 FPS。

## 主要结果

- 一万 W1、16 ms、100% 表现：Core / 表现 / 普通单拍整帧 p95 分别为
  **1.8212 / 2.8035 / 4.6089 ms**，低于 2 / 4 / 6 ms 参考预算；p99 也低于参考
  上限，但三项最坏值 **5.4193 / 10.6946 / 13.2575 ms** 分别超过 4 / 8 / 12 ms。
- 十万 W1、33 ms、10% 表现：Core p95/p99/max 为
  **14.4570 / 15.5239 / 27.9312 ms**，低于 16 / 24 / 32 ms，Core max 也低于
  33 ms quantum。普通零拍与单拍同次运行合并后的表现 p95/p99/max 为
  **8.1365 / 8.7861 / 17.7370 ms**，三项均超过 4 / 6 / 8 ms 参考值。
  同口径连续整帧 p50/p95/p99/max 为
  **16.8999 / 21.6411 / 23.2719 / 41.1761 ms**。单拍组和零拍组仍分别保留，
  这里没有相加 component percentile，也没有混入边界或突发帧。
- 十万 W4：每轮两个指定帧的整帧 burst max 中位数为 **3503.3509 ms**，最坏
  **4295.3141 ms**。每帧 2000 条 observation 命令所在的 lifecycle 实测区间
  占该帧时间的 **98.98%–99.48%**；该区间包括宿主命令执行与相应校验，不是
  exclusive CPU 或更细的函数归因。不能用约 14 ms 的 Core 与约 7 ms 的表现
  掩盖这个秒级突发。W4 不套用普通 W1 预算，也没有从两样本生成 p95/p99。
- W1/W2 的十个诊断配置均出现预热后的 allocation/reallocation，未满足零分配
  参考要求。一万 W1 各比例为 7 / 39 次，十万 W1 为 7 / 55 次；直接包围
  `TrafficWorld::step` 的 W2 也非零，不能把所有分配归因于 Bevy 调度。
  全部非零拍与字节保留在 [allocation-audit.json](allocation-audit.json)。
- 其他敏感性行也存在明显尾值，例如十万 W1/100% 普通单拍整帧 max 为
  308.0622 ms。完整数据全部保留；未完成细粒度归因，不将这些尖峰解释为已解决，
  也不因某一主行 Core 达标而宣称整个协议通过。

## 运行与复核方法

W1/W3/W4 使用真实 Bevy Session/Plugin、同根 SpatialSession 和 ECS Transform，
固定 logical rank 选择跨状态与句柄替换不变。每拍消费命令和有序事件，完整表现批次
预检后才统一提交 Transform。W2 只执行 Core。生产 Runtime、Spatial、Adapter API
没有变化；实现与回归入口见 [harness README](../../tools/laneflow-synth-harness/README.md)。

W1/W3 使用冻结的整数纳秒 60 Hz 序列；为预热、H/2H/4H 与最终边界截短的帧保留
并单列，时间不丢弃。W4 预热后恰好输入两个 quantum 帧，分别完成 B0/B1。连续
整帧计时包含生命周期、全部 Core steps、有序事件消费、选择映射、Spatial 和
Transform 提交；完整状态快照、文件写入及排序位于声明的帧间。该服务时间不等于
真实墙钟排队延迟。W1–W3 均覆盖冻结的完整观察窗口，不以检查点前缀代替 tail。

| 阶段 | 窗口数 | 成功 Core 拍数（含预热） | Observation 拍数 | 实际外层帧数（含预热） |
| --- | ---: | ---: | ---: | ---: |
| 标称 | 60 | 1810380 | 1163820 | 2090808 |
| Stretch | 3 | 130572 | 87048 | 125361 |
| 分配诊断 | 20 | 603460 | 387940 | 696936 |

标称是一万/16 ms 与十万/33 ms 各十个配置，每个三个 fresh-process rounds，
每轮行顺序左移七项。Stretch 仅测十万 W1/16 ms/10% 三轮，其他 stretch 行未测。
诊断使用独立 instrumentation binary，标称二十个配置各一个完整窗口；其耗时
不进入 latency 结果。83 个子进程累计约 10 小时 52 分钟，包含各自初始化与
证据工作，不是 Core 或 integrated 计时，也未包含九个 oracle 的准备时间。

百分位使用 nearest-rank：每轮分别计算 p50/p95/p99，再取三轮中位数；max 使用
三轮最坏值。W4 只报告 B0/B1 raw 与每轮 burst max 的三轮 median/worst。
W3 不套用 W1 预算。正常零拍、单拍、追赶、生命周期及边界帧分别保留；补充的
普通帧合并统计只合并同轮零拍和单拍，不跨轮池化。

独立复核使用本地 Python 标准库重新计算 SHA-256、原始样本统计、帧分类、时间
守恒和三轮聚合；与 harness 输出逐值比较，83/83 一致。还核对全部有序事件、
W3/W4 命令字节及批次字段、完整状态检查点与同输入 oracle。相等范围是检查点
的提交状态和完整有序事件/命令，不声称逐拍全部内部状态都由独立实现重算。
复核清单见 [raw-audit.json](raw-audit.json)。

W2 的共用准备步骤也写出 `frame-inputs.json`，但 Core-only 分支不消费该序列；
`frames.json` 为空，tick 的 `frame` 字段为 `tick - 1`。manifest 的共用 timing
说明不适合作为 W2 的逐路径描述：W2 实际直接包围 `TrafficWorld::step`，没有
Spatial/Adapter 或 integrated 样本。审计据源码核对这个口径并修正了最初要求
W2 输入文件为空的假设，未修改原始数据；清单显式记录
`outer_frame_inputs_consumed=false`，未将这些未执行输入计入外层帧数量。

## 资源与后续判断

Runtime owned-capacity 只在独立诊断构建读取，正常延迟运行对应字段为 null。
Runtime 账本、宿主缓冲、既有 Adapter/Spatial capacity counters 和进程内存分别
报告。capacity 是保留存储，不能当作每拍写入量或实际 heap peak；HashMap capacity
也不包含完整 allocator/control-byte 开销。

进程 working set/private bytes 是声明检查点的样本；累计 working-set/commit peak
包含初始化、输入验证与证据缓冲，不声称覆盖最终落盘之后的退出瞬间。正常标称
记录到的最大 private bytes 为 271.27 MiB，累计 commit peak 为 1306.20 MiB。
这两者不是同一计数口径，不据此宣称 Runtime 稳态需要约 1.3 GiB。

当前数据支持后续分别调查表现路径、lifecycle 命令成本、预热后扩容和异常尾值；
尚未取得函数级排他 CPU 归因，也没有实施这些优化。W3/W4 的失败重试交通语义
仍引用 [D 切片证据](../issue-1162-lf-synth-burst/README.md) 的实际源码身份，不能
冒称为本次新表现路径的失败重试测量。E 的批次提交失败原子性、身份连续性和
调度边界另由本提交的回归验证。完整产品协议继续保持未认证状态。

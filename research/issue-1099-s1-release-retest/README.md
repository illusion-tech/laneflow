# 四阶段统一 release 重测

任务：[#1099](https://github.com/illusion-tech/laneflow/issues/1099)，父议题
[#790](https://github.com/illusion-tech/laneflow/issues/790)。本报告重测
[#1093](../issue-1093-s1-efficiency/README.md) 的相同 17 条样本和四个冻结阶段。
旧报告已在 [#1100](https://github.com/illusion-tech/laneflow/pull/1100) 降级为
未受控探索性计时；本次不修改旧原始数据，也不以新百分比重新解释旧计时。

## 结果与判断

2026-10-27 17:05–17:12（Asia/Tokyo），统一 release 构建完成了 32 个正式块，
每阶段 8 块、每块 10 个新进程；另有 4 个预热块。表中耗时是每个块内 10 次
样本搜索总耗时的均值，再对该阶段的 8 个块取中位数和范围。

| 阶段 | 累计实现 | 搜索耗时中位数 | 块均值最小—最大 | 相对 A | 进程 CPU 中位数 |
| --- | --- | --- | --- | --- | --- |
| A | 原枚举，共同计时入口 | 1.000072 s | 0.996022–1.006287 s | 基线 | 0.996875 s |
| B | A + 固定 cubic 累计切向扫描复用 | 0.441277 s | 0.438467–0.443454 s | -55.875% | 0.454688 s |
| C | B + 完整规范点序列去重 | 0.445128 s | 0.441520–0.450173 s | -55.490% | 0.456250 s |
| D | C + 保留游标、前缀坐标和指标的有界回溯 | 0.434077 s | 0.432807–0.437569 s | -56.595% | 0.441406 s |

本机、本次固定样本的结果支持扫描复用带来明显收益：A → B 的搜索耗时约减少
55.9%，D 相对 A 约减少 56.6%，每次运行这 17 条样本少约 0.566 秒。进程 CPU
时间也呈相同的大幅下降，但它包含进程内的校验和 I/O 等工作，不能与搜索计时相减
后解释为纯算法额外开销。

候选去重没有命中重复项，不能据此认定它带来性能收益。按连续四阶段组成的 8 个
配对周期比较，C 相对 B 的变化中位数为 +1.04%，范围 -0.17%～+2.05%。
D 相对 C 为 -2.10%，范围 -3.86%～-1.44%；D 相对 B 为 -1.59%，范围
-2.36%～-0.20%。这说明本样本中的有界回溯增量较小，主要收益来自扫描复用。
配对周期差值与表中“各阶段中位数的比值”是不同统计量，未作显著性或总体外推。

**本次保留了实际背景竞争，不是安静负载认证。** 用户先把负载阈值改为平均
≤6%、峰值≤10%，随后要求直接开始，因此在完整批次前取消了负载超限中止。
所有 32 个正式块均纳入统计，没有筛掉较慢或超限的块。结论仅适用于此次研究入口；
不表示整个 LuST 转换器提速 56.6%，也不构成生产 S1、交通质量或 #790 的 G1 验收。

## 模式、电源与实际负载

- 主机为 AMD Ryzen 9 9955HX、32 个逻辑处理器；Windows 11 Pro Insider
  Build 29695。完整版本见 [environment.json](environment.json)。
- 用户确认已设置狂暴模式；初始检查及全部 36 个块的前后只读检查均得到 OEM
  `MainOption.json` 的 `OperatingMode = 2`，交流供电均在线。
- Windows 电源计划全程为 `381b4222-f694-41f0-9685-ff5bb260df2e`（平衡）。
  它与厂商模式分别记录；没有将 Windows“平衡”解释为厂商未进入狂暴模式。
- OEM 配置路径在 [protocol.json](protocol.json) 中记录。该证据为用户确认加配置
  交叉核对，未独立读取固件实际状态，也没有采集温度、功耗或时钟频率。
- 正式块背景 CPU 占整机能力的中位数为 **5.653%**，范围 **4.919%–9.326%**。
  320 个进程运行区间的背景 CPU 最大值为 **16.138%**；这是区间平均值的最大值，
  不是硬件瞬时峰值。块前 1 Hz 空闲采样的最大值为 **15.338%**。
- 11／32 个正式块的背景均值高于 6%；15／320 个进程区间高于 10%；综合块前
  空闲采样、块均值及进程区间，17／32 个块至少一项超过参考阈值。没有剔除。

负载采集使用 Windows `Processor(_Total)/% Processor Time` 性能计数器。
独立准备采样使用原生 `typeperf`；测量器读取同一计数器的 `CounterSample` 对，
以整机活跃 CPU 时间减去被测进程 CPU 时间估算背景竞争，计入测量器自身开销。
计时区间不运行全进程 CPU 枚举或编译；电源查询放在块前的 5 秒采样窗口之前。
准备阶段单计数器探针测得采集器与等待进程合计约 0.033% 整机 CPU，但这不是
对整个测量器所有开销的上限承诺。实现依据见微软
[性能计数器采样](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.performancecounter.nextsample)
与 [typeperf](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/typeperf)。

## 一致性与恢复结果

360 个进程（320 正式、40 预热）的完整结果文件均直接逐字节等于各自冻结阶段
的 release 校验结果。四阶段的全部候选、跨度参数、指标及保留的完整程序再使用
`System.Text.Json` 精确对照旧基线，结果相同；没有仅用摘要代替这项内容比较。

9 条原失败边仍只有 `sumo::-10004_5_1` 产生 8 份候选，6 条因划分预算截断，
2 条耗尽有限候选族。相应阶段的停止原因、计数和输出没有改变。A 的切向求值
52,669,197 次降至 B / C / D 的 13,851 次；D 另有 135 次前缀复用、43 次回溯，
划分尝试从 205,457 降至 204,884。去重命中为零。

准备阶段另运行了 A、D 的完整 release 路径校验，完整结果文件分别逐字节等于
此前对应阶段：16,265 条原成功边重放一致，34 条目标路径的基线接受 7 条，
候选赋值后接受 8 条。B、C 没有单独重跑完整转换器，其完整候选及保留程序与 A
精确相同。本轮没有完整转换流程的交错计时，也没有实际堆峰值测量。

## 源码与重测口径

| 阶段 | 冻结源码提交 |
| --- | --- |
| A | `4f32cb8ffcb911f9964553dd0dddfd8b942736f4` |
| B | `af4a2301d607cce72cb3ad5b0d50f848d312ddf3` |
| C | `9ba518da5a364bef088690f2ee245b58cce7582d` |
| D | `464783ae95ae940810050d4f94391f90d9a12c72` |

四阶段均使用 Rust 1.99.1（`58cf8f9c3`）、`x86_64-pc-windows-msvc`，同一新建
构建目录和命令：

```text
cargo +1.99.1 test --release --locked -p laneflow-lust-converter --lib --no-run --message-format=json
```

Cargo 输出确认被测测试程序的 `opt_level=3`、`debuginfo=0`、
`debug_assertions=false`、`overflow_checks=false`。构建脚本及过程宏存在
`opt_level=0` 的 host 制品，不能将“被测程序 opt-level 3”写成所有构建制品均为 3。
四份可执行文件分别冻结，测量前后以独立 `Get-FileHash -Algorithm SHA256` 复核；
完整提交、可执行文件摘要、实际 profile 和结果摘要见
[comparison.json](comparison.json)。这些构建产物摘要标识本次运行对象，
不承诺不同工作目录或机器的重新构建必然生成相同字节。

输入沿用 [#1093 的 inputs.json](../issue-1093-s1-efficiency/inputs.json)，SHA-256 为
`D2B2EED3FEE4B2559A60397BF387EB0E52EAA370A68CE42435E8B8BB5870513C`。
从上述冻结提交分别构建后，为各新进程设置 `S1_BENCH_INPUTS` 指向该文件，
`S1_OUTPUT_DIR` 指向尚不存在的输出目录，再执行测试二进制：

```text
<stage-test-executable> output::emit::s1::measurement::fixed_sample_search_measurement --exact --ignored --nocapture
```

计时范围是 17 条样本的搜索以及候选指标、结果构造，排除输入解析、原程序重放校验
与输出文件 I/O。每次进程另记录 CPU、进程墙钟时间及背景负载，不能把这几种范围混用。

预热顺序为 A B C D；正式测量按下列 8 个四阶段周期串行运行，每阶段每个位置各出现
两次。每块包含 10 个新进程，统计单位是 8 个块均值，不将 80 次进程视为 80 个独立块。

```text
A B C D | B A D C | C D A B | D C B A
D C B A | C D A B | B A D C | A B C D
```

没有绑定 CPU 亲和性或隔离机器。冻结协议的 `background_load_policy` 明确覆盖此前
负载超限即停止的条款；输入、可执行文件、输出、电源、模式及编译并发检查继续有效。

## 不完整尝试与交付边界

[stopped-attempts.json](stopped-attempts.json) 保留前三次尝试的状态摘要：

1. `attempt-01` 在 A 预热时停止，无正式块。背景 CPU 计算发现 PowerShell
   `Math.Max` 重载取整问题；修正后的区间值为 9.3866%，仍超过当时 9% 的限制。
   原记录保留，后续运行明确使用 double 重载。
2. `attempt-02` 在 B 预热时背景均值达到 5.2121%，超过当时 5% 的限制，无正式块。
3. `attempt-03` 取消负载中止后运行，随聊天中断结束，已持久化 10 个正式块；
   没有正常完成状态，不能当作完整批次或与后续批次拼接。

最终统计只采用完整的 `attempt-04`。预热、准备探针和不完整尝试不进入最终统计，
不是在完整批次中挑选最快数据。所有失败和中断原件仍保存在本地证据目录。
